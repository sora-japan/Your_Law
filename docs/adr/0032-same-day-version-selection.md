# ADR-0032: 同一施行日の版が複数ある場合は改正法令IDが最大のものを選ぶ

## Context and Problem Statement

ADR-0015 で現行版の特定を「施行日 ≤ 今日のうち最新」と決めたが、
同一法令・同一施行日のファイルが複数存在する場合の扱いを定めていなかった。

実装は施行日のみを比較していたため、同じ施行日の版が複数あると更新条件
（`enforce_date > latest[law_id]`）が偽になり、`rglob` が先に返したファイルが
残っていた。`rglob` の順序はファイルシステムに依存するため、
**どの版が選ばれるかが保証されない状態だった。**

評価では閾値・埋め込みモデル・検索方式を変えながら Recall@k や MRR を比較する。
比較が成立するには、変えていない部分が変わらないことが前提になる。
コーパスの内容が実行ごとに変わりうる状態では、数値の変化が設定変更によるものか
コーパス変化によるものか切り分けられない。

### 実測（2026-10-11 時点）

| 項目 | 値 |
|---|---|
| ファイル名の (法令ID, 施行日) が重複する組 | 86組 |
| うち施行済みで現行版の選択に影響する法令 | 28件（いずれも施行日 20261001） |
| 候補と他版の比較回数 | 33回 |

未施行の重複58組は現時点では選択に影響しないが、施行日の到来とともに
この28件に加わる。時間経過によって自然に増える性質の問題である。

## Decision Drivers

* 評価を繰り返す前提では、同じ入力から同じインデックスが得られる必要がある
* 古い版を選ぶと改正前の条文を現行として提示することになり、
  「法改正が自分に関係あるか」を根拠つきで示すというプロダクトの目的に反する
* ADR-0016 で「改正法令IDが最新の版が他を包含する」仮説を反例で棄却しているため、
  同じ仮説を無検証で採用すると記録として一貫しない

## Considered Options

1. 施行日のみで比較する（現状維持）
2. 改正法令IDが最大の版を選ぶ
3. 同一施行日の版をすべてインデックスする
4. ファイル名の辞書順で最初または最後のものを選ぶ

## Decision Outcome

Chosen option: **「改正法令IDが最大の版を選ぶ」**

比較キーを `(施行日, 改正法令ID)` のタプルとし、施行日が同じ場合のみ
改正法令IDで決着する形にした。Python のタプル比較は要素を順に評価するため、
「施行日で比べ、同じときだけ改正法令IDで比べる」が1つの式で表現できる。

選択肢1は再現性がないため採れない。

選択肢3は ADR-0016 の「1つに絞れない」という結論に沿う案だが、
28法令について条文が重複してインデックスされ、同じ条が検索結果に複数並ぶ。
後述の検証で条の取りこぼしが起きないと確認できたため、採用しなかった。

選択肢4は決定的になるが、選ぶ基準に意味がない。

### 決定性が成立する条件

本決定が決定性を保証するのは、比較キー `(施行日, 改正法令ID)` が法令内で
一意である場合に限る。同一の法令ID・施行日・改正法令IDを持つファイルが
複数存在すると、再び `rglob` の順序に依存する。

ファイル名は3要素で構成されるため、これは同名ファイルが複数ディレクトリに
存在する場合にのみ起きる。一括ダウンロードのデータで重複するファイル名を数え、
**0件**であることを確認した（2026-10-11）。
キーが一意であれば最大値が1つに定まるため、反復順序に関わらず結果は同一になる。

### 検証

改正法令IDが最大の版を候補とし、他の版の本則の条番号の集合と比較した（33回）。

* 他版にあって候補にない条: **0件**
* 33回中32回は条数が完全に一致
* 例外は `335M50000100012` の1件のみで、候補が4条多い（287条 vs 283条）

選択基準の変更により、現行版のチャンク総数は **706,026 → 706,075（+49）** に
変化した（同一プロセス内で両方式を測定し、日付による影響を排除）。
選択される法令数は 8,997 で変わらないため、この差は選ばれるファイルが
差し替わった結果である。最大でない改正法令IDの版が選ばれていた法令が
実在したことを示す。

### 改正法令IDの大小が公布年の順序と一致する根拠

法令IDの構造をデジタル庁の公式ドキュメントで確認した。
出典: https://laws.e-gov.go.jp/docs/law-data-basic/607318a-lawtypes-and-lawid/

15桁で「元号1桁＋年2桁 / 法令の種類9桁 / 番号3桁」の構造を持ち、
元号コードは 1:明治、2:大正、3:昭和、4:平成、5:令和 の昇順である。
したがって文字列の辞書順は公布年の順序と一致する。

改正法令IDはファイル名の3番目の要素で、改正する側の法令の法令IDである。
同じ構造が適用される。

### Consequences

* Good: 選ばれる版が決定的になり、インデックスが再現可能になった
* Good: 条の取りこぼしが起きないことを33回の比較で実測した
* Good: 法令IDの命名規則が一次出典で確認でき、文字列順が年代順と一致することを
  仕様から言えるようになった
* Good: 修正の効果を数値で示せた（+49チャンク）
* Good: チャンク数が減少ではなく増加した。改正法令IDが大きい版ほど条文が多いという
  逐次適用の解釈と向きが一致しており、弱い裏付けになる
* Bad: 条番号の集合のみを比較しており、同じ条番号で中身が異なる場合は検出できない。
  租税特別措置法では「条数は496で同じだが内容が違う条が129件」という実例がある
* Bad: 本則のみを比較した。附則は未検証
* Bad: 33回中32回は集合が完全に一致したため、この検証の識別力は低い。
  「最大が正しい版である」ことの積極的な根拠は `335M50000100012` の1件のみ
* Bad: 同年・異種類の改正法令IDが並んだ場合、文字列順は法令の種類コードで決まり
  公布順と無関係になる。28法令にこのケースはなく、すべて年または番号で決着したが、
  将来発生すれば基準が意味を失う
* Bad: 検証対象の施行日はすべて 20261001 であり、他の日付で成立するかは未検証
* Bad: 文字列順が示すのは公布の順序である。改正が条文に適用される順序と一致する
  という前提は、e-Gov「法令文書とバージョン管理」の「複数の改正規定が連続するとき、
  それぞれの改正規定は一つ前が溶け込んだ条文に対して適用される」という記述に
  依存する仮定であり、ファイル名からは適用順を読み取れない
* Bad: 未施行の重複58組は施行日の到来とともに対象に加わるため、再検証が必要になる
