# ADR-0031: 附則のメタデータに `Type` を使わず、`Extract` は本則と別キーで保持する

## Context and Problem Statement

附則をチャンク化するにあたり（ADR-0029）、`SupplProvision` が持つ属性のうち
どれをメタデータとして保持するかを決める必要がある。

法令標準XMLスキーマには以下の属性が定義されている。

* `AmendLawNum`: 改正附則が属する改正法令の番号
* `Type`: `"New"`（制定時）/ `"Amend"`（改正時）
* `Extract`: 抄録（一部を抜粋して収録）している場合に `true`

`Type` は「この附則が制定時のものか改正によるものか」を表すため、
出典表示や改正検知に使えると考え、実データでの分布を測定した。

| 値 | 件数 | 割合 |
|---|---|---|
| 属性なし | 358,760 | **99.1%** |
| Amend | 1,762 | 0.5% |
| New | 1,359 | 0.4% |

**99%の附則に `Type` 属性が存在しなかった。**
「`AmendLawNum` を持つ附則は `Amend` のはず」という想定も外れており、
`AmendLawNum` を持つ附則は大量にあるのに `Type` は 3,121 件しかない。

`Extract` の分布は以下のとおり。

| 値 | 件数 | 割合 |
|---|---|---|
| true | 237,897 | 65.7% |
| 属性なし | 122,501 | 33.8% |
| false | 1,483 | 0.4% |

本則の `Extract="true"` は 292 件（全法令の 2.7%）であり、
附則とは件数の桁が異なる。

## Decision Drivers

* 実データで使われていない属性を保持しても意味がないこと
* スキーマ上の定義が同じ属性を、本則と附則で別扱いする場合は理由が必要なこと
* 利用者に注記として表示するかは、評価の段階で判断できること

## Considered Options

`Type` について:
1. メタデータとして保持する
2. 保持しない

`Extract` について:
1. 附則には保持しない（本則の `is_extract` のみ）
2. 本則と同じ `is_extract` キーに入れる
3. `suppl_is_extract` として別キーで保持する

## Decision Outcome

### `Type` は保持しない

実データの 99.1% に属性が存在せず、メタデータとして機能しない。
スキーマに定義があることと、実データで使われていることは別であった。

**測定せずに実装していれば、使えないメタデータを組み込んでいた。**

### `Extract` は `suppl_is_extract` として別キーで保持する

当初は「附則の `Extract="true"` は改正法の附則からの抜粋という正常な収録方式であり、
66%に付いている以上ユーザーに伝える意味がない」として、附則には保持しない案を採った。

しかし**スキーマ上の定義は本則と附則でまったく同じ文言**である。

> `Extract`: `boolean` — 抄録（一部を抜粋して収録）している場合は `true` を指定します。

同じ意味の属性を、片方だけ保持して片方を捨てるのは一貫していない。
収録範囲の限界を利用者に伝えるという目的（ADR-0006）も、本則・附則で変わらない。

したがって保持する。ただし本則の `is_extract` とは**別のキー**とする。
同じキーに入れると「本則が抄録か」と「附則が抄録か」が区別できなくなるため。

値は `suppl.get('Extract') == 'true'` で `bool` に潰す。
「属性なし」と `false` が同じ扱いになるが、
スキーマの「抄録している場合に `true` を指定する」という定義からすれば
指定がない場合は抄録ではないと読むのが自然であり、`false` は 1,483 件にとどまる。
ただしスキーマに既定値の明記はなく、この解釈は確認できていない。

本則のチャンクにも `suppl_is_extract: False` を入れてキーを揃える。

`AmendLawNum` は `amend_law_num` として保持する（ADR-0004 の方針どおり）。
本則のチャンクには空文字を入れる。

### Consequences

* Good: 実データで使われない属性を保持せずに済む
* Good: 本則と附則で同じ属性を同じ基準で扱える
* Good: 全チャンクが同じキーを持ち、メタデータでの絞り込みが可能になる
* Bad: 附則の 65.7% が `true` となるため、注記として表示するとほぼ全ての附則に
  同じ文言が付く。表示するかどうかは評価の段階で判断する
* Bad: `Extract` の「属性なし」と `false` を区別していない。
  スキーマに既定値の記載がないため、この解釈は確認できていない
* Bad: 本則のチャンクに `suppl_is_extract: False` が入る。
  意味としては不自然だが、キーを揃えるための措置である
