# ADR-0037: 検索の指標は Recall@k と MRR に限り、指標を追加しない

## Context and Problem Statement

ADR-0027 で定量評価の範囲を限定し、検索側の指標として Recall@k / Hit@k /
MRR を想定していた。評価データが50問で確定した（ADR-0036）ことで、
各問の gold 件数が測れるようになり、**どの指標が実際に情報を持つのか**を
事前に判断できる状態になった。

指標は多いほど良いように見えるが、同じことを言い換えただけの数字が増えると
報告が散り、読む側は「どれを見ればいいのか」が分からなくなる。測る前に
決める。

### 実測した gold 件数の分布

`scripts/count_gold.py` で全50問の `len(row['gold'])` を集計した（2026-10-17）。

| gold 件数 | 問数 | 内訳 |
|---|---|---|
| 0 | 5 | unanswerable（意図的に空） |
| 1 | 31 | fact 10 / number 5 / negation 5 / long 5 / summary 5 / multi_doc 1 |
| 2 | 13 | comparison 5 / multi_doc 4 / situation 4 |
| 3 | 1 | situation 1 |

gold の総件数は 31×1 + 13×2 + 1×3 = **60件**。法令別に数えた内訳
（特商法16 / 建築基準法11 / 介護保険法10 / 都市計画法8 / 食品衛生法8 /
消防法7）の合計と一致しており、別経路の集計で同じ値が出ている。

回答可能な45問のうち、**gold が1件の問題が31問（69%）**である。

### Recall と Precision の分母は違う

混同しやすいので明記する。

```
Recall@k    = 上位k件で引けた正解の数 ÷ 正解の総数（gold の件数）
Precision@k = 上位k件に含まれる正解の数 ÷ k
```

Recall は「取りこぼしていないか」を問うので分母は**取るべきだったもの**、
Precision は「余計なものを混ぜていないか」を問うので分母は**取ってきたもの**
である。同じ「2件当たった」が、gold 3件なら Recall 0.67、k=5 なら
Precision 0.4 になる。

### gold が1件の問題では Recall@k と Hit@k が同値になる

```
gold が1件の問題:
  上位k件にその1件が入った   → Recall@k = 1/1 = 1.0,  Hit@k = 1
  入らなかった               → Recall@k = 0/1 = 0.0,  Hit@k = 0
```

**常に一致する。** 2つが異なる値になるのは gold が2件以上の問題（14問、
31%）だけであり、そこでのみ Recall は「3件のうち2件引けた」という部分点を
表現できる。

2つの指標が最も離れる場合を計算すると、

| | 値 |
|---|---|
| Hit@k 平均（全45問で1件は引けた場合） | 1.000 |
| Recall@k 平均（複数 gold は1件しか引けなかった場合） | 0.841 |
| **差の上限** | **0.159** |

つまり Recall@k が Hit@k に対して追加で表現できる幅は、最大でも約0.16に
とどまる。残りは同じ情報の言い換えである。

## Decision Drivers

* ADR-0011 で「網羅性を保証せず**再現率を実測する**」と決めている。
  再現率 = Recall であり、プロダクトが解決すると宣言した「抜けがないか
  確信が持てない」という不安に対応する指標である
* 指標の数より、各指標が何を意味するか説明できることを優先する
* 評価対象は45問しかない。対象が少ない指標を足しても、差が標本の揺れに
  埋もれて解釈できない
* 生成側の評価（RAGAS）と重複する指標を検索側に置かない

## Considered Options

1. Recall@k / Hit@k / MRR をすべて報告する
2. **Recall@k と MRR を報告し、Hit@k は計算するが報告しない**
3. Hit@k と MRR を報告する（Recall を落とす）
4. nDCG@k を追加する
5. Precision@k を追加する

## Decision Outcome

Chosen option: **「Recall@k と MRR を報告し、Hit@k は計算するが報告しない」**

```python
EVAL_K_LIST = (1, 3, 5, 10)
```

k ごとに Recall を出し、MRR はあわせて1つ報告する。

### Hit@k は計算するが報告しない

Hit は `find_rank` の戻り値から追加コストなしで得られる。

```python
rank = find_rank(gold_list, retrieved_list, k)
# rank is not None  → Hit
# 1 / rank          → RR（MRR の材料）
```

`find_rank` は MRR のために必ず呼ぶため、Hit の計算コストはゼロである。
したがって「計算するか」ではなく「**報告に載せるか**」だけが判断の対象になる。
載せない理由は、45問の69%で Recall と同値になり、読む側に「2つの数字が
ある」と誤解させるためである。

**ただし k=1 については Hit@1 を使う。** Recall@1 は gold 件数が分母に
入るため、

```
gold 3件の問題の Recall@1 → 上限 0.33
gold 1件の問題の Recall@1 → 上限 1.0
```

となり、「1位で正解を当てた」という同じ事実が分母によって違う数字になる。
k=1 に限っては Hit@1（0 か 1、分母に汚染されない）の方が読みやすい。

**これは情報の問題ではなく提示の問題である。** Recall@1 が 0.33 でも
`> 0` なので Hit@1 は復元できる（後述）。切り替える理由は「1位で当てた」が
0.33 と表示されると読み違えられるためで、失われた情報を取り戻すためではない。

### 選択肢3（Recall を落とす）を採らない理由

Recall は Hit の上位互換である。問題ごとの Hit は Recall から常に復元できる。

```
Hit = (Recall > 0)
```

gold 1件なら Recall と Hit は同値、2件以上なら Recall に部分点が乗る。
k=1 でも成立する（gold 3件で1位に当たれば Recall@1 = 0.33 > 0 なので
Hit@1 = 1）。したがって **Hit が持っていて Recall が持っていない情報は
存在しない。** 加えて ADR-0011 で再現率を測ると宣言している。

この復元は問題ごとの Recall を記録していることが前提になる（後述の
「問題ごとの正否を記録する」）。集計値の平均からは Hit の平均を逆算できない。

### 選択肢4（nDCG）を却下した理由

nDCG は順位に応じた減衰を入れることで、上位k件に入った正解すべてを順位込み
で評価する。3つの指標が何を見ているかを並べると、位置づけがはっきりする。

| 指標 | 正解の数 | 順位 |
|---|---|---|
| Recall@k | 全部見る | k件の中での順位は見ない |
| MRR | 最初に引けた1件だけ | 見る |
| nDCG@k | 全部見る | 見る |

`find_rank` は検索結果を外側、gold を内側でループして最初に一致した順位を
返すため、MRR が使うのは「最初に正解を引けた検索結果の順位」である。
複数 gold の問題で2件目・3件目がどこにいたかは捨てられる。
Recall@k は k を振れば粗い順位の情報は得られるが（Recall@1 と Recall@5 の
差）、k件の中での順位は値に影響しない。

したがって nDCG は **本評価データに実在する穴に対応している。**

却下の理由は、nDCG が**新しい情報を持つ範囲が14問しかない**ことである。

nDCG の値自体は、gold が1件の問題でも Recall や RR と一致しない。

| 正解の順位 r | RR = 1/r | nDCG@k | Recall@k |
|---|---|---|---|
| 1 | 1.0000 | 1.0000 | 1.0 |
| 2 | 0.5000 | 0.6309 | 1.0 |
| 3 | 0.3333 | 0.5000 | 1.0 |
| 5 | 0.2000 | 0.3869 | 1.0 |

しかし gold が1件なら、RR も nDCG もどちらも r の単調減少関数である。
問題の順序づけは同じになるため、**nDCG は RR の重みを変えただけで、
新しい情報を持たない。**

新しい情報が出るのは複数 gold の場合だけである。

```
gold 3件、1位・3位・4位で当たったとき
  Recall@5 = 3/3 = 1.0     ← 満点
  RR       = 1/1 = 1.0     ← 1位で当たったので満点
  nDCG@5   =       0.9060  ← 2件目以降が下にあるため満点にならない
```

したがって nDCG が Recall・MRR で言えないことを言えるのは、複数 gold の
**14問だけ**である。構成を比較したときにこの14問由来の差を読むことになり、
45問で測る Recall より揺れが大きい（指標全体が揺れるという話ではなく、
**他の指標との差分**が14問に依存するという話である）。

測って解釈できない数字を出すより、**検討して却下した記録を残す**方が価値が
あると判断した。評価データを増やして複数 gold が十分な数になれば、再検討
する余地がある。

### 選択肢5（Precision@k）を足さない理由

Recall は「正解を引けたか」だけを見て、**無関係な文書を何件混ぜたか**を
見ない。k=5 で正解1件なら残り4件はノイズで、それが生成の文脈に入る。
これは実在する穴である。

### 本評価データでは Precision を測れない

却下の理由は、**Precision が要求する判定を評価データが持っていない**
ことである。

| 指標 | 必要な関連性判定 | 評価データで足りるか |
|---|---|---|
| Recall@k | gold の各件について「引けたか」 | **足りる**。gold 以外を知る必要がない |
| Precision@k | **上位k件の各件**について「関連あるか」 | **足りない**。gold 以外は判定されていない |

ADR-0027 で埼玉県の一覧を「**最低限含まれるべき**法令の集合」として使うと
決め、ADR-0011 で「網羅性を保証しない」と宣言している。つまり
**gold に入っていない文書が無関係であるとは言えない。**

具体例を挙げる。建築基準法第6条が gold のとき、第7条のチャンクが引けたら
どうなるか。条レベルの gold では不一致なのでノイズに数えられるが、実際には
関連する可能性がある。Precision@k はこれを機械的に減点する。gold は
「少なくともこれは必要」という下限であって、「これ以外は無関係」という
上限ではないため、分母側（引いてきたもの）の良し悪しを判定できない。

これは情報検索の評価で、関連性判定が不完全な場合に Precision が成立しない
という既知の問題にあたる。Recall は gold 側だけを見るため不完全な判定でも
成立し、Precision は成立しない。**指標の選択が評価データの性質から決まる。**

### RAGAS の Context Precision との関係

ADR-0027 で RAGAS の Context Precision を使うと決めている。これは
「文脈に入った文書のうち関係あるものが上位に来ているか」を測るため、
検索側の Precision@k と**役割は重なる。**

ただし**同じものを二度測るわけではない。** 関連性の判定方法が違う。

| | 関連性の判定 |
|---|---|
| Precision@k（検索側） | 人手の gold との一致 |
| Context Precision（RAGAS） | LLM が参照回答に対して判断 |

LLM 判定の妥当性は未検証であり（評価方針で「人手との一致を検証してから
軽量化する」と決めている）、Context Precision が Precision@k の完全な
代替になるとは言えない。したがってこれは**補足であって、却下の主たる
理由ではない。** 主たる理由は前節のとおり、評価データが Precision に
必要な判定を持たないことである。

### 絶対値の読みにくさは却下の理由にしない

「gold が1件の問題では Precision@5 の上限が 0.2 になる」という性質がある
が、**これは却下の理由にしない。** この天井は全構成に同じように効くため
比較の邪魔をせず、k=1 の Recall が 1/件数 で天井に当たるのと同じ「読み方の
注意」にすぎない。加えて、サブセットでは Recall の絶対値も全件へ転移しない
（ADR-0033）。絶対値の読みにくさを理由に Precision を落として Recall を
残すのは筋が通らない。

### 不可答5問は検索指標では測れない

gold が空なので Recall も MRR も適用できない。これは検索側の欠陥ではなく
**評価の分担**である。不可答問題で測りたいのは「わからないと言えたか」
「ts043 / ts044 なら委任規定を示せたか」であり、生成側の棄権評価の仕事に
なる。検索指標を追加しても埋まらない。

検索の評価対象は45問、不可答5問は別枠として報告する（ADR-0034 の
「分母と総問数を並べて出す」）。

### 偶然の水準を併記する

**Recall@k の報告には、同じ条件で無作為に引いたときの値を併記する。**

サブセットは gold の法令を必ず全部含むため（ADR-0033）、その法令が
コーパスに占める割合が高くなる。状況型の gold は法令レベルなので、
この割合がほぼそのまま偶然の正解率になる。

5万件のサブセット（基準日 20261013）での実測値。

| 種類 | 偶然の Recall@5 |
|---|---|
| 条文型40問（gold が特定の条） | 約 0.0001 |
| 状況型5問（gold が法令レベル） | **0.079**（問題ごとに 0.037〜0.113） |

```
「Recall@5 = 0.72」            ← 読めない
「Recall@5 = 0.72（偶然 0.079）」 ← 読める
```

1万件のサブセットでは状況型の偶然の水準が 0.333（ts046 は 0.463）で、
実測が 0.6 でも「偶然より少し良い」以上のことが言えなかった。
**サイズを5万件に変更した判断そのものが、この計算から出ている**
（ADR-0033）。

全件で測るときも併記する（状況型 0.006、条文型 0.0000007）。サブセットと
全件で偶然の水準が14倍違うため、併記しないと「全件のほうが数値が低い」
ことの意味が読めない。

### 最大kで1回検索し、スライスで各kを測る

`EVAL_K_LIST = (1, 3, 5, 10)` の4通りを測る。k ごとに検索すると
45問 × 4 = 180回になるが、最大の k=10 で1回検索し、`find_rank` と
`calculate_recall_at_k` の内部にある `retrieved_list[:k]` でスライス
すれば45回で済む。

この代用が成り立つ条件は **「`n_results=10` の上位5件」が
「`n_results=5` の5件」と一致すること**である。Chroma の HNSW は近似
最近傍探索であり、`n_results` の値によってグラフの探索範囲が変わりうる。
変わる場合、`n_results=10` の方が広く探して `n_results=5` が見逃した
チャンクを拾い、順位がずれる。

**このずれは件数では検出できない。** どちらも5件返るため、
`len()` を見ても気づけない。ADR-0040 の `is_current` と同じ、
「検証していない軸に依存が残る」形である。

1問（特定商取引法のクーリング・オフ）で実測した。

| | 上位5件の `chunk_id` 連番 |
|---|---|
| `n_results=5` | `#211, #14, #15, #56, #23` |
| `n_results=10` の上位5件 | `#211, #14, #15, #56, #23` |

一致したためスライスを採用する。

**ただしこれは1問での確認であり、全45問での保証ではない。** 全問で
`search(k_max)[:k]` と `search(k)` を突き合わせる検証は未実施。
検索回数が4倍になっても測れる規模（180回）であるため、数値に疑義が
出た場合は k ごとの検索に切り替えて確認できる。

### 報告の形

種類別に分けて報告する（ADR-0035）。gold 1件の条文型と、法令レベルの
状況型を合算した平均は意味が薄い。

あわせて、集計値とは別に**問題ごとの正否を記録する。** 50問という少なさを
設計で補うためである。同じ50問を全構成に使うため、

```
閾値500が勝った問題: 8問
閾値1000が勝った問題: 3問
どちらも同じ: 34問
```

という対応のある比較ができる。集計値の差（例: 0.72 と 0.74）は1問の当たり
外れで 0.02 動くため、勝敗の数え方の方が強い情報を持つ。

## 追記（2026-11-05）: スライスの代用はハイブリッドでは成り立たない

「最大kで1回検索し、スライスで各kを測る」で、代用が成り立つ条件を
**近似探索が `n_results` に依存しないこと**と特定し、1問で確認した。

**この条件はベクトル検索についてのものであり、ハイブリッドには別の条件が
必要だった。そしてそれは成り立たない。**

### 反例

同じコレクション `ruri-v3-310m_1000_20261013_50055` に対し、
`EVAL_K_LIST` だけを変えて2回測定した（条文型40問）。

| 方式 | R@1 | R@3 | R@5 | R@10 |
|---|---|---|---|---|
| vector（`max(K)` = 10） | 0.4375 | 0.6250 | 0.7000 | 0.7375 |
| vector（`max(K)` = 100） | 0.4375 | 0.6250 | 0.7000 | 0.7375 |
| bm25（`max(K)` = 10） | 0.2000 | 0.3000 | 0.3375 | 0.4125 |
| bm25（`max(K)` = 100） | 0.2000 | 0.3000 | 0.3375 | 0.4125 |
| hybrid（`max(K)` = 10） | 0.3250 | 0.6000 | 0.6625 | 0.7500 |
| hybrid（`max(K)` = 100） | **0.2875** | **0.5250** | **0.6500** | **0.7750** |

**vector と bm25 は1桁も動かない。ハイブリッドは全ての k で動く。**

ベクトル検索については、本ADRで1問だけ確認していたスライスの代用が、
40問の全ての k で成り立つことが結果的に確認できた。BM25 は全件に
スコアを付けてから切るため、構造的に前方一致が保証される。

### 成り立たない理由

ハイブリッドの順位は2つのリストの**融合の結果**であり、融合の入力が
変わると出力の順位が変わる。

```
max(K) = 10    rrf(vector の上位10件,  bm25 の上位10件)
max(K) = 100   rrf(vector の上位100件, bm25 の上位100件)
```

11〜100位にいて**両方のリストに現れる**チャンクは、前者では存在しないが
後者では融合に参加する。そして RRF の性質上、それが片方で1位のチャンクを
追い越す。

```
片方1位のみ      1/(60+1)              = 0.016393
両方15位と12位   1/(60+15) + 1/(60+12) = 0.027222   ← こちらが勝つ
```

実例として `ts038`（long）は、`max(K)` = 10 では圏外だったが、
`max(K)` = 100 ではハイブリッドの**2位**である。

```
vector  23位   bm25  17位
RRF     1/(60+23) + 1/(60+17) = 0.012048 + 0.012987 = 0.025035
```

片方のリストにしか現れないチャンクの最大スコアは `1/(60+1)` = 0.016393
なので、この値には届かない。したがって `ts038` より上位にいる1件も
両方のリストに現れるチャンクであり、**両リストの上位20件付近に同時に
入っているチャンクは全体で1件しかない**ことになる。

### 本ADRへの帰結

```
vector / bm25   1回の測定で全ての k が読める（前方一致が成り立つ）
hybrid          k ごとではなく N ごとに測り直す必要がある
```

ハイブリッドの R@k は **k と N の2変数の関数**である。
`max(K) = 100` の測定から「N=20 のときの R@20」を読むことはできない。

リランキングの設計で N（取得件数）を決める際、候補ごとに測定を
回す必要がある。本ADRの決定（Recall@k と MRR に限る）は変わらないが、
**測定の手順が方式によって違う**ことを明示しておく。

## 追記（2026-11-05）: MRR の値は `max(EVAL_K_LIST)` に依存する

本ADRは「MRR はあわせて1つ報告する」としているが、**どの k の MRR かを
書いていない。** 実際には `find_rank` に渡す k で値が変わる。

```python
rank = find_rank(gold_list, retrieved_list, k)   # 内部で retrieved_list[:k]
```

`k` 件の外にある正解は `rank = None` となり、RR が 0 になる。
`k` を広げるとそれらに順位が付き、MRR が上がる。

vector 条文型40問での実測。

```
max(EVAL_K_LIST) = 10    MRR 0.5889880952380953
max(EVAL_K_LIST) = 100   MRR 0.5932493824755001
```

差は、10位の外にあった正解に順位が付いた分で説明できる。

```
ts018  null →  42位   +0.023810
ts022  null →  46位   +0.021739
ts029  null →  71位   +0.014085
ts030  null →  33位   +0.030303
ts036  null →  27位   +0.037037
ts038  null →  23位   +0.043478

0.5889880952380953 + (合計 ÷ 40) = 0.5932493824755001
実測                               0.5932493824755001
```

**小数点以下16桁まで一致する。** 測定のばらつきではなく、指標の定義が
変わったことによる差である。

したがって報告では **MRR@10 / MRR@100 のように k を明示する。**
`EVAL_K_LIST` を変えた測定どうしの MRR は、そのままでは比較できない。

Recall@k は k が名前に入っているため、この混乱は起きない。


## Consequences

* Good: 指標を増やさなかった理由を、推測ではなく実測（gold 件数の分布）
  で言える
* Good: 報告する数字が Recall@k と MRR の2つに絞られ、どちらが何を意味
  するか説明できる
* Good: nDCG という選択肢を知った上で、対象の少なさを理由に却下した
  記録が残る。評価データが増えたときの再検討の起点になる
* Good: Hit を計算し続けるため、後から報告に加える判断に切り替えても
  コードの変更が要らない
* Good: 偶然の水準を併記するため、数値が「偶然より良いか」まで含めて
  読める。偶然の水準を計算している評価は多くない
* Good: **スライスの代用が成り立つ条件を、方式ごとに切り分けられた。**
  本ADRは1問の実測で代用を採用したが、その検証はベクトル検索についての
  ものだった。BM25 は構造的に成り立ち、ハイブリッドは成り立たない
* Good: **ベクトル検索のスライス代用が、結果的に40問全ての k で確認できた。**
  本ADRが「1問のみ」として Bad に挙げていた点が、2回の測定の一致で
  部分的に埋まった（`max(K)` を 10 と 100 で変えても R@1〜R@10 が同一）
* Good: MRR が `max(EVAL_K_LIST)` に依存することを、16桁の検算付きで
  特定できた。**同じ名前の指標が別物になる経路を潰せる**
* Good: 最大kで1回検索しスライスする代用について、成り立つ条件（近似探索が
  `n_results` に依存しないこと）を特定し、実測で確認した。速さの話ではなく
  `find_rank` / `calculate_recall_at_k` の設計の正しさの話である
* Bad: 複数 gold の問題で、2件目・3件目の順位の情報を捨てている。
  nDCG を足さない判断の代償であり、「上位k件に入ったか」までしか言えない
* Bad: k=1 だけ指標が切り替わる（Recall@1 ではなく Hit@1）。報告時に
  説明が必要になり、表の作り方が揃わない
* Bad: 検索側でノイズの量を測らないため、「検索を良くしたら生成が良く
  なった」の説明は Context Precision に依存する。生成側の評価が回らないと
  この経路が検証できない
* Bad: ノイズの量を検索側で測るには、評価データに「無関係」の判定を足す
  必要がある。構成ごとに上位k件が変わるため、構成を増やすたびに人手の判定が
  増える。今回の50問の規模では現実的でなく、**評価データの設計から見直す
  話になる**。この穴は実装では埋まらない
* Bad: そのスライスの検証は1問のみである。**全45問での保証はない。**
  「確認した」と「保証されている」を区別して記載しているが、
  この区別が読み飛ばされると過大な主張になる
* Bad: 検索の指標の母数は45問であり、50問ではない。Recall@k や MRR の
  数値には母数45を併記する必要がある（ADR-0034）。不可答5問も検索自体は
  実行されるが、gold が空のため検索の指標では測れず、生成側の棄権評価が
  担当する。「評価データは50問」「評価全体で50問を使った」は正しく、
  「検索の Recall を50問で測った」が誤りになる
* Bad: **ハイブリッドの測定コストが方式によって違う。** N の候補ごとに
  測り直す必要があり、「最大kで1回」の方針が適用できない
* Bad: **過去の報告に MRR の k が書かれていない。** ADR-0025 の
  2026-11-04 の追記に載せた MRR は MRR@10 である。後から読むと
  どの k の値か分からない
