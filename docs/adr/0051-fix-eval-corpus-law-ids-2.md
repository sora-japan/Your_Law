# ADR-0051: 評価コーパスの法令集合を閾値から切り離して固定する

## Context and Problem Statement

チャンク閾値を変えた比較をしようとしたところ、投入件数がこうなった。

| 閾値 | 投入チャンク数 |
|---|---:|
| 1000 | 50,055 |
| 2000 | 50,084 |

**閾値を上げたのに件数が増えている。** 区切りを緩めたのだから減るか同じになるはずで、説明がつかなかった。

原因は `create_sub_chunks` の停止条件がチャンク数だったことである。

```python
for law_id in shuffled_law_ids:
    if len(result) >= target_num:
        break
    result.extend(chunks_by_law_ids[law_id])
```

法令を1本ずつ足し、目標チャンク数に届いたら止める。閾値を上げると1法令あたりのチャンクが減るので、目標に届くまでに入る法令が増える。

`SUBSET_TARGET_CHUNKS` は 50,000 で、`break` は足す前に判定するため、最後の1法令で目標を飛び越える。50,055 と 50,084 はその超過分の差だった。分割の異常ではない。

つまり **閾値を変えると評価コーパスに入る法令が変わっていた。**

候補法令の並び順は閾値に依存しない（`sorted()` と固定 seed）。その並びを先頭から足していくだけなので、法令集合は入れ子になる。閾値2000の集合は閾値1000の集合を丸ごと含み、そのぶん gold ではない法令が多い。

合計チャンク数は目標値のすぐ上に貼り付く作りなので、差は29件（0.06%）しか出ない。**合計を見ているだけでは、中身がずれていることに気づけなかった。**

発覚の経緯は、閾値2000のコレクションを作った直後である。「閾値を上げたのに件数が増えた」という1点だけが説明できず、そこから停止条件を読み直して分かった。

## Decision Drivers

* **閾値の比較では、分割の粒度だけが変わり、コーパスの中身は同じでなければならない。** 中身が変われば、測った差がどちらから来たのか分けられない
* **固定する量は、分割の前に決まるものでなければならない。** 分割したあとに数えるものは閾値に依存する
* 既存の閾値1000のコレクションと、そこで測った結果を無効にしたくない
* コーパスが変わったときに黙って進まず、止まってほしい

## Considered Options

1. **法令IDのリストをJSONに固定し、それで絞る**
2. 停止条件をチャンク数から法令数に変える
3. チャンク数を目標値ちょうどに切り詰める

## Decision Outcome

Chosen option: **「法令IDのリストをJSONに固定し、それで絞る」**

### チャンク数でも文字数でも固定できない

* **チャンク数** 分割したあとに数えるものなので、閾値に依存する
* **文字数** 同じ理由で依存する。`paragraph_chunking` は分割後の各チャンクに条見出しを前置するため、条が割れるたびに見出しが複製され、小さい閾値ほど総文字数が増える

```python
chunk['text'] = article_heading + chunk['text']
```

閾値に依存しないのは、分割の前に決まるものだけである。法令の集合、XMLファイル、基準日である。

**「少ししか変わらないから大丈夫」という判断は、どちらでも成り立たない。** 29件という差を根拠にしかけたが、合計が目標値に貼り付く作りでは、合計の差が中身の一致を保証しない。

### 法令IDのリストで固定する

* リストは閾値1000で作る。この閾値で測った結果が既にあり、同じ法令集合になればそれを使い続けられる
* 非gold法令は671本。gold は6本で、出どころが `eval_set.jsonl` なのでリストには含めない
* `scripts/export_subset_law_ids.py` がリストを生み、`src/ingestion/sub_set.py` の `select_sub_chunks` が使う
* `select_sub_chunks` は random も seed も目標件数も持たない。入力が同じなら必ず同じ結果になる
* `create_sub_chunks`（random と目標件数で選ぶ側）は、リストを作り直すために残す
* リストの法令がコーパスにない場合は `ValueError` で止める

基準日を引数で受け取るようにしたのと同じ考え方（ADR-0040）。**原則は立てていたが、サブセットには適用されていなかった。**

### 案2・案3を却下した理由

**案2（停止条件を法令数にする）** は、コードは短くなるが、法令集合が「seed とソート順と N」の組み合わせで決まる暗黙のものになる。将来XMLを追加・再取得すると候補集合が変わり、並び順も変わるため、同じ N でも別の法令が入る。それに気づく手段が無い。

**案3（チャンク数を目標値ちょうどに切り詰める）** は、法令の途中で切ることになる。`create_sub_chunks` の docstring にある「選択の単位は法令」という設計が崩れる。

### 旧実装と結果が一致することを確認した

旧 `create_sub_chunks` と新 `select_sub_chunks` の結果を閾値1000で比較した。

```
旧(目標チャンク数で止める)   50,055件
新(law_idのリストで絞る)     50,055件
chunk_idの集合が一致         True
```

`build_eval_index.py` を差し替えて閾値1000で走らせたところ、コレクション名が既存のものと衝突して停止した。モデル名・閾値・基準日・件数・前置の5つが一致しているということなので、**本番経路でも同じことが確認できた。**

既存の `ruri-v3-310m_1000_20261013_50055_prefixed` と、そこで測った結果はそのまま使える。

### 混入していた法令の影響

修正前後の閾値2000を比べると、条文型40問でこうなった。

| k | 修正前（50,084件） | 修正後（42,387件） |
|---|---:|---:|
| MRR | 0.7930 | 0.8068 |
| @1 | 0.6250 | 0.6500 |
| @3 | 0.8375 | 0.8375 |
| @5 | 0.8875 | 0.8875 |
| @10 | 0.9125 | 0.9125 |
| @20 | 0.9375 | 0.9500 |
| @30 | 0.9500 | 0.9500 |
| @50 | 0.9750 | 0.9750 |
| @100 | 1.0000 | 1.0000 |

余分な 7,697 チャンク（18.2%）が入っていた。gold ではないので全部が邪魔者である。これが R@1 で1問ぶん下げていた。

閾値1000と2000の差は R@1 で2問なので、**混入の影響が測りたかった効果の半分の大きさだった。** 直さずに進めていたら、閾値の効果を1.5倍に見積もっていた。

状況型5問は、修正前後で全ての値が完全に一致した。

## Consequences

* Good: **閾値を変えても評価コーパスの中身が動かなくなった。** 閾値の比較で、測った差が分割の粒度だけから来ていると言える
* Good: `select_sub_chunks` に random も seed も目標件数も無いため、**入力が同じなら必ず同じ結果になる。** 旧実装は seed に依存していた
* Good: リストの法令がコーパスにない場合は `ValueError` で止まる。**XMLや基準日が変わったときに、黙って別のコーパスで測ることがない**
* Good: 閾値1000の既存コレクションと測定結果が無効にならなかった。`chunk_id` の集合一致で確認している
* Good: ADR-0040 で「比較実験の間コーパスを固定する」という原則を立てていたため、**その適用漏れとして見つけられた。** 原則が無ければ29件の差で止まらなかった
* Bad: **投入チャンク数が閾値で変わるため、索引の大きさを目標値で抑えられなくなった。** 閾値200では 97,106件まで増えた。構築時間とディスクが閾値に引きずられる
* Bad: `evaluation/rag/subset_law_ids.json` という、**コードと別に管理するファイルが1つ増えた。** 評価セットに gold 法令が増えると、コーパスもそのぶん増える
* Bad: `create_sub_chunks` の呼び出し元が `export_subset_law_ids.py` だけになった。**本番経路から呼ぶと、また閾値でコーパスが動く状態に戻る。** docstring に用途を書いているだけで、仕組みでは防いでいない
* Bad: **29件という差を「小さいから影響がない」と判断しかけた。** 合計が目標値に貼り付く作りでは、合計の差が中身の一致について何も語らない。実際には R@1 を1問ぶん動かしていた
* Bad: **法令の本数の差は数えていない。** 測ったのはチャンク数（7,697件）だけである
* Bad: 過去に前置なしで測った閾値200と2000の結果は、法令集合が違うので今回の結果と並べられない。**前置なしの閾値1000は同じ閾値で選んでいるため集合が同じで、ADR-0050 の前置あり/なしの比較はそのまま有効である**
