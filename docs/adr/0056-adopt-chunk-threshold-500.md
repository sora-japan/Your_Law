# ADR-0056: チャンク生成の修正後に検索を測り直し、閾値を500に変更する

## Context and Problem Statement

ADR-0055 でチャンク生成の欠落を直した。号を持つ項が閾値を超えると項の柱書が
どのチャンクにも入らなかったものが、入るようになった。

**修正前の測定には、閾値比較だけに効く交絡があった。** 柱書が落ちる条件は
「号を持つ項が閾値を超えたとき」なので、**閾値が小さいほど欠落が多い。**
5方式の比較や渡す件数の比較はすべて同じ閾値1000のコーパスで測っており欠落の量も
同じだったが、閾値の比較だけは、比べている4つのコーパスで欠落の量が違っていた。

そこで4閾値のコレクションを修正後のコードで作り直し、同じ条件で測り直した。
コレクション名には `CHUNKING_VERSION`（`v2`）を入れて修正前のものと区別している。
チャンク数が偶然一致する場合に同名になるのを避けるためで、実際に閾値2000の
サブセットは修正前後で 42,387 のまま変わらなかった（ADR-0048 に追記する）。

### 改善幅が閾値の小ささに比例した

条文型40問、`hybrid-rerank`、`Recall@1` の修正前後の差である。

| | 閾値200 | 閾値500 | 閾値1000 | 閾値2000 |
|---|---:|---:|---:|---:|
| 修正前 | 0.5375 | 0.5875 | 0.7000 | 0.6500 |
| 修正後 | 0.7250 | **0.7375** | 0.7125 | 0.6625 |
| 差 | +0.1875 | +0.1500 | +0.0125 | +0.0125 |

状況型5問でも独立に同じ形が出た。`Recall@1` が 0.2000 / 0.3000 / 0.4000 / 0.3000
から 0.4000 / 0.4000 / 0.4000 / 0.3000 になり、**改善は200と500にだけ現れた。**

柱書が落ちる条件は「号を持つ項が閾値を超えたとき」なので、**閾値が小さいほど
該当する項が多い。** 改善が小さい閾値に集中したのは、修正の内容と向きが合う。
ただし該当する項の件数を閾値ごとに測っていないため、向きが合うというところまで
しか言えない。

**その結果、最適値が1000から500に移った。**

## Decision Drivers

* ADR-0054 で決めた順番を踏襲する。**`Hit@k` を最初のふるいにし、その後 MRR・
  文字数・時間で比べる**
* 生成に渡す件数と同じ k で評価する
* プロンプトを短く保つ
* 評価セットの条文型40問を基準にする。状況型は5問で1問の増減が 0.2 動く
* **法令を扱うので、根拠の完全性を重く見る**

## Considered Options

1. **閾値500**
2. 閾値1000（現状維持）
3. 閾値200
4. 閾値2000

## Decision Outcome

Chosen option: **閾値500**（選択肢1）

```python
CHUNK_THRESHOLD = 500   # 1000 から変更
COLLECTION_NAME = 'ruri-v3-310m_500_20261013_64593_prefixed_v2'
```

**`Recall@1` と `MRR@100` が500で頂点になる。** 条文型は 0.7250 → 0.7375 →
0.7125 → 0.6625 で、閾値に対して単調ではない。状況型の `Recall@1` は200・500・
1000が並び、2000だけ落ちる。状況型は5問なので頂点を特定できない。

### 閾値200は Hit@5 で落ちる

条文型40問、k=5。

| | 閾値200 | 閾値500 | 閾値1000 | 閾値2000 |
|---|---:|---:|---:|---:|
| Hit@5 | 0.925（37問） | **0.950（38問）** | **0.950（38問）** | **0.950（38問）** |
| MRR@5 | 0.8521 | **0.8646** | 0.8425 | 0.8146 |
| Recall@5 | 0.8500 | 0.8750 | 0.8750 | **0.8875** |
| 検索＋リランク | **1,635.6ms** | 2,138.1ms | 2,913.7ms | 4,388.8ms |
| 本文の上限文字数 | **1,000** | 2,500 | 5,000 | 10,000 |

検索時間は検索の中央値とリランクの中央値を足したもので、合計そのものの中央値では
ない。「本文の上限文字数」は「チャンク閾値 × 件数」で、**前置きを含まない。**
ADR-0055 で前置きを閾値の判定より後に足す形にしたため、チャンクは条見出しと柱書の
ぶんこれより長くなる。

**閾値200は答えられる問題が1問少ない。** `MRR` は500に次いで高く、時間と文字数は
最良だが、最初のふるいで落ちる。状況型の `Hit@5` は4閾値すべて 1.0 で、閾値を
選ぶ材料にならない。

### 閾値500は、本番の動作点で1000に負けていない

ハイブリッド＋リランキング、k=5。

```
Hit@5          0.950 対 0.950        同値
Recall@5       0.8750 対 0.8750      同値
MRR@5          0.8646 対 0.8425      500
検索＋リランク   2,138.1 対 2,913.7    500が775.6ms速い
本文の上限文字数  2,500 対 5,000        500が半分
状況型 Hit@5     1.0 対 1.0            同値
状況型 MRR@5     0.9000 対 0.8667      500
```

**1000が勝っているのは3点だけである。**

```
条文型 Recall@30   0.9625 対 0.9500   2条 gold の2条目1件ぶん
索引構築時間        3.8〜4.3秒 対 4.6〜5.4秒
チャンク数          50,047 対 64,593
```

どれも本番の動作点（k=5）の外か、起動時に1回払う費用である。索引構築時間は
同じコレクションで複数回測った幅で、閾値1000と500は範囲が重ならない。閾値2000は
1回だけの測定で 3.8秒、閾値200は 7.1秒である。

### 閾値の優位は方式にほぼ依存しない

条文型40問、k=5。左が閾値500、右が閾値1000。

| 方式 | Hit@5 | MRR@5 | Recall@5 |
|---|---|---|---|
| BM25 | 0.350 / 0.350 | **0.2863** / 0.2729 | 0.3250 / 0.3250 |
| ベクトルのみ | 0.850 / **0.875** | **0.7896** / 0.7488 | 0.8125 / **0.8250** |
| ハイブリッド（RRF） | **0.775** / 0.750 | **0.5958** / 0.5454 | **0.7000** / 0.6875 |
| ベクトル＋リランキング | 0.950 / 0.950 | **0.8646** / 0.8425 | 0.8750 / 0.8750 |
| ハイブリッド＋リランキング | 0.950 / 0.950 | **0.8646** / 0.8425 | 0.8750 / 0.8750 |

**`MRR@5` は5方式すべてで500が上である。** `Hit@5` と `Recall@5` は、採用候補の
リランキング系2方式とBM25で同値、ハイブリッドで500が上、**素のベクトル検索だけ
1000が上**になる。

素のベクトル検索を10件渡しで比べると、`Hit@10` 0.950 対 0.900、`MRR@10` 0.8046
対 0.7523、`Recall@10` 0.9250 対 0.8625 で、**3指標とも500が上である。** 1000を
好むのは k=5 のときだけで、候補として検討している k=10 では逆になる。

`Recall@1` と `MRR@100`（ADR-0052 の表と同じ指標）では5方式すべてで500が上である。

| 方式 | Recall@1 | MRR@100 |
|---|---|---|
| BM25 | 0.2375 / 0.2000 | 0.3219 / 0.3069 |
| ベクトルのみ | 0.6750 / 0.6000 | 0.8061 / 0.7567 |
| ハイブリッド（RRF） | 0.4000 / 0.3750 | 0.6178 / 0.5660 |
| ベクトル＋リランキング | 0.7375 / 0.7125 | 0.8667 / 0.8452 |
| ハイブリッド＋リランキング | 0.7375 / 0.7125 | 0.8668 / 0.8448 |

### 閾値2000は MRR・文字数・時間で負ける

2000は `Recall@5` が 0.8875、`Recall@10` が 0.9000、`Recall@100` が 1.0000 で
深い k では最良だが、**`Hit@5` は500と同じ 0.950 である。** `Hit` が同じで
`Recall` だけ高いのは、増えているのが2条 gold の2条目であり、答えられる問題は
増えていない。ADR-0054 が閾値1000を2000より優先したときと同じ論法が、そのまま
500に適用できる。

`MRR@5` は 0.8146 で4閾値中最低、本文の上限文字数は 10,000 で500の4倍、
検索＋リランクは 4,388.8ms で2倍かかる。状況型の `MRR@100` も 0.7667 で最低である。

### 渡す件数は5件のままでよい

閾値500、`hybrid-rerank`、条文型40問。

| 渡す件数 | Hit | MRR | Recall | 本文の上限文字数 |
|---|---:|---:|---:|---:|
| 3件 | 0.925（37問） | 0.8583 | 0.8625 | 1,500 |
| **5件** | **0.950（38問）** | **0.8646** | **0.8750** | **2,500** |
| 10件 | 0.950（38問） | 0.8646 | 0.8875 | 5,000 |

**k=5 が折れ点である構造が、閾値500でも再現した。** 3件から5件で `Hit` が1問
増え、5件から10件では `Hit` も `MRR` も動かない。`MRR@5` と `MRR@10` は
0.8645833333333334 で一致する。6位から10位に最初の正解がある問題は1問も無く、
`Recall` が +0.0125 増えるのは2条 gold の2条目が入るぶんだけである。

閾値1000では3件が 0.875（35問）だったのに対し、**閾値500では3件でも 0.925
（37問）取れる。** 浅い k でも成績が出る構成になっている。

状況型5問は3件の時点で `Hit` 1.0・`MRR` 0.9000 に達し、10件まで何も動かない。

## 今回の測定で優秀だった2構成

**閾値500では、ADR-0054 の最初のふるいが方式を絞れなくなった。**

閾値1000では素のベクトル検索の `Hit@10` が 0.900（36問）で落ちていた。
**閾値500では 0.950（38問）になり、`Hit` で落とせなくなった。**

ベクトル＋リランキング・5件は状況型の `Hit@5` が 0.8（5問中4問）で落ちる。
ADR-0054 が同じ理由で落としたのと同じ形である。残るのは3構成である。

| 構成 | Hit | MRR | Recall | 検索時間 | 本文の上限文字数 |
|---|---:|---:|---:|---:|---:|
| ベクトルのみ・10件 | 0.950 | 0.8046 | **0.9250** | **17.2ms** | 5,000 |
| ベクトル＋リランキング・10件 | 0.950 | **0.8646** | 0.8875 | 1,334.9ms | 5,000 |
| ハイブリッド＋リランキング・5件 | 0.950 | **0.8646** | 0.8750 | 2,138.1ms | **2,500** |

このうち**ベクトル＋リランキング・10件は、ハイブリッド＋リランキング・5件と
`Hit` も `MRR` も同値で、プロンプトが2倍になる。** `Recall` が +0.0125 高く
803.2ms 速いが、ADR-0054 の順番（`Hit` → MRR → 文字数 → 時間）では文字数で
落ちる。

**残る2構成が、今回の測定で優秀だったものである。**

| 構成 | 優れている点 |
|---|---|
| **ベクトルのみ・10件** | `Recall` 0.9250 で根拠の完全性が最良。検索が 17.2ms で最速。BM25索引もリランカーも不要 |
| **ハイブリッド＋リランキング・5件** | `MRR` 0.8646 で上位に来る。本文の上限が 2,500字 で最短。状況型 `Hit` も 1.0 |

`Hit` が同値（38問）なので「何問に答えられるか」では差がつかない。差は
「根拠が完全か」（`Recall`）と「上位に来ているか」（`MRR`）である。

`Recall` の差を問題数に戻すと 0.9250 × 40 = 37.0 に対し 0.8750 × 40 = 35.0 で
**2問分。** `Hit` が同じなので、この2問は「2条必要な問題で2条目まで引けたか」
の差である。条文型40問のうち9問が2条 gold、状況型5問はすべて複数 gold である。

**根拠が欠けると答えが実質的に間違う例を、すでに記録している。** ADR-0046 の
ts009（特定商取引法第26条）は `rank=1` / `Recall=1.0` でありながら第1項の8号が
文脈に入っておらず、回答が誤った。順位が良くても必要な部分が入っていなければ
誤答する。逆に順位が低くてもプロンプトに入っていれば読む機会はある。この非対称
から `Recall` を優先する理屈は立つ。

一方で、**プロンプトの中での位置が成績に効く**という報告がある
（[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9.pdf)）。`MRR` の差
0.06 を無視はできない。そして人手判定（ADR-0046）では検索が届いた36問のうち
○+△ が22問（61%）で、**文脈に入っていることは十分条件ではない**ことを自分で
確認している。

**どちらを採るかは `Recall` と `MRR` のどちらを重く見るかで決まり、それは
生成で測るまで決められない。** 人手判定は50問の手作業で、2構成を比べると
100問になる。LLM-as-a-Judge を使う案はあるが、どうするかはまだ決めていない。
本ADRで決めるのは閾値だけである。

## Consequences

* Good: **閾値の比較から交絡が消えた。** 4閾値を同じ修正後コーパスで測ったので、
  欠落の量が閾値ごとに違う状態での比較ではなくなった。これが測り直した一番の
  目的である
* Good: **ADR-0052 の結論は形が残った。** 「チャンクの分割幅には最適値がある」
  「閾値に対して単調ではない」は成立している。動いたのは最適値の位置だけである
* Good: **修正の効果が閾値ごとの改善幅として現れた。** `Recall@1` の改善が
  +0.1875 / +0.1500 / +0.0125 / +0.0125 と小さい閾値に集中し、ADR-0055 の修正が
  狙った向きに効いたことの裏付けになる
* Good: **本番の動作点でプロンプトが半分、検索が 775.6ms 速くなった。** `Hit` と
  `Recall` を落とさずに `MRR` が上がった
* Good: **閾値500は浅い k でも成績が出る。** 3件渡しで 0.925（37問）で、閾値1000
  の3件（35問）より2問多い
* Good: **`Hit@100` が 1.0 だったため、README に「区別できない」と書いていた点が
  分かった。** 条文型の `Recall@100` 0.9875 の不足 0.5 は、2条 gold の1問が片方
  しか引けていないという意味であり、まるごと外れた問題は無い（閾値1000で確認。
  閾値500では測っていない）
* Bad: **方式と渡す件数を決められなかった。** 閾値500では `Hit` でベクトルのみ・
  10件を落とせなくなり、ベクトルのみ・10件 と ハイブリッド＋リランキング・5件 の
  2構成が残った。`Recall` と `MRR` が逆を向くため、検索の指標では決着しない
* Bad: **生成で測っていない。** 本ADRの判断はすべて検索指標に基づく。どちらの
  構成が正しく答えられるかは確かめていない
* Bad: **人手判定（ADR-0046）は修正前・閾値1000のコーパスで行ったものである。**
  README の生成側の数字は測り直していない
* Bad: **索引構築が約1秒遅くなり、チャンクが 14,546件増えた。** 起動時の費用と
  ディスクが増える
* Bad: **ADR-0053 の k 依存が閾値に依存していた。** 「@10 では素のベクトル検索が
  上回る」は閾値500では成立するが、閾値1000では成立しない。方式の選択が k で
  決まるという構造自体が、閾値によって現れたり消えたりする
* Bad: **リランカーの優位が閾値に依存していた。** 閾値1000では `Hit@10` で2問
  勝っていたものが、500では同値になった。この依存関係は測るまで分からなかった
* Bad: **「本文の上限文字数」は上限ではなくなっている。** ADR-0055 で前置きを
  閾値の判定より後に足す形にしたため、チャンクは条見出しと柱書のぶん長くなる。
  実際のプロンプト長は測っていない
* Bad: **閾値200と2000は `hybrid-rerank` しか測っていない。** 方式ごとの比較は
  500と1000の間でしか行えない
