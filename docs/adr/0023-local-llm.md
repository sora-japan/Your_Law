# ADR-0023: ローカルLLM を採用し、準備フェーズと利用フェーズを分離する

## Context and Problem Statement

本プロダクトは、事業者が自由入力で自社の状況を記述し、
関係しそうな法令を提示する。入力には業種、従業員数、立地、開業時期などが含まれる。

扱う情報は2種類ある。

| 情報 | 出所 | 機微度 |
|---|---|---|
| 法令データ | e-Gov（公開情報） | なし |
| **事業情報** | **ユーザー入力** | **ある** |

法令データだけを扱うのであればクラウドの LLM API でも問題はない。
しかしユーザーが入力する事業情報は、企業によっては外部に出したくない情報である。

## Decision Drivers

* ユーザーの事業情報を外部に送信しないこと
* 法令データの取得には e-Gov への通信が必要であること
* 想定ユーザーは法令調査の初期段階にあり、情報の取り扱いに不安を持ちうること

## Considered Options

1. クラウドの LLM API を使う
2. ローカルLLM を使う
3. 法令検索のみローカルで行い、生成はクラウドに送る

## Decision Outcome

Chosen option: "ローカルLLM を使う", because
選択肢1・3はいずれもユーザーの事業情報を外部に送信する。
選択肢3は検索結果の条文とユーザーの状況をプロンプトに含めるため、
結局は事業情報が外に出る。

ローカルLLM を採用したうえで、処理を2つのフェーズに分離する。

**準備フェーズ（ネットワークを使用・事前処理）**

```
e-Gov XML一括ダウンロード → 現行版の特定 → パース → チャンク化
  → メタデータ付与 → 埋め込み → ベクトルDB
```

差分更新では e-Gov の `/laws` API を呼ぶが、送信するのは法令IDのみである。

**利用フェーズ（外部通信なし）**

```
自由入力 → 確認事項の選択 → 埋め込み → 検索 → LLM → 表示
```

**ユーザーの事業情報は、準備フェーズに一切登場しない。**
利用フェーズはすべてローカルで完結し、外部への通信が発生しない。

この分離を README とデータフロー図で明示する。

### Consequences

* Good: ユーザーの事業情報が外部に出ない構成を、データフローで示せる
* Good: 利用時にネットワークが不要（モデルと法令データを取得済みであれば）
* Good: LLM API の利用料が発生しない
* Bad: 実行環境のメモリと計算資源に制約される。
  埋め込みモデルと生成モデルを同時にメモリへ載せる必要があり、
  大きなモデルを選べない（ADR-0024 の埋め込みモデル選定に影響）
* Bad: クラウドの大規模モデルと比べ、生成の品質が劣る可能性がある
* Bad: レスポンス時間の目標（10秒以内）を満たせるかは未実測。
  生成が支配的になる見込みで、収まらない場合はモデルの変更、
  生成量の削減、ストリーミング表示などの対応が必要
* Bad: 利用者が自分の環境にモデルを用意する必要があり、導入の敷居が上がる
