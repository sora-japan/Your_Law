# ADR-0033: 比較実験用のサブセットは法令単位で抽出し、seedで固定する

## Context and Problem Statement

閾値（200 / 500 / 1,000 / 2,000）を振って Recall@k / MRR を比較する計画がある。
現行版の全チャンクは 706,075件（8,997法令、基準日 20261013）あり、
1万件の投入に98秒かかる実測から、全件投入は約1時間55分と見込まれる。
組み合わせごとに埋め込み直すため、全件で実験を繰り返すのは現実的でない。

ADR-0027 で「比較実験はサブセットで候補を絞り、最終的な数値は全件で測る」
という2段階方式を決めた。本ADRはそのサブセットの作り方を定める。

サブセットには2つの要件がある。

1. **評価データの gold に出てくる法令を必ず含む。** 含まれない法令は
   どんな検索方式でも引けないため、その問題の Recall が永久に 0 になる。
2. **同じ入力・同じ設定なら、毎回同一のサブセットになる。** 比較が成立する
   条件は「変えていない部分が変わらないこと」であり、コーパスが実行ごとに
   変わると、数値の変化が設定変更によるものかコーパス変化によるものか
   切り分けられない。

当初は `chunks[:10000]` で先頭から取っていたが、この並びは
`find_current_version_paths` の `rglob` 順に由来するため、特定の法令の
チャンクだけが偏って入る（実際に教科用図書検定規則のチャンクのみが
読み込まれる状態になった）。

## Decision Drivers

* ADR-0032 で潰したのと同種の問題（反復順への依存）を、新しく足す処理で
  再び持ち込まないこと
* 評価データの gold が含まれることを、ハードコードではなく評価データから
  自動で導くこと（問題を追加したときに更新を忘れない）
* サブセットが「現実にありうる小さいコーパス」であること
* **偶然に正解してしまう水準を、測りたい差より十分低くすること**（後述）

## Considered Options

1. 先頭から目標件数まで取る（当初の実装）
2. チャンク単位で無作為抽出する
3. 法令単位で無作為抽出し、gold の法令は必ず含める
4. 全件で実験する（サブセットを作らない）

## Decision Outcome

Chosen option: **「法令単位で無作為抽出し、gold の法令は必ず含める」**

選択肢1は `rglob` 順に依存し、偏りも再現性もない。

選択肢2を却下した理由が本決定の中心である。チャンク単位で抽出すると
「法令は同じだけ存在するが、条がランダムに欠けている」コーパスになる。
これは**実在しない状態**であり、そこで測った Recall が何を意味するのか
説明できない。さらに欠け方が法令ごとに異なるため、閾値を変えて比較した
ときに「閾値の差」と「欠け方の差」が混ざる。

法令単位なら「法令が少ない世界」になる。これは実在しうる状態なので、
数値の解釈が可能になる。

選択肢4は時間的に成立しない（全件1通りで約1時間55分、閾値4通りで約8時間）。

### 実装

* 選択の単位は法令。法令IDごとにチャンクをまとめ、法令IDを選ぶ
* gold の法令のチャンクを先に入れ、残りを無作為に足す
* 目標件数に達した時点で停止するため、**件数は目標以上になる**
* gold の法令だけで目標を超える場合は、その件数をそのまま返す
* gold の法令IDがコーパスに存在しない場合は `ValueError` で停止する
  （ADR-0034 参照）

### 決定性が成立する条件

以下の3つすべてが必要であり、1つでも欠けると再現性は成立しない。

| 対象 | 手段 | 固定するもの |
|---|---|---|
| gold の法令ID（集合） | `sorted()` | 反復順 |
| 候補の法令ID（集合） | `sorted()` | シャッフルの入力順 |
| 乱数 | `random.Random(seed)` | どのシャッフルをするか |

`sorted()` が2箇所必要なのは、**文字列の集合の反復順が実行ごとに変わる**
ためである。Python は起動ごとにランダムな値で `str` / `bytes` の
ハッシュを初期化する。

`random.sample` / `random.shuffle` は要素の**位置**を入れ替える操作であり、
入力の並びが変わると同じ seed でも結果が変わる。

したがって **`random.Random(seed)` だけでは再現性は成立しない。**
この挙動は後述の負の対照で実際に確認している。候補側の `sorted()` を
`list()` に差し替えると、seed を固定したまま別プロセス間で結果が食い違う。

乱数はモジュール共有の `random.seed()` ではなく `random.Random(seed)` で
独立したインスタンスを使う。同一プロセス内の他のコードが `random` を
使うと、呼び出し順で結果が変わるため。

> *class* `random.Random`([*seed*])
>
> Class that implements the default pseudo-random number generator used by
> the `random` module.
>
> — https://docs.python.org/3/library/random.html

ドキュメントの散文には「コンストラクタに渡すと種まきされる」と明記が
ないため、CPython 実装（`Lib/random.py`）を確認した。`__init__` が
`self.seed(x)` を呼び、docstring に
"Optional argument x controls seeding, as for Random.seed()" と記載がある。

### `list()` ではなく `sorted()` を使う

`random.sample` は Python 3.11 以降、集合を受け取らない。

```
TypeError: Population must be a sequence.  For dicts or sets, use sorted(d).
```

標準ライブラリが「集合をそのまま渡す」という最もありがちな誤りを入口で
止めてくれる。ただし `list()` で包めば型エラーは出ず、集合の反復順が
そのまま残る。`list()` と `sorted()` は見た目が似ており、違うのは順序の
保証だけである。コードにコメントで明記した。

## 目標件数を5万件とする

目標件数は当初1万件としていたが、評価データの確定（ADR-0036）後の
再測定を経て**5万件に変更した。** 判断の根拠を記録する。

### 1万件では偶然の正解率が高すぎた

評価データの gold に含まれる法令が1件（特定商取引法）から6法令に増えた
結果、サブセット1万件に占める gold 法令の割合が **41.0%（4,112件）** に
なった。ADR-0036 が「合計が3,000〜5,000件、目標1万件の3〜5割になる
可能性がある」と予測していた範囲に収まった。

状況型の gold は法令レベル（ADR-0035）であり「その法令のどのチャンクでも
正解」と判定するため、**この占有率がほぼそのまま偶然の正解率になる。**

無作為に5件引いて1件以上当たる確率を計算すると、1万件版ではこうなる。

| 法令 | チャンク数 | 占有率 | 5件で当たる確率 |
|---|---|---|---|
| 介護保険法 | 1,431 | 14.27% | **53.71%** |
| 建築基準法 | 942 | 9.40% | 38.95% |
| 都市計画法 | 553 | 5.52% | 24.71% |
| 消防法 | 511 | 5.10% | 23.02% |
| 特定商取引法 | 430 | 4.29% | 19.69% |
| 食品衛生法 | 245 | 2.44% | 11.64% |

状況型5問の「偶然の Recall@5」は 0.173〜0.463（平均 0.333）だった。
**ts046 は検索が何もしなくても 0.463 が出る。** 実測が 0.6 だったとして、
「偶然より少し良い」以上のことが言えない。

さらに問題ごとに偶然の水準が2.7倍違う（ts047 の 0.173 対 ts046 の 0.463）。
これは検索の難しさの差ではなく、**gold に挙がる法令の大きさの差**である。

### サイズと偶然の水準の関係

| サブセット | gold占有率 | 状況型の偶然のRecall@5 | 条文型 | 1回の投入 | 閾値4通り |
|---|---|---|---|---|---|
| 1万件 | 41.0% | 0.333 | 0.0499% | 2分 | 7分 |
| **5万件** | **8.2%** | **0.079** | **0.0100%** | **8分** | **33分** |
| 10万件 | 4.1% | 0.040 | 0.0050% | 16分 | 65分 |
| 全件 | 0.6% | 0.006 | 0.0007% | 115分 | 461分 |

```
1万 → 5万    時間4倍   偶然の水準4.2倍改善
5万 → 10万   時間2倍   偶然の水準2.0倍改善
```

**改善が逓減する。** 1万→5万は払った時間の分だけ効くが、5万→10万は
払った分しか効かない。5万を折り返し地点として採用した。

### 条文型は1万件でも問題がなかった

条文型の gold は特定の条であり、閾値1,000では条の79.2%が1チャンクに収まる
（ADR-0014）。当たりが1〜2件なので、偶然の Recall@5 は1万件でも 0.05% で
ある。**問題だったのは状況型だけだった。**

5万件にすることで、状況型5問をサブセットの比較実験から外す必要がなくなった。
45問すべてを同じコーパスで測れる。

### 偶然の水準は報告に併記する

ADR-0037 に追記した。「Recall@5 = 0.72」だけでは読めず、
「Recall@5 = 0.72（偶然の水準 0.079）」で初めて解釈できる。

## 検証

`scripts/verify_sub_chunks.py` で以下を確認した（2026-10-19、基準日 20261013）。

| 項目 | 値 |
|---|---|
| 全チャンク | 706,075 |
| サブセット | **50,055チャンク**（目標50,000、超過55） |
| サブセットの法令数 | **677 / 8,997（7.5%）** |
| gold の法令数 | 6 |
| gold の法令のチャンク数 | **4,112（8.2%）** |
| chunk_id の重複 | 0 |
| 別プロセス2回の chunk_id の並び | **完全一致** |

gold の法令ごとの内訳は、介護保険法1,431 / 建築基準法942 / 都市計画法553 /
消防法511 / 特定商取引法430 / 食品衛生法245。

件数の一致だけでは「中身は同じで順序だけ違う」を検出できないため、
`chunk_id` の並びを `diff` で突き合わせた。順序が変わると Chroma への
挿入順が変わり、HNSW の構築順が変わって近似探索の結果が変わりうるため、
順序まで一致させる必要がある。

**負の対照も確認した。** 候補側の `sorted()` を `list()` に差し替えると、
別プロセス間で `chunk_id` の並びが大きく食い違う。差分はある法令の
チャンクが連続した塊として現れ、これは選択の単位が法令であることの
副次的な裏付けにもなっている。

### この検証が見ていない範囲

`chunk_id` は `law_revision_id#連番` であり（ADR-0031）、メタデータの値を
含まない。したがって **`chunk_id` の `diff` はメタデータの一致を保証しない。**

実際に、`get_chunks_with_meta` の `is_current` が `datetime.now()` で
計算されていたため、日をまたぐとメタデータだけが変わる状態が残っていた
（ADR-0040 で修正）。**検証は検証した範囲しか保証しない。**

## 1法令あたりのチャンク数

サブセットに入った法令数は677件（全8,997法令の **7.5%**）。
1法令あたりのチャンク数は 50,055 ÷ 677 ≒ **73.9件**で、
全体の 706,075 ÷ 8,997 ≒ **78.5件**の **94%** にあたる。

1万件版では 10,014 ÷ 181 ≒ 55.3件（全体平均の70%）であり、サイズを
増やしたことで全体平均に近づいた。

gold を除いた無作為の部分だけを見ると 45,943 ÷ 671 ≒ **68.5件**で、
全体平均をまだ下回っている。

**チャンク数の分布の形（中央値、分散）は未測定であり、下回る原因の説明は
仮説にとどまる。** 目標件数に達した時点で停止する方式が小さい法令を
選びやすくする（固定サイズを埋めるほど、小さい要素が多く入る）可能性が
あるが、測っていないため断定しない。

確認できているのは、サブセットが **法令数で7.5%、かつ1法令あたりの
チャンク数が全体平均の94%** である世界だという事実までである。

## Consequences

* Good: サブセットが決定的になり、比較実験の前提が整った
* Good: 再現性を壊す経路を3つ特定し、それぞれに対策を入れた
* Good: 検証が「失敗するケースで失敗する」ことを負の対照で確かめたうえで
  一致を確認している
* Good: gold の法令を評価データから自動で導くため、問題を追加したときに
  更新漏れが起きない
* Good: **偶然の正解率を計算してからサイズを決めた。** 1万件のままでは
  状況型5問が解釈できない数字を出していた
* Good: サイズを5万件にしたことで、1法令あたりのチャンク数が全体平均の
  94%になり、代表性が上がった（1万件版は70%）
* Bad: gold の法令は必ず全部入れるため、**占有率は原理的に全件の水準まで
  下がらない。** 5万件での 8.2% は全件の 0.6% の約14倍であり、状況型の
  Recall の絶対値は全件へ転移しない
* Bad: 法令数7.5%の世界で測った Recall は、競合する文書が少ないため
  全件より良く出る。絶対値は参考値として扱う。相対順位が転移する保証も
  ない（ADR-0027）
* Bad: 目標件数を超えるため「5万件のサブセット」は正確には50,055件。
  境界に大きい法令が来れば超過は数百件になりうる。seed や目標件数を
  変えるたびに実測が必要
* Bad: 1回の投入が8分になった（1万件版は2分）。評価スクリプトを書いている
  間の試行が遅くなるため、配線の確認は小さいコーパスで行う必要がある
* Bad: 閾値を変えるとチャンク数が変わるため、**5万件に収まる法令数が
  閾値ごとに変わる。** 閾値200では法令数が減り、2000では増える。Recall の
  差には chunking の粒度とサブセットの法令構成の両方が含まれており、
  分離していない
* Bad: チャンク数の分布（中央値、分散）を測っていないため、1法令あたりが
  全体平均を下回る原因の説明が仮説のまま残っている
* Bad: サブセットの構成が評価データの gold に依存するため、評価データを
  追加するとコーパスが変わり、過去の数値と比較できなくなる（ADR-0036）。
  実際に gold が1法令から6法令に増えた結果、本ADRの数値を全面的に
  取り直すことになった
* Bad: `shuffle` と `sample` は同じ seed でも異なる並びを返す。将来
  乗り換えるとサブセットが変わり、過去の数値と比較できなくなる
* Bad: `chunk_id` による検証はメタデータの一致を保証しない。メタデータ
  全体を突き合わせる検証は未実装（ADR-0040）
