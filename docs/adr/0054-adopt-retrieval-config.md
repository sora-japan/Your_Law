# ADR-0054: 検索はチャンク閾値1000・ハイブリッド＋リランキング、生成に渡すのは5件とする

## Context and Problem Statement

ADR-0052 でチャンク閾値の採用を保留し、ADR-0053 で検索方式の採用を保留した。
保留の理由は同じで、**プロンプトの長さが「チャンク長 × 渡す件数」で決まるため、
3つを独立に決められない**ことだった。

決めようとしたところ、**手持ちの数字では決まらなかった。** 渡す件数の候補である k=5 で
比べると、条文型40問の `Recall@5` の差が 0.0125 しかない。

```
hybrid-rerank  0.8750
vector         0.8625
```

0.0125 は2条 gold の問題の片方1件ぶんで、**`Recall` が取りうる最小の刻み**である。
これを根拠に方式を決めることはできない。

さらに MRR を `max(EVAL_K_LIST)` = 100 で出していた。**ADR-0025 の 2026-11-05 の
追記で「以降は k を明記する」と決めていたのに、k=5 の判断に MRR@100 を使おうと
していた。**

そこで `compare_retrieval.py` に `--k` を足して保存済みの `rank` を k で切り直し、
**`Hit@k` を指標に加えた。** それで3つとも決まった。

## Decision Drivers

* **生成に渡す件数と同じ k で評価する。** 5件渡すのに `Recall@10` を報告すると、
  6位から10位で見つかった正解も数に入る。その正解はプロンプトに入らない
* **「答えられる問題が増えるか」を最初のふるいにする。** `Recall` の部分点は、
  1件も引けなかった問題を平均に紛れさせる
* プロンプトを短く保つ。生成が応答時間の9割を占める
* 評価セットの条文型40問を基準にする。状況型は5問で、1問の増減が 0.2 動く
* 実装の変更を小さく保つ

## Considered Options

いずれも前置あり（ADR-0050）・法令集合固定（ADR-0051）の測定で、指標は条文型40問。
「最大文字数」は「チャンク閾値 × 件数」で、実測ではなく上限値。**「検索時間」は
1問あたりの中央値**（検索とリランクの合計）で、その1問の中で候補100件の取得と
リランクが行われている。

| | MRR | Hit | Recall | 最大文字数 | 検索時間 |
|---|---:|---:|---:|---:|---:|
| 1. 閾値2000・hybrid-rerank・k=10 | 0.8042 | 0.950 | 0.9125 | 20,000 | 4,381.5ms |
| 2. 閾値2000・hybrid-rerank・k=5 | 0.8042 | 0.950 | 0.8875 | 10,000 | 4,381.5ms |
| 3. 閾値1000・hybrid-rerank・k=10 | 0.8292 | 0.950 | 0.8875 | 10,000 | 2,752.6ms |
| 4. **閾値1000・hybrid-rerank・k=5** | **0.8292** | **0.950** | **0.8750** | **5,000** | **2,752.6ms** |
| 5. 閾値1000・vector-rerank・k=5 | 0.8292 | 0.950 | 0.8750 | 5,000 | 1,927.0ms |
| 6. 閾値1000・hybrid-rerank・k=3 | 0.8167 | 0.900 | 0.8375 | 3,000 | 2,752.6ms |
| 7. 閾値1000・vector・k=10 | 0.7490 | 0.925 | 0.9000 | 10,000 | 26.7ms |
| 8. 閾値1000・vector・k=5 | 0.7454 | 0.900 | 0.8625 | 5,000 | 26.7ms |

測定では候補を常に100件取得して全件をリランクしているため、**検索時間は k に
依存しない。** 本番で取得件数を k に応じて減らす設計にすれば変わるが、現在は
`RETRIEVAL_K` と `GENERATION_K` が分離されていない。

**閾値2000はチャンク数が少ないのに遅い。**

| | 検索 | リランク | 合計 |
|---|---:|---:|---:|
| 閾値1000（50,055チャンク） | 46.0 | 2,706.6 | 2,752.6 |
| 閾値2000（42,387チャンク） | 40.5 | 4,341.0 | 4,381.5 |

リランクが 1.60倍（4,341.0 ÷ 2,706.6）になっている。チャンクが長いぶん、
クロスエンコーダに渡すトークンが増えるためである。平均チャンク長の比は 1.18倍
（50,055 ÷ 42,387）なので、**リランク時間は長さの比より速く増えている。** 原因は
特定していない。

## Decision Outcome

Chosen option: **「閾値1000・ハイブリッド＋リランキング・k=5」**（選択肢4）

```python
CHUNK_THRESHOLD = 1000   # 変更なし
GENERATION_K = 5         # 10 から変更
検索方式 = hybrid-rerank  # ADR-0025 のまま
```

**実装の変更は `GENERATION_K` の1行である。**

### MRR と Recall では決まらなかった

k=5 で vector と hybrid-rerank を比べると、**2つの指標がカテゴリごとに逆を向く。**

| | 条文型 MRR@5 | 条文型 Recall@5 | 状況型 MRR@5 | 状況型 Recall@5 |
|---|---:|---:|---:|---:|
| hybrid-rerank | **0.8292** | **0.8750** | 0.8667 | 0.4667 |
| vector | 0.7454 | 0.8625 | **1.0000** | **0.5667** |
| 差 | +0.0838 | +0.0125 | -0.1333 | -0.1000 |

条文型では hybrid-rerank、状況型では vector が上回る。しかも条文型の `Recall` の差
0.0125 は最小の刻みで、状況型は1問の増減が 0.2 動く母数である。**どちらを重く見るかで
結論が変わる状態だった。**

加えて vector は 2,726ms 速く、BM25 索引の構築（4.9秒）も不要である。時間を含めると
vector のほうが合理的に見えた。

### Hit@k を指標に加えた

**決められなかったので、指標を見直した。**

`Recall@k` は部分点を持つ。gold が2条ある問題で1条だけ引けると 0.5 になる。
**そのため「1件も引けなかった問題」が平均に紛れる。**

`Hit@k` は「上位k件に1件でも正解が入ったか」を 0 か 1 で見る。
`metrics.py` に `calculate_hit_rate` が既にあり、保存済みの `rank` から計算できる。

行き詰まったから足した指標だが、**妥当性の根拠は別にある。** 人手判定（ADR-0046）の
分析で、既にこの区切りを使っていた。

| | 問数 | ○+△ |
|---|---:|---:|
| 検索が届いた | 36 | 22（61%） |
| 検索が届かなかった | 9 | 0（0%） |

この「届いた／届かなかった」が `Hit` である。**1件も引けなかった問題の ○+△ は
0/9 だった。生成の成否を分けているのは `Hit` である。** だから `Hit` を最初の
ふるいに使う。

### 指標の刻み

部分点の有無が、指標の分解能を決める。条文型40問は gold が1条の問題が31、
2条の問題が9で、**3条以上の問題はない。**

```
1条の問題を引けた        1   ÷ 40 = 0.0250
2条の問題の片方を引けた   0.5 ÷ 40 = 0.0125   ← Recall の最小の刻み
```

```
Recall@5 0.8625 × 40 = 34.5   「34.5問ぶん」としか言えない
Hit@5    0.9000 × 40 = 36     「36問」と言える
```

**`Hit` は失敗した問題数をそのまま言える。** `Hit` の刻みは 1/40（0.025）で、
0.05 の差は2問である。3条の gold が1つでもあれば `Recall` の刻みは 1/240
（約0.0042）になるが、現在の評価セットにはない。

### Hit で5つに絞られる

| Hit | 1件も引けない問題 | 選択肢 |
|---:|---:|---|
| 0.950 | 2問 | 1 / 2 / 3 / 4 / 5 |
| 0.925 | 3問 | 7 |
| 0.900 | 4問 | 6 / 8 |

**選択肢6・7・8 は、答えられる問題が1〜2問少ない。** 落とす。

k=3（選択肢6）と素のベクトル検索（選択肢7・8）がここで消える。`Recall` では
選択肢7が 0.9000 で選択肢4（0.8750）より高いが、**`Hit` では1問少ない。**
素のベクトル検索は2条 gold の問題で片方を引いて `Recall` を稼ぐ一方、1件も
引けていない問題が多い。

### 残った5つのうち、4と5以外は劣位になる

| | MRR | Hit | Recall | 最大文字数 | 検索時間 |
|---|---:|---:|---:|---:|---:|
| 1. 閾値2000・k=10 | 0.8042 | 0.950 | **0.9125** | 20,000 | 4,381.5ms |
| 2. 閾値2000・k=5 | 0.8042 | 0.950 | **0.8875** | 10,000 | 4,381.5ms |
| 3. 閾値1000・k=10 | 0.8292 | 0.950 | **0.8875** | 10,000 | 2,752.6ms |
| 4. 閾値1000・k=5 | 0.8292 | 0.950 | 0.8750 | 5,000 | 2,752.6ms |
| 5. 閾値1000・vector-rerank・k=5 | 0.8292 | 0.950 | 0.8750 | 5,000 | 1,927.0ms |

**選択肢4は `Recall` だけが劣る。** 1・2・3 のいずれも `Recall` が 0.0125 から 0.0375
高い。その代わり MRR・文字数・時間では最良か同値である。

```
4 対 3   MRR 同値、Hit 同値、Recall −0.0125、文字数が半分、時間が同じ
4 対 2   MRR が上、Hit 同値、Recall −0.0125、文字数が半分、時間が速い
4 対 1   MRR が上、Hit 同値、Recall −0.0375、文字数が4分の1、時間が速い
```

**`Recall` の差を受け入れる根拠は `Hit` が同じであることである。** `Hit` が同じで
`Recall` だけ高いということは、増えているのが「2条 gold の問題の2条目」であり、
**答えられる問題は1問も増えていない。**

選択肢1の `Recall` 0.9125 は全選択肢で最高だが、`Hit` は 0.950 で選択肢4と同じ
である。`Recall` だけを見ていたら選択肢1を選び、プロンプト4倍・検索1.6秒遅いという
代償を払っていた。

k=10 については、さらに強い根拠がある。hybrid-rerank の MRR は k=5 と k=10 で
0.8291666666666666（表では 0.8292）と、小数点以下16桁まで一致する。

MRR は問題ごとに「最初に見つかった正解の順位」の逆数を使う。ある問題の最初の正解が
7位にあれば、k=5 では 0、k=10 では 1/7 として計算されるので、**値は必ず変わる。**
変わらなかったということは、**どの問題も最初の正解が5位以内か10位より後ろのどちらかで、
6位から10位には1問も入っていない**という意味である。`Hit` が 0.950 のまま動かないのも
同じことを示している。

つまり6位から10位の5枠には、2条 gold の問題の2条目しか入っていない。`Recall` が
+0.0125 増えるのはそのためで、**プロンプトを2倍にしても答えられる問題は1問も
増えない。**

これは件数を増やす一般的な傾向とも合う。渡した文脈の中で正解が先頭にあるときの
成績が最も良く、中央が最も悪いこと、そして読み手の成績が検索の `Recall` より早く
飽和すること（20件から50件で GPT-3.5-Turbo +1.5%、Claude-1.3 +1%）が報告されて
いる（[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9.pdf)）。
ただし文字数やトークン数の閾値は報告されておらず、Qwen3-8B（`config.LLM_MODEL`）
では測られていない。

### 4と5は条文型で同値。状況型の Hit で決めた

選択肢5（vector-rerank）は条文型の3指標すべてが選択肢4と同値で、**825.6ms 速い。**
条文型では選べない。

状況型5問、k=5。

| 方式 | MRR@5 | Hit@5 | Recall@5 |
|---|---:|---:|---:|
| hybrid-rerank | 0.8667 | 1.0 | 0.4667 |
| vector-rerank | 0.8000 | 0.8 | 0.4000 |

**vector-rerank は状況型で1問落とす**（`Hit@5` 0.8 は5問中4問）。825.6ms は本番の
生成時間（30,050ms）の 2.7% にあたるため、**状況型で1問落とさないほうを選んだ。**

状況型は5問で1問の増減が 0.2 動く母数であり、根拠としては弱い。README で
「プロダクト本来の用途」と位置づけたカテゴリであることを踏まえた判断である。

なお素のベクトル検索は状況型では `Hit@5` 1.0・MRR@5 1.0 で最良だが、条文型の
`Hit` で既に落ちている。

### 検索側より生成側のほうが伸びしろが大きい

```
検索の伸びしろ   Hit@5 を 0.950 から 1.0 にして 2問
生成の伸びしろ   届いた36問のうち14問が失敗している
```

**生成側のほうが7倍大きい。** そして検索を1問ぶん伸ばしても、61%しか成功に変わらない。
検索側への投資は収穫逓減に入っている。

## Consequences

* Good: **渡す件数と、評価する k が揃った。** これまで `GENERATION_K = 10` に対して
  `Recall@10` を見ていたが、件数を決める根拠がなかった。5件渡して `Hit@5` /
  `MRR@5` / `Recall@5` を報告する形になり、報告する数字が本番の構成と一致する
* Good: **MRR と `Recall` がカテゴリごとに逆を向いて決まらなかったところを、指標を
  1つ足して抜けられた。** `Hit` でふるってから MRR・文字数・時間で比べる順番にした
  ことで、判断が成り立った。1つの指標だけで決めたのではない
* Good: **`Hit@k` が、既に使っていた区切りを指標として明示した。** 人手判定の分析で
  「検索が届いた／届かなかった」で分けていたものが、これである
* Good: **`Hit@k` は問題数に戻せる。** 刻みが 1/40 なので「4問が完全に外れた」と
  断言できる。`Recall@k` の 34.5 は半端な数で、問題数として読めなかった
* Good: **`Recall` だけを見ていたら選択肢1（閾値2000・k=10、0.9125）を選んでいた。**
  `Hit` が同じであることが分かったため、プロンプト4倍・検索1.6秒遅いという代償を
  払わずに済んだ
* Good: **k=5 が折れ点であることが挟み込めた。** k=3 では2問落ち、k=10 では1問も
  増えない。`Recall` だけを見ていたら、0.0375 と 0.0125 という連続的な数字にしか
  見えなかった
* Good: **`compare_retrieval.py` に `--k` を足したことで、測り直さずに別の k を
  見られる。** 保存済みの `rank` が最小の順位なので、k で切り直すのは `find_rank` を
  k で呼ぶのと同じ結果になる。`--k 100` で走らせると `evaluate_retrieval.py` が
  出した MRR と16桁一致することを5方式で確認した
* Good: **実装の変更が `GENERATION_K` の1行で済む。** 閾値と方式は現状のままで、
  コレクションも測定結果もそのまま使える
* Good: **ADR-0052 と ADR-0053 の保留が閉じた。** どちらも「3つを組で決めるしかない」
  という理由で保留しており、本ADRがその組を決めた
* Bad: **生成で測っていない。** 本ADRの判断は検索指標に基づく。k=5 が k=10 より
  生成で良いかどうかは確かめていない。`evaluate_generation.py` に `--method` がなく、
  `RETRIEVAL_K` と `GENERATION_K` が分離されていないため、本番の構成
  （100件取得 → リランク → 上位5件）を生成側で再現できない
* Bad: **最後の1択を状況型5問で決めた。** 選択肢4と5は条文型で完全に同値で、
  差は状況型の `Hit@5` で1問だけである。1問の増減が 0.2 動く母数であり、
  **生成で測れば最初に覆る候補である**
* Bad: **プロンプトの長さを実測していない。** 「最大5,000字」はチャンク閾値 × 件数の
  上限値で、実際の文字数もトークン数も測っていない
* Bad: **閾値2000でリランクが1.60倍になる原因を特定していない。** 平均チャンク長の
  比が1.18倍なのに、リランク時間は 2,706.6ms から 4,341.0ms へ増えている
* Bad: **位置の影響を自分のデータで測っていない。** 正解を1位・3位・5位に置いた
  プロンプトで生成の正解率を比べれば確かめられるが、生成と人手判定が必要になる
* Bad: Hit@k を足したため、本ADRが ADR-0037 の決定を変更させている（同日に追記した）
* Bad: **`Hit@5` を 1.0 にしても生成が正しくなるとは限らない。** 自分の人手判定では、
  検索が届いた36問のうち ○+△ は22問（61%）だった。検索は必要条件だが十分条件では
  ない
