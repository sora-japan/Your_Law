# ADR-0025: ハイブリッド検索（ベクトル + BM25）とリランキングを自前で実装する

## Context and Problem Statement

ベクトル検索のみでは、条番号・法令名・専門用語といった
**固有名詞の完全一致**に弱い。一方 BM25 のような語彙ベースの検索は
言い換えや意味の近さを捉えられない。

日本語RAGでは、全角と半角の混在、略称と正式名称の使い分け、
同義語の揺れが検索に影響すると指摘されている。
法令には略称（`LawTitle` の `Abbrev` 属性）が存在し、
「個人情報保護法」と「個人情報の保護に関する法律」のような
表記の揺れが実際に発生する。

Chroma はハイブリッド検索をネイティブにサポートしていない（ADR-0024）。

また、日本語の BM25 には形態素解析が必要である。
PostgreSQL の全文検索を日本語で使う場合は pg_bigm や PGroonga などの
拡張が別途必要になる。

## Decision Drivers

* 固有名詞の一致と意味の近さの双方を捉えること
* 検索方式は比較実験の対象であり、条件を制御できること（ADR-0010）
* DB の移行に時間を使わないこと

## Considered Options

1. ベクトル検索のみ
2. ハイブリッド検索がネイティブな Qdrant へ移行する
3. pgvector へ移行し、PostgreSQL の全文検索と組み合わせる
4. Chroma のまま、BM25 と統合処理を Python で自前実装する

## Decision Outcome

Chosen option: "Chroma のまま、BM25 と統合処理を Python で自前実装する", because
選択肢2・3はいずれも DB の移行を伴う。移行に要する時間は、
本プロジェクトの論点（検索方式の比較と評価）に寄与しない。
選択肢3はさらに日本語全文検索の拡張導入が必要で、負担が大きい。

Python 側で形態素解析器と BM25 の実装を用いれば、DB を変えずに実現できる。
加えて ADR-0010 で「検索方式は評価対象のため自前実装する」と定めており、
BM25 の重みや統合方法を自分で制御できることは比較実験の前提でもある。

**統合には RRF（Reciprocal Rank Fusion）を用いる。**
ベクトル検索のスコア（コサイン、0〜1）と BM25 のスコア（上限なし）は
単位が異なり、単純に加算できない。RRF はスコアではなく順位のみを用いるため、
正規化を必要とせずに異なる検索結果を統合できる。

```
スコア = Σ 1 / (k + 順位)
```

`k` は定数（60 が慣例）。両方の検索で上位に入る文書が優先される。

**リランキングを併用する。**検索で上位20件を取得し、
日本語対応のクロスエンコーダで並べ直して上位5件に絞る。
リランカーはローカルで実行できるモデルを用い、ADR-0023 の設計と矛盾させない。

比較実験では以下を同一の評価データで測定する。

* ベクトル検索のみ
* BM25 のみ
* ハイブリッド（RRF）
* ハイブリッド + リランキング

**本ADRは proposed とする。** 実装前であり、
ハイブリッド検索とリランキングが実際に精度を改善するかは未検証である。
評価結果を踏まえて accepted に更新する。

## 追記（2026-11-04）: ハイブリッドの実測と採否

本ADRは `proposed` のままだった。実測が出たので記録する。

### 測定の条件

固定したコレクション `ruri-v3-310m_1000_20261013_50055`（5万チャンク）に
対して、vector / bm25 / hybrid の3方式を測定した。

gold のある45問を対象とし、不可答5問は検索で測るものがないため除いている
（ADR-0034 の C）。

コーパスを固定しているため、同じ方式の2回目の測定が前回と小数点以下
16桁まで一致している（ADR-0048）。以下の数字は再現する。

### 出力そのまま

### 条文型40問

| 方式 | MRR | R@1 | R@3 | R@5 | R@10 |
|---|---|---|---|---|---|
| vector | 0.5890 | 0.4375 | 0.6250 | 0.7000 | 0.7375 |
| bm25 | 0.2846 | 0.2000 | 0.3000 | 0.3375 | 0.4125 |
| hybrid | 0.5067 | 0.3250 | 0.6000 | 0.6625 | 0.7500 |

### 状況型5問

| 方式 | MRR | R@1 | R@3 | R@5 | R@10 |
|---|---|---|---|---|---|
| vector | 0.6000 | 0.3000 | 0.4000 | 0.4000 | 0.4000 |
| bm25 | 0.4917 | 0.2000 | 0.2667 | 0.2667 | 0.3667 |
| hybrid | 0.5333 | 0.2000 | 0.4000 | 0.4000 | 0.4667 |

状況型は5問しかないため、1問の増減で 0.2 動く。傾向としても読まない。

### ハイブリッドが勝つのは R@10 だけである

条文型40問、vector との比較。

```
R@1   0.4375 → 0.3250   下がった
R@3   0.6250 → 0.6000   下がった
R@5   0.7000 → 0.6625   下がった
R@10  0.7375 → 0.7500   上がった
MRR   0.5890 → 0.5067   下がった
```

本ADRの Bad に「1位の精度は上がるが上位3件の精度は下がる傾向があるという
報告もある」と書いていたが、**この傾向は再現しなかった。1位も下がった。**
上位は全面的に薄まり、10件まで広げたときにだけ勝つ。

### 差は4問に絞れる

条文型40問のうち、R@10 が vector と hybrid で違うのは4問だけである。

| 問題 | vector | bm25 | hybrid | |
|---|---|---|---|---|
| ts005 | 0.000 | 1.000 | 1.000 | 救出 |
| ts023 | 0.000 | 1.000 | 1.000 | 救出 |
| ts021 | 1.000 | 0.000 | 0.000 | 脱落 |
| ts031 | 1.000 | 0.000 | 0.500 | 脱落 |

いずれも R@10 の値である。保存済みの jsonl の該当する4行を開けば確認できる。

```
救出 +2.0   脱落 -1.5   差 +0.5   →  40で割って +0.0125
```

残り36問は vector と hybrid で同じ結果である。

**脱落の仕組みが具体的に見える。**

```
ts021  vector で7位だった正解が、10件の外に出た。bm25 側は R@10 が 0.000
ts031  gold が2つあり、片方が落ちて 1.000 → 0.500。bm25 側は R@10 が 0.000
```

どちらも **BM25 が1件も正解を引けていない問題**である。RRF は両方の
リストの順位だけを見るため、片方が無関係な結果を返してもその順位は
加算される。ハイブリッドの代償はここに出る。

なお `ts024` は BM25 で6位に入っていたが、RRF では10件に届かなかった。
**BM25 が引けることと、ハイブリッドで救えることは別である。**

### 時間は採否の理由にならない

検索時間（条文型40問、ミリ秒、`compare_retrieval.py` で集計）

| 方式 | 中央値 | 平均 | 最大 |
|---|---|---|---|
| vector | 15.7 | 19.6 | 160.7 |
| bm25 | 12.5 | 13.4 | 27.4 |
| hybrid | 28.5 | 32.6 | 119.4 |

ハイブリッドは中央値で **+12.8ms**。生成は TTFO が 17.5〜20.9秒
（2026-10-04 の生成ベンチマークの実測）なので、13ms は全体の 0.1% 未満
である。**時間を根拠にハイブリッドを却下することはできない。**

判断には中央値を使う。

```
          条文型            状況型
vector    15.7 → 19.6 +25%  15.0 → 15.3  +2%
bm25      12.5 → 13.4  +7%  12.6 → 12.9  +2%
hybrid    28.5 → 32.6 +14%  29.7 → 29.9  +1%
```

左が中央値、右が平均。ベクトルを使う方式の平均だけが条文型で大きく
膨らむ。最大値は3方式とも ts001 で、vector は2問目に 25.9ms へ落ちる。
bm25 は ts001 が 10.8ms で最小級である。

**bm25 だけ初回が遅くないことから、これは埋め込みモデルの初回推論である。**
ts001 は条文型の1問目なので、状況型には現れない。平均を使うと1問が
全体を歪めるため、判断には中央値を使う。

### 索引の構築に起動時 4.6〜4.7秒かかる

BM25 を使う方式には、検索時間とは別の固定費がある。

```
bm25    チャンクの取得と索引の構築: 4.7秒
hybrid  チャンクの取得と索引の構築: 4.6秒
vector  なし（Chroma が構築済みの索引を持つ）
```

5万チャンクでの値である。全件（706,075チャンク）では未測定で、
行数に比例するとは限らない（CountVectorizer の語彙構築が入る）。

プロセスごとに1回なので、常駐するサービスなら起動時のみ。ただし
**CLI で1問ずつ実行する使い方では毎回かかる。** 1問あたり +12.8ms より
こちらが支配的になる。

### 採否を決めるのは「生成に渡す件数」である

当初「リランキングの有無で結論が変わる」と整理したが、機構が違う。
反転させるのは**生成に渡す件数**である。

```
10件すべてを文脈に入れる
  → 答えが文脈にあるかだけが効く。順序は二次的
  → 効く指標は R@10。hybrid 0.7500 > vector 0.7375  →  hybrid

件数を減らす（k=5 や k=3）
  → 10件の中の順序が効く
  → 効く指標は R@5 / R@3。vector 0.7000 > hybrid 0.6625  →  vector
```

**リランキングは後者の前提を変える手段である。** 並べ替えが効けば、
hybrid の10件から良い5件を取り出せる。つまりリランキングは
「件数を減らしたいが vector に負けたくない」場合に効く。

生成の評価は検索結果をすべて `build_context` に渡している。

```python
search_results = db.search(collection, embed_model, query_text, config.GENERATION_K)
context = build_context(search_results)
```

件数を決めているのは `config.GENERATION_K` である（値は `config.py` を参照）。
**この設計のままなら hybrid を採用する。**

件数を減らす判断（ADR-0045 の Bad「k=10固定で件数の影響を見ていない」）を
採るなら、リランキングを実装してから決める。

### 採用しても生成の評価には反映されない

生成の評価は `db.search` を直接呼んでおり、**検索方式を切り替える引数が
ない。** `evaluate_retrieval.py` の `--method` に相当するものが生成側に
存在しないため、hybrid を採用すると決めても、生成の評価はベクトル検索の
ままになる。

ハイブリッドの採用は、生成側の検索呼び出しを差し替えるまで完了しない。

## 追記（2026-11-05）: 2026-11-04 の追記の訂正

### MRR の表記

2026-11-04 の追記に載せた MRR は、すべて **MRR@10** である。
`find_rank` に渡す k が `max(EVAL_K_LIST)` = 10 だったため、
10位の外にある正解は RR が 0 になっている。

`EVAL_K_LIST` を変えると同じ名前で別の値が出る（ADR-0037 の
2026-11-05 の追記）。以降は k を明記する。

### 削除する Bad

```
Bad: rrf の戻り値を件数で切っていないため、ハイブリッドだけ結果が
     最大20件になる。今回のデータは正解の順位が最大6位なので数値に
     影響はないが、構造としては他の方式と条件が揃っていない
```

**この項目は誤りである。削除する。**

`find_rank` と `calculate_recall_at_k` はいずれも `retrieved_list[:k]`
で切っているため、`rrf` の戻り値が何件でも指標は上位 k 件しか見ない。

さらに「条件が揃っていない」という評価そのものが成り立たない。
BM25 は5万件すべてにスコアを付けてから k 件に切っており、ベクトル検索も
索引は5万件全体に張られている。**どの方式も内部で見ている候補の数は
揃っていない。** 測定は3方式すべてに「上位 k 件を出せ」と要求しており、
条件は揃っている。検索を2回走らせる分のコストは `+12.8ms` として
測って報告済みである。

代わりに残すべき問題は別の場所にある。

```
Bad: rrf は件数で切らないため、戻り値は最大 2k 件になる。
     find_rank と calculate_recall_at_k は [:k] で切るので検索の指標は
     壊れないが、build_context は切らない。生成に繋ぐときに
     GENERATION_K を超えた文脈が静かに渡る
```

## 追記（2026-11-05）: 取得件数を100件まで広げて測った

リランキングは並べ替えであり、**取得した候補の外にある正解には届かない。**
したがってリランキングを実装する前に、候補を増やす価値があるかを測った。

`EVAL_K_LIST` を `(1, 3, 5, 10, 20, 30, 50, 100)` に変更し、
同じコレクション `ruri-v3-310m_1000_20261013_50055` に対して
3方式を測定した。コードの変更はない。

### 条文型40問

| 方式 | R@1 | R@3 | R@5 | R@10 | R@20 | R@30 | R@50 | R@100 |
|---|---|---|---|---|---|---|---|---|
| vector | 0.4375 | 0.6250 | 0.7000 | 0.7375 | 0.7375 | 0.7875 | 0.8625 | 0.8875 |
| bm25 | 0.2000 | 0.3000 | 0.3375 | 0.4125 | 0.5625 | 0.6000 | 0.7125 | 0.7875 |
| hybrid | 0.2875 | 0.5250 | 0.6500 | 0.7750 | 0.8625 | 0.8625 | 0.8625 | 0.9625 |

MRR@100 は vector 0.5932 / bm25 0.3034 / hybrid 0.5009。

### 状況型5問

| 方式 | R@1 | R@3 | R@5 | R@10 | R@20 | R@30 | R@50 | R@100 |
|---|---|---|---|---|---|---|---|---|
| vector | 0.3000 | 0.4000 | 0.4000 | 0.4000 | 0.7000 | 0.7000 | 0.8000 | 0.8000 |
| bm25 | 0.2000 | 0.2667 | 0.2667 | 0.3667 | 0.4667 | 0.6667 | 0.7667 | 0.8667 |
| hybrid | 0.2000 | 0.3000 | 0.3000 | 0.4667 | 0.5667 | 0.7000 | 0.8000 | 1.0000 |

5問なので1問で 0.2 動く。傾向としても読まない。

### リランキングの余地は大きい

```
条文型   hybrid R@10 0.7750 → R@100 0.9625    +0.1875
状況型   hybrid R@10 0.4667 → R@100 1.0000    +0.5333
```

**100件取れば、正解はほぼすべてその中にある。** リランキングが
並べ替えで届く範囲が、10件のときの 0.7750 から 0.9625 に広がる。

候補を増やす価値があることが、実装前に確認できた。

### 10件では3方式すべて圏外だった7問の行方

`EVAL_K_LIST` が 10 だった測定で、vector / bm25 / hybrid のいずれでも
`rank` が null だった問題が7つある。100件まで広げた結果。

| 問題 | gold | vector | bm25 | hybrid |
|---|---|---|---|---|
| ts011 | 2 | 圏外 | 35位 | 70位 |
| ts018 | 1 | 42位 | 圏外 | 77位 |
| ts022 | 1 | 46位 | 圏外 | 90位 |
| ts029 | 2 | 71位 | 63位 | **圏外** |
| ts030 | 2 | 33位 | 圏外 | 62位 |
| ts036 | 1 | 27位 | 31位 | 14位 |
| ts038 | 1 | 23位 | 17位 | **2位** |

**6問は件数を増やせば救える。** `ts038` は10件では圏外だったものが、
100件取るとハイブリッドの2位である。

`ts029` だけ逆向きである。vector が71位、bm25 が63位で**両方が100件の
中に見つけているのに、ハイブリッドの上位100件には入っていない。**

```
両方63位と71位   1/(60+63) + 1/(60+71) = 0.00813 + 0.00763 = 0.01576
片方1位のみ      1/(60+1)                                   = 0.01639
```

RRF は「両方のリストに出ているか」を評価するが、**両方で下位なら
片方の1位にも勝てない。** そして200件を100件に絞る過程で押し出される。

### ハイブリッドの R@k は取得件数にも依存する

**上の表の `R@20` を「N=20 で走らせた結果」と読んではいけない。**

```
hybrid R@10   N=10 で走らせた   0.7500
              N=100 で走らせた  0.7750
```

同じ k でも値が違う。融合の入力が変わると上位の中身が組み替わるためで、
vector と bm25 では起きない（ADR-0037 の 2026-11-05 の追記に詳細）。

したがって **N の候補ごとに測り直す必要がある。**

### `rrf_k = 60` が効く定数になった

本ADRの Bad に「RRF の `rrf_k=60` は Cormack ら（2009）の経験値を
そのまま使っており、本プロジェクトで振っていない」と書いていた。
N を増やす設計では、この定数が結果を左右する。

```
片方1位のみ      1/(60+1)              = 0.016393
両方15位と12位   1/(60+15) + 1/(60+12) = 0.027222
```

N が大きいほど「両方のリストに現れる」チャンクが増え、片方で上位
だったチャンクが押し下げられる。N=10 から N=100 にしたときに
`R@1` が 0.3250 から 0.2875 に下がったのは、この効果である。

**候補を増やすほど上位が薄まる。** リランキングで並べ直すならそれでも
よいが、リランキングなしで N を増やすのは逆効果になる。

### 当初の計画（上位20件 → 上位5件）について

本ADRの Decision Outcome に「検索で上位20件を取得し、日本語対応の
クロスエンコーダで並べ直して上位5件に絞る」と書いている。

測定できる状態になったが、**N=20 での測定はまだ無い。**
上の表の `R@20` は N=100 で走らせた結果の上位20件であり、
N=20 で走らせた結果とは別物である。

```
必要な測定   N=20 / N=30 / N=50 で、それぞれハイブリッドを回す
読む値       その N での R@N（リランキングの天井）
             その N での R@5（リランキングなしの値、比較の基準）
```

### 検索時間（100件取得、条文型40問、ミリ秒）

| 方式 | 中央値 | 平均 | 最大 | 10件のときの中央値 |
|---|---|---|---|---|
| vector | 24.3 | 31.7 | 244.5 | 15.7 |
| bm25 | 12.3 | 13.1 | 26.2 | 12.5 |
| hybrid | 31.4 | 34.7 | 110.8 | 28.5 |

**BM25 は件数を増やしても変わらない。** 5万件すべてにスコアを付けてから
切っているため、`argsort` の後のスライスが10か100かの差しかない。

vector が +8.6ms なのは HNSW がより広く探索するためである。
それでも35ms以下で、生成の TTFO（17.5〜20.9秒）の 0.2% にとどまる。

索引の構築は bm25 4.5秒 / hybrid 3.8秒（11/03 は 4.7 / 4.6秒）。

### Consequences

* Good: DB を変えずにハイブリッド検索を実現できる
* Good: BM25 の重み、RRF の定数、統合方法を制御でき、比較実験の条件を揃えられる
* Good: 略称と正式名称の揺れなど、語彙一致が効く場面に対応できる
* Good: **ハイブリッドの代償が2問（ts021 / ts031）に特定でき、仕組みまで
  辿れた。** どちらも BM25 側が1件も正解を引けていない問題で、RRF が
  順位しか見ないことの直接の帰結である。「ハイブリッドは精度が上がる」
  という一般論ではなく、何を得て何を失うかを問題単位で言える
* Good: **時間の実測が出たことで、保留していた判断から「遅いかもしれない」
  という未知が消えた。** +12.8ms は生成の TTFO の 0.1% 未満である
* Good: Bad に書いていた外部の報告（1位は上がるが上位3件は下がる）が
  **再現しなかったことを自分の測定で確認できた。** 借りてきた傾向を
  そのまま前提にしない根拠になる
* Good: 中央値を使う判断が実測で裏付けられた。bm25 だけ初回が遅くない
  という対照があるため、初回の遅さが埋め込みモデルに由来すると言える
* Good: **リランキングを実装する前に、実装して効く範囲を測れた。**
  候補を100件に広げるとハイブリッドの R@100 が 0.9625（状況型は 1.0）に
  達し、並べ替えで届く範囲が 0.7750 から大きく広がる
* Good: **10件で届かなかった7問の行方を問題単位で特定できた。**
  6問は件数で救え、`ts029` はハイブリッドが落としている。「リランカーで
  改善しなかった」が起きたときに、候補の問題か並べ替えの問題かを
  切り分けられる
* Good: **`rrf_k = 60` が結果を左右する定数であることが実測で出た。**
  Bad に挙げていた「振っていない」が、振る必要のある項目に変わった
* Good: 本ADRの Decision Outcome に書いた「上位20件 → 上位5件」という
  計画が、測定可能な形になった
* Bad: 実装量が増える。形態素解析、BM25 インデックスの構築と保持、
  RRF、リランカーの4つを自前で用意する必要がある
* Bad: BM25 インデックスをベクトルDBとは別に保持することになり、
  更新時に両方を同期させる必要がある
* Bad: リランキングの分だけレスポンス時間が伸びる。
  非機能要件（10秒以内）への影響は未測定
* Bad: ハイブリッド検索は万能ではなく、1位の精度は上がるが
  上位3件の精度は下がる傾向があるという報告もある。
  評価で確認する必要がある
* Bad: **4問の差で方式を決めている。** 40問のうち R@10 が動いたのは4問
  だけで、残り36問は同じ結果である。母数が小さい
* Bad: **`k=10` 前提の結論である。** k=5 では vector が勝つ。生成に渡す
  件数を減らす判断とは両立しない
* Bad: RRF の `rrf_k=60` は Cormack ら（2009）の経験値をそのまま使っており、
  本プロジェクトで振っていない
* Bad: **BM25 側の重みを調整していない。** RRF は2つのリストを対等に扱うが、
  bm25 の R@10 が 0.4125（vector の半分強）であることから、対等でない方が
  良い可能性がある。脱落した2問はどちらも bm25 が 0.000 の問題だった
* Bad: **索引の構築時間を全件で測っていない。** 5万チャンクで4.6〜4.7秒
  という値しかなく、706,075チャンクでの値は未知である
* Bad: rrf は件数で切らないため、戻り値は最大 2k 件になる。
  find_rank と calculate_recall_at_k は [:k] で切るので検索の指標は
  壊れないが、build_context は切らない。生成に繋ぐときに
  GENERATION_K を超えた文脈が静かに渡る
* Bad: **ハイブリッドの R@k は k と N の2変数の関数である。**
  1回の測定で N の候補を比べられない。N ごとに測り直す必要があり、
  ADR-0037 の「最大kで1回検索しスライスする」が適用できない
* Bad: **N を増やすと上位が薄まる。** `R@1` が 0.3250 から 0.2875 に
  下がった。リランキングなしで N を増やす選択肢は無い
* Bad: **`ts029` でハイブリッドが両方の検索結果より悪い。** 2つの
  検索がどちらも100件以内に見つけているものを、統合が落としている。
  RRF の設計上の性質であり、重みや `rrf_k` の調整で変わる可能性がある
  が未検証
* Bad: **`rrf` の戻り件数を記録していない。** 「和集合で最大 2k 件」は
  構造からの推定であり、実測していない。`len(retrieved)` を記録すれば
  確かめられる
* Bad: **N=20 / 30 / 50 での測定がまだ無い。** 本ADRの計画（上位20件）を
  評価するには、その N で走らせた測定が必要である
