# ADR-0042: 検索評価のばらつきは近似探索では説明できない。原因未特定のまま幅で報告する

## Context and Problem Statement

**同一コード・同一シードで検索評価を繰り返したところ、Recall@10 が
実行ごとに変わった。**

| 実行 | 条件 | 圏外 | Recall@10 | 証跡 |
|---|---|---|---|---|
| 10/19 | 検索のみ | 15 | **0.633** | `retrieval_ruri310m_20261019.jsonl` |
| 10/20 | 検索のみ | 8 or 10 | 0.774 | `retrieval_20261020_run1.jsonl` |
| 10/20 | 検索のみ | 8 or 10 | 0.741 | `retrieval_20261020_run2.jsonl` |
| 10/20 | 生成（RAGあり）実行時 | 9 | 0.767 | `generation_rag_20261020.jsonl` |
| 10/29 | 項番号修正後 | 8 | 0.789 | `generation_rag_20261029.jsonl` |
| 10/29 | 枝番修正後 | 11 | 0.719 | `generation_rag_20261029b.jsonl` |
| 日付不明 | — | — | 0.752 | **証跡なし** |

10/29 の2回は生成プロンプト（`build_context`）の修正後だが、**検索側の設定は
変わっていない。** `src/config.py` の変更は出力先のみで、`src/ingestion`、
`src/embedding`、`src/store` は最初の測定以降一度も変更されていない
（`git log` で確認）。

```
同一設定の5回   0.719 / 0.741 / 0.767 / 0.774 / 0.789        幅 0.070
10/19 の1回     0.633                                        同一設定の幅の外
全体            0.633 〜 0.789                               幅 0.156
```

**当初この幅を「HNSW の近似最近傍探索によるばらつき」と結論した。
2026-10-30 の検証でこの結論が否定された。**

発覚の経緯は、生成の接続（RAGあり50問）を回したときである。事前に
「Recall@10 は 0.633 になる」と予想していたが実測は 0.767 だった。
予想の外れ方を調べた結果、予想が悪いのではなく、同じコードが
違う答えを返していることが判明した。

## Decision Drivers

* **比較実験の判断に使う数字である。** ばらつきより小さい差を
  「改善した」と報告すると、ポートフォリオの主張そのものが崩れる
* **残り日数が限られている。** 原因の特定に無制限に時間を使えない
* 原因不明のまま数字を出すのは避けたいが、原因不明であることを
  隠すのはもっと避けたい

## Considered Options

1. 原因を特定して固定する
2. **幅で報告し、原因は未特定と明記する**
3. 1回の実行結果だけを報告する

## Decision Outcome

Chosen option: **「幅で報告し、原因は未特定と明記する」**

対処（コーパスの永続化と構築時の検品）は ADR-0048 に分けた。
**このADRは「何が原因でないと分かったか」の記録である。**

---

## 原因は HNSW の近似探索ではない

10/29 と 10/29b の `retrieved_chunk_ids` を問題ごとに突き合わせた。

```
50問のうち 44問が、順序まで完全に一致
変わった6問は、共通するチャンクが 0/10
```

**近似最近傍探索のばらつきなら、結果は部分的に重なる。** 探索の経路が
少し違っても、近傍の大半は同じはずである。44問が完全一致で残り6問が
完全不一致という分布は、近似探索では説明できない。

さらに、変わった6問のうち2問で決定的な症状が出た。

### ts005 と ts024 が互いに完全同一の10件を返した

```
ts005   訪問販売で契約した場合、クーリング・オフは何日以内にできますか
ts024   要介護認定の有効期間は
```

**無関係な2問が、完全に同じ10件を返した。** 内容はどちらの質問とも
無関係な省令で、rank は両方 null。

これは「上位k件の選び方が少しずれた」という現象ではない。**検索が
クエリに反応していない。**

## 以前の記述の誤りを5点訂正した

### 1. 結論そのものが誤りだった

```
旧   同日のばらつきは HNSW の近似探索で説明がつく
新   44/50 の完全一致により否定された。原因は未特定
```

旧版は「45問のうち34問は毎回同じ結果で、11問だけが境界で前後する。
この観測は説明と整合する」と書いていた。**chunk_id を突き合わせる前の、
Recall の数字だけを見た推測だった。** 突き合わせたら分布が合わなかった。

### 2. 幅は「同日 0.033」ではなく「同一設定 0.070」

旧版は 10/20 の3回だけを見て幅 0.033 としていた。10/29 の2回を
加えると、同じ検索設定で 0.070 ある。

**これが運用上の閾値に直接響く**（後述）。

### 3. 測定は4回ではなく6回だった

旧版の表は4行で、生成実行時の 0.767 が落ちていた。0.767 は
「予想が外れた」ことに気づいた当の数字であり、これを落とした表は
経緯と合わない。10/29 の2回も追加した。

0.752 には証跡がない。出力先が固定名で、実行ごとに前回を上書きしていた。
**表から消さずに「証跡なし」と明記する。** 消すと、ばらつきの幅を
小さく見せる操作になる。

### 4. `num_threads` は「無言で捨てられた」のではない

旧版は「`configuration` 経由で `num_threads: 1` を渡したが、値は無言で
捨てられた。エラーも警告も出ない」と書いた。**これは設定できる場所を
間違えていた。**

Chroma の HNSW 設定の可変性:

```
作成時のみ設定可（作成後変更不可）   space / ef_construction / max_neighbors
作成後に変更可                      ef_search / num_threads / batch_size /
                                    sync_threshold / resize_factor
```

`num_threads` は**作成時には設定できない項目**だった。捨てられたのでは
なく、そこでは受け取らない。

**検証が不可能だったのではなく、検証の方法が間違っていた。**
`collection.modify()` 経由なら設定できたはずである。ただし原因が
HNSW でないと分かったため、この検証はもう必要ない。

### 5. 埋め込みの決定性検証が、本番のクエリ経路を通っていなかった

旧版は `embed_documents` で2回埋め込んで一致を確認し、「埋め込みは
完全に決定的」と結論した。

```python
embed_query(model, text)      → '検索クエリ: ' + text
embed_documents(model, texts) → '検索文書: ' + text
```

**プレフィックスが違う。** 検索で使うのは `embed_query` の経路である。
旧版の検証は文書側だけを見ていた。

2026-10-30 に `embed_query` でも検証した（後述）。結果は決定的だったため
結論は変わらない。**しかし「検証した」と書いていた範囲が実際より広かった。**

## 切り分けの記録

### 1. 埋め込みが非決定的ではないか → 否

プロセス内で2回埋め込んで `.tolist()` で全桁比較、プロセスを分けて
2回実行して `diff` にかけた。差分なし。

**`print(numpy_array)` は末尾を `...` で省略し値も丸めるため、
`.tolist()` で全桁を出す必要があった。**

### 2. コードが変わっていないか → 変わっていない

`git log` で `src/ingestion`、`src/embedding`、`src/store` が最初の測定以降
一度も変更されていないことを確認した。`src/config.py` の変更は出力先のみ。

### 3. HNSW の探索パラメータが小さすぎないか → 否

| 項目 | 値 |
|---|---|
| `space` | l2（`metadata` 経由の cosine 指定が拾われていなかった。ADR-0021） |
| `ef_construction` | 100 |
| `ef_search` | **100** |
| `max_neighbors` | 16 |
| `num_threads` | CPU数 |

`ef_search` は既に 100 だった。**ここで「既定値は 10 なので上げれば
安定する」と述べたが誤りだった。** 根拠にしていたのは Chroma 1.0 より前の
Cookbook の表で、1.5.9 の既定値は 100 である。公式ドキュメントで訂正した。

なお `space` が l2 だったことは**検索結果に影響しない。** 埋め込みが
正規化済みなので、L2 距離と cosine 距離は単調な関係にあり、上位k件の
順位が一致する（ADR-0021）。

### 4. マルチスレッドの非決定性ではないか → 検証方法が誤り（上記訂正4）

### 5. シードを指定できないか → 手段なし

Chroma 1.5.9 の HNSW 設定にシードの項目は文書化されていない。

### 6. ベクトルが数値として壊れていないか → 異常なし

`scripts/check_embedding.py` で、10/29b の結果に現れた疑わしい文書10件と、
評価50問のクエリすべてを調べた。

```
NaN を含む行          0 / 10（文書）、0 / 50（クエリ）
Inf を含む行          0
ノルムが 1.0±0.01 の外  0
ベクトルの完全一致      なし
```

**ゼロベクトルは NaN にならない。** sentence-transformers の正規化は
ゼロ除算を避ける eps を持つため、ゼロベクトルは「ノルム 0 のまま」通る。
NaN だけを見ると見逃すので、`np.abs(norms - 1.0) > 0.01` で両側を見た。

**この検査で異常が出なかったことが、原因の特定を難しくしている。**
調べたのは疑わしい10件だけで、5万件すべてではない。

### 7. chunk_id の突き合わせ → HNSW 仮説の否定（上記）

## 残っている仮説

```
H1  ベクトルの退化
    5万件のうち一部のベクトルが、クエリに関わらず近傍に出る状態になっている
    （representation collapse に近い現象）

H2  インデックスの局所的な破損
    ベクトルは正常だが、HNSW のグラフが一部壊れていて、
    どのクエリからも同じノード群に到達する
```

**`retrieved_distances` を記録すれば区別できる。** NaN なら H1、
正常値なのに的外れなら H2。10/29b では距離を記録していなかった。

ただし**区別できても対処は同じ**である（構築のやり直し）。そのため
原因の特定より回避を選んだ（ADR-0048）。

## 運用上の取り決め（改訂）

| 決めたこと | 理由 |
|---|---|
| 単一の値ではなく**幅で報告する** | 1回の実行値は再現できない |
| **0.05 の閾値を撤回する** | 同一設定の幅が 0.070 で、閾値を上回る |
| **コーパスを永続化して固定する** | 再構築の回数を構成の数まで減らす（ADR-0048） |
| 生成の比較では**検索結果を固定する** | `retrieved_chunk_ids` を記録済み |

### 0.05 の閾値を撤回した理由

旧版は「同一コーパス内では 0.05 未満の差を情報として扱わない」と決めた。
同日の幅 0.033 の約1.5倍という根拠だった。

**同一設定の幅が 0.070 と判明したため、この閾値は機能しない。**

```
ばらつき 0.070  >  閾値 0.05
→ ばらつきの範囲内の差を「有意」と判定してしまう
```

さらに深刻なのは、ばらつきが期待される効果より大きいことである。

```
一般に報告されるチャンク設定の変更の効果   0.02 〜 0.05
ばらつき                                   0.070
→ 効果がばらつきに埋もれる
```

旧版はこれを「幅 0.141 は埋め込みモデルの比較で期待される差と同じ桁」と
書いていたが、これも誤りだった。**「同じ桁だから区別できない」ではなく、
「ばらつきが効果より大きいので、効果が埋もれる」**が正しい。

### 3回ずつ回す案も成立しない

旧版は「各構成を3回ずつ回して幅を出し、幅が重ならない場合にのみ差を
主張する」と決めた。幅 0.070 では、**どの構成も幅が重なる**ため、
「有意差なし」しか出せない。

**コーパスを固定して再構築の回数を減らすのが、実際に取れる唯一の手である**
（ADR-0048）。

### 10/19 の 0.633 は未解決である

同一設定の幅（0.070）では説明できない。**5問が圏外（recall 0.0）から
1位（recall 1.0）に飛んでいる。**

```
候補1  コーパスのサブセット（対象法令・対象版）が違った
候補2  チャンク設定（閾値・オーバーラップ）が違った
候補3  必須法令がサブセットに入っていなかった
```

**候補3が最も動き方と合う。** `create_sub_chunks` が必須法令を入れ損ねると、
その法令の問題がまとまって圏外になり、次の実行で入れば一斉に1位に戻る。
エラーは出ない。

原因を追うことはしなかった。ADR-0048 の検品（検査3）が、同じ型の失敗を
今後は検出する。

## Consequences

* Good: **自分の結論を実測で否定して書き直した。** 「HNSW の近似探索」は
  もっともらしい説明だったが、chunk_id を突き合わせたら分布が合わなかった。
  Recall の数字だけを見た推測と、中身を突き合わせた検証の差が記録に残る
* Good: **原因の切り分け過程が7点残る。** 埋め込みの決定性、コードの
  不変性、探索幅、スレッド数、シード、ベクトルの数値検査、chunk_id の
  突き合わせ。「分からない」ではなく「ここまで分かって、ここが残っている」と
  言える
* Good: **以前の記述の誤りを5点訂正した。** 結論、幅、測定回数、
  `num_threads` の扱い、埋め込み検証の範囲。特に「検証した」と書いた範囲が
  実際より広かった点（`embed_documents` のみ）は、検証の記録として重要
* Good: `ef_search` の既定値について誤った前提を指摘し、公式ドキュメントで
  訂正した。**ツールのバージョン差による古い情報を鵜呑みにしなかった**
* Good: **比較実験の設計が変わった。** 0.05 の閾値と3回反復の両方が
  成立しないと分かり、コーパスの永続化という別の手段に移った（ADR-0048）
* Bad: **原因が未特定である。** H1（ベクトルの退化）と H2（インデックスの
  局所的破損）の区別をしていない。`retrieved_distances` を記録すれば
  区別できるが、区別しても対処が同じなので追っていない
* Bad: **ベクトルの検査が5万件全部ではない。** 疑わしい10件とクエリ50問
  だけを見た。H1 を否定したとは言えない
* Bad: **10/19 の 0.633 の原因が未特定である。** 候補3（必須法令の欠落）が
  最も有力だが、確認していない
* Bad: **0.752 の1回は証跡が残っていない。** 出力先が `EVAL_RESULT_FILE` の
  固定名で、実行ごとに前回を上書きしていた。**この構造は未修正である**
  （`evaluate_retrieval.py` が固定名を `'w'` で開いている）。比較実験で
  同じことが起きる
* Bad: **変わった6問の特徴を分析していない。** スコアが近接しているのか、
  特定の法令に偏っているのか。調べれば H1 と H2 の区別に近づけた可能性がある
* Bad: **この Recall 自体が過大評価を含んでいる**（ADR-0047）。0.070 も
  0.156 も、条レベルの Recall の上で測った幅である。粒度を直した後、
  幅が変わる可能性がある
