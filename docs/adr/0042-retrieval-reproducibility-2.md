# ADR-0042: 検索評価のばらつきは原因を特定せず、幅で報告する

## Context and Problem Statement

同一コード・同一シードで検索評価を繰り返したところ、Recall@10 が
実行ごとに変わった。

| 実行 | Recall@10 | 証跡 |
|---|---|---|
| 10/19 07:03 | 0.633 | retrieval_ruri310m_20261019.jsonl |
| 10/20 08:23 | 0.774 | retrieval_20261020_run1.jsonl |
| 10/20（時刻不明） | 0.752 | **ファイルなし。ターミナル出力のみ** |
| 10/20 17:16 | 0.741 | retrieval_20261020_run2.jsonl |
| 10/20 19:45 | 0.767 | generation_rag_20261020.jsonl |

5回目は生成評価の副産物だが、同じ45問・同じ k=10 で計算しているため
同じ量の測定として扱う。

幅は2段階に分かれる。

  同日（10/20）の4回   0.741 〜 0.774   幅 0.033
  10/19 を含める        0.633 〜 0.774   幅 0.141

比較したい差はこれより小さい。ADR-0041 で参照した他者の比較では
ruri-v3-310m と bge-m3 の差は P@1 で 0.014、MRR で 0.016 だった。
つまり埋め込みモデルを変えても、その効果はばらつきに埋もれる。

45問のうち34問は毎回同じ結果で、11問（ts005, ts010, ts013, ts023,
ts024, ts026, ts034, ts035, ts046, ts047, ts049）が実行ごとに前後する。
ただしこの11問は性質が異なる2群に分かれる（後述）。

発覚の経緯は、生成の接続（RAGあり50問）を回したときである。10/19 の
実測値から「Recall@10 は 0.633 になる」と見込んでいたが実測は 0.767
だった。外れ方を調べた結果、予想が悪いのではなく、同じコードが違う
答えを返していることが判明した。

## Decision Drivers

* **比較実験の判断に使う数字である。** ばらつきより小さい差を
  「改善した」と報告すると、ポートフォリオの主張そのものが崩れる
* 原因の特定に時間を使えない
* 原因不明のまま数字を出すのは避けたいが、原因不明であることを
  隠すのはもっと避けたい

## Considered Options

1. **原因を特定して固定する**
2. **幅で報告し、意味のある差の閾値を決める**
3. 1回の実行結果だけを報告する

## Decision Outcome

Chosen option: **「幅で報告し、意味のある差の閾値を決める」**

### 前段から順に切り分けた

原因を特定しなかったのは、調べなかったからではない。**前段から
順に潰して、残った場所が特定できなかった。**

**1. 埋め込みが非決定的ではないか**

`scripts/check_embedding.py` を書いて確認した。

```python
document1 = embed_documents(model, ['日本の首都は東京です'])
document2 = embed_documents(model, ['日本の首都は東京です'])
print(document1.tolist())
print(document2.tolist())
```

プロセス内で一致。プロセスを分けて2回実行し、出力を `diff` にかけても
差分は出なかった。**`print(numpy_array)` は末尾を `...` で省略し値も
丸めるため、`.tolist()` で全桁を出す必要があった。**

→ 埋め込みは完全に決定的。原因ではない。

**2. コードが変わっていないか**

`git log` で `src/ingestion`、`src/embedding`、`src/store` の3つが
最初の測定以降一度も変更されていないことを確認した。

→ 前段の処理は同一。原因ではない。

**3. HNSW の探索パラメータが小さすぎないか**

`scripts/check_db.py` で `collection.configuration` を出力した。

| 項目 | 値 |
|---|---|
| `space` | l2（`metadata` 経由で cosine を指定） |
| `ef_construction` | 100 |
| `ef_search` | **100** |
| `max_neighbors` | 16 |
| `num_threads` | CPU数 |
| `sync_threshold` | 1000 |
| `resize_factor` | 1.2 |

`ef_search` は既に 100 だった。**ここで調査者（Claude）が
「既定値は 10 なので上げれば安定する」と述べたが、これは誤りだった。**
根拠にしていたのは Chroma 1.0 より前の Cookbook の表で、
1.5.9 の既定値は 100 である。公式ドキュメントを確認して訂正した。

→ 探索幅は既に広い。原因ではない。

**4. マルチスレッドの非決定性ではないか**

`num_threads` が CPU 数になっているため、並列実行の順序が
結果に影響する可能性がある。`configuration` 経由で `num_threads: 1`
を渡して試した。

**値は無言で捨てられた。** エラーも警告も出ず、
`collection.configuration` にも現れない。

→ 検証できなかった。**仮説は残っているが未確認である。**

**5. シードを指定できないか**

Chroma 1.5.9 の HNSW 設定にシードの項目は文書化されていない。

→ 手段が無い。

### 残ったのは HNSW の近傍探索である

埋め込みが決定的で、前段のコードが同一で、設定も変えていないのに
結果が変わる。**残るのはベクトルストアの中の探索処理である。**

HNSW は近似最近傍探索であり、厳密な上位k件を返す保証がない。
グラフの構築順やスレッドの実行順で、同じクエリに対して違う近傍を
返しうる。34/45 が安定し、境界にある11問だけが動くという観測は
この説明と整合する。

**ただし「HNSW が原因である」ことを直接実証していない。**
`num_threads: 1` が通らなかったため、マルチスレッドを除いた状態での
再現性を確認できていない。

### 運用上の取り決め

| 決めたこと | 理由 |
|---|---|
| 単一の値ではなく**幅で報告する** | 1回の実行値は再現できない |
| **0.05 未満の差は情報として扱わない** | 実測の幅 0.141 の約3分の1。これ以下の差はばらつきと区別できない |
| 生成の比較では**検索結果を固定する** | `retrieved_chunk_ids` を記録済み。再利用すれば検索の分散を除去できる |

3つ目が重要である。**生成の良し悪しを比べたいときに検索が毎回
変わっていると、何を測っているのか分からなくなる。** 記録した
chunk_id を再投入すれば、生成だけを比較できる。

## Consequences

* Good: **原因の切り分け過程が残る。** 埋め込みの決定性、コードの
  不変性、探索幅、スレッド数、シードの5点を順に潰した記録がある。
  「分からない」ではなく「ここまで分かって、ここが残っている」と言える
* Good: ばらつきより小さい差を改善として報告しない方針が明文化された。
  **以後の比較実験で、誤った結論を出すリスクが下がる**
* Good: `ef_search` の既定値について誤った前提を指摘し、公式
  ドキュメントで訂正した。**ツールのバージョン差による古い情報を
  鵜呑みにしなかった**
* Good: 生成の比較で検索を固定する手段（`retrieved_chunk_ids`）を
  先に用意した。ADR-0044 の比較はこの上に乗る
* Bad: **原因を特定していない。** HNSW の探索が原因という仮説は
  残っているが、`num_threads: 1` が通らなかったため実証できていない。
  Chroma のクライアント初期化側に別の経路があるか未調査
* Bad: **4回の実行のうち2回分しか証跡が残っていない。** 出力先が
  `EVAL_RESULT_FILE` の固定名で、実行ごとに前回を上書きしていた。
  再現できない結果を固定名で書く構造になっていたのが設計の穴である。
  残った2回分を `retrieval_20261020_run1/run2.jsonl` に改名して保存した
* Bad: 11問がどういう問題なのかを分析していない。**境界にある問題の
  特徴（スコアが近接している、goldが複数ある等）を調べれば、
  ばらつきの大きさを事前に見積もれた可能性がある**
* Bad: 0.05 という閾値は実測の幅から逆算した経験値で、統計的な
  根拠がない。実行回数を増やして分布を見ていない（1回8分かかるため）
