# ADR-0039: コレクション名を構成から組み立てる

> **本ADRは proposed である。** PersistentClient へ移行する時点で必要になる
> 決定を、先に記録している。現時点では in-memory の `Client()` を使って
> いるため問題が顕在化しておらず、実装も未着手である。移行時に Decision
> Outcome を確定させ、accepted に更新する。

## Context and Problem Statement

Chroma のコレクション名が固定値になっている。

```python
# config.py
COLLECTION_NAME = 'my_collection'
```

現在は in-memory の `Client()` を使っているため（ADR-0024）、プロセスごとに
コレクションが空から作られる。**同じ名前でも衝突しない。**

問題は `PersistentClient` へ移行した時点で現れる。比較実験では閾値を
4通り（200 / 500 / 1,000 / 2,000）振るため、**内容の異なるコレクションを
4つ作る**ことになる。

```
閾値1000でサブセットを投入 → 'my_collection' に保存される
閾値500に変えて実行        → create_collection が「既に存在する」で落ちる
```

ここで落ちるだけなら気づける。問題はその直し方である。

```
get_or_create_collection に差し替える
  → 閾値1000のチャンクが入ったコレクションを、閾値500の実験で使ってしまう
```

**エラーを直した結果、静かに間違ったデータで測る**という経路ができる。
`collection.count()` は50,055件を返すので、件数を見ても気づけない。

これは ADR-0032 / ADR-0033 と同じ系統である。あちらは「変えていない部分が
変わらないこと」の保証だったが、本件は裏返しの「**変えたはずの部分が
変わっていないこと**」を検出できない問題である。

## Decision Drivers

* 比較実験の前提として、構成とコレクションが1対1で対応していること
* 誤りがエラーとして現れるか、少なくとも名前で目視できること
* 全件投入（約1時間55分）をやり直す事態を避けること

## Considered Options

1. 固定名のまま、実験ごとに手でコレクションを削除する
2. コレクション名を構成から組み立てる
3. 実験ごとに `PersistentClient` の保存先ディレクトリを分ける

## Proposed Decision Outcome

Proposed option: **「コレクション名を構成から組み立てる」**

```
chunks_th{閾値}_{モデル}_seed{seed}_n{目標件数}_ref{基準日}
```

名前が違えば混ざらない。`create_collection` を使い続けられるため、
同じ名前で2回作ろうとしたときは落ちる。

選択肢1は、削除を忘れた1回で実験が汚染される。しかも汚染されたことが
数値から判別できない。

選択肢3はディレクトリが増えるだけで、ディレクトリ名に構成を含めないと
同じ問題が残る。名前で区別するなら、コレクション名で区別するのと同じこと。

## 未解決の論点

本ADRを proposed のままにしている理由である。

### 名前に何を含めるか

コレクションの内容を決めている設定を列挙すると、以下が候補になる。

| 設定 | 内容を変えるか |
|---|---|
| `CHUNK_THRESHOLD` | **変える**（チャンクの切り方） |
| `EMBEDDING_MODEL` | **変える**（ベクトルの値） |
| `DISTANCE_SPACE` | **変える**（HNSW の構築） |
| `SUBSET_SEED` | **変える**（どの法令が入るか） |
| `SUBSET_TARGET_CHUNKS` | **変える**（何件入るか） |
| `REFERENCE_DATE` | **変える**（どの版を現行版とするか、ADR-0040） |
| `MIN_RATIO` | 変える（句点分割の探索範囲） |

**全部を名前に入れると長くなりすぎる。** Chroma のコレクション名には
長さと使える文字の制約があり、未確認である。

### 評価データへの依存を名前で表せない

サブセットの構成は**評価データの gold に依存する**（ADR-0033 の要件1、
ADR-0036）。gold の法令が1件から6件に増えた結果、同じ seed・同じ目標件数
でもサブセットの中身が変わった実例がある。

つまり `eval_set.jsonl` の内容もコレクションの内容を決めているが、
**ファイルの内容を名前に含める方法が自明でない。** 候補は2つある。

* 内容のハッシュを名前に含める（短縮すると衝突の可能性、長いと読めない）
* 名前には含めず、別途メタデータとして記録する

### 名前が読めなくなる問題

設定を全部詰めると、人が見て区別できない名前になる。

```
chunks_th1000_cl-nagoya-ruri-v3-310m_cosine_seed42_n50000_ref20261013_eval8f3a1c
```

**代替案として、名前は短くし、構成を別ファイルに記録する**形も考えられる。

```
コレクション名: exp001
experiments.jsonl に exp001 の全設定を1行で記録
```

この場合、名前の衝突は防げるが「`exp001` が何の構成か」を名前からは
読めない。対応表を見る運用になる。どちらが良いかは、実験を何通り回すかで
変わる。4通りなら名前に詰める方が早く、20通りなら対応表の方が整理できる。

## Consequences（想定）

* Good: 構成とコレクションが1対1になり、取り違えがエラーとして現れる
* Good: 複数の構成を同時に保持できるため、再投入なしで測り直せる
* Good: 全件投入をやり直す事態を防げる
* Bad: 設定を1つ増やすたびに、名前に含めるかの判断が増える
* Bad: 評価データへの依存を名前で表す方法が未定。gold が変わったのに
  同じ名前のコレクションを使う経路が残りうる
* Bad: 名前が長くなると人が区別できない。短くすると構成が読めない
* Bad: 本ADRは proposed であり、**PersistentClient への移行自体が
  まだ決まっていない。** 残り日数によっては in-memory のまま
  比較実験を回す判断もありうる。その場合、本決定は不要になる
