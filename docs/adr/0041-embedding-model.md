# ADR-0041: 埋め込みモデルは日本語特化の ruri-v3-310m を使う

## Context and Problem Statement

`config.py` に埋め込みモデルが定数として書かれているだけで、**なぜそれを
選んだかの記録が無い。**

```python
EMBEDDING_MODEL = 'cl-nagoya/ruri-v3-310m'
```

ADR-0021（類似度関数）、ADR-0023（ローカルLLM）、ADR-0024（ベクトルストア）
はあるが、埋め込みモデルの選定が抜けていた。

発覚の経緯は、比較実験の候補を検討していたときである。「別のモデルと比べて
みよう」という話になった時点で、**比べる相手を決める基準が無い**ことに
気づいた。基準が無いのは、最初の選定の基準も記録していなかったからである。

本ADRは事後の記録である。選定自体は実装時に行われており、**本ADRを書く
過程で初めて、その選定が妥当だったかを外部ベンチマークで確認した。**

## Decision Drivers

* **検索対象が日本語の法令文である。** 多言語モデルより日本語特化モデルの
  方が有利でありうる
* **ローカルで実行する（ADR-0023）。** 生成用のLLMと同じメモリに同居する
* **50,055チャンク（サブセット）、将来は706,129チャンク（全件）を投入する。**
  モデルが大きいほど投入時間が伸びる
* 商用利用可能なライセンスであること

## Considered Options

1. **cl-nagoya/ruri-v3-310m**（日本語特化、315M、768次元）
2. BAAI/bge-m3（多言語、1024次元）
3. Qwen/Qwen3-Embedding-0.6B（多言語、2025年）
4. nvidia/Nemotron-3-Embed-8B-BF16（RTEB 1位、8B、4096次元）
5. text-embedding-3-large（OpenAI、API）

## Decision Outcome

Chosen option: **「cl-nagoya/ruri-v3-310m」**

### JMTEB の検索タスクで1位である

JMTEB（日本語の埋め込みベンチマーク）の**検索タスク単独**のスコア。

| モデル | パラメータ | 次元 | JMTEB 検索 |
|---|---|---|---|
| **ruri-v3-310m** | 315M | 768 | **81.89** |
| ruri-v3-130m | 132M | 512 | 81.89 |
| PLaMo-Embedding-1B | 1.05B | 2048 | 79.94 |
| text-embedding-3-large | 非公開 | 3072 | 74.48 |
| Qwen3-Embedding-0.6B | 0.6B | 1024 | 72.81 |
| multilingual-e5-large | 560M | 1024 | 70.98 |

**1B クラスの PLaMo より上、OpenAI の text-embedding-3-large より7ポイント
上である。** パラメータ数が3分の1以下でこの順位になるのは、日本語特化の
学習によるものと考えられる。

Qwen3-Embedding-0.6B との差は9ポイントあり、「新しいモデルの方が良い」とは
言えない。**ベンチマークの対象言語が性能を決めている。**

### 他者による日本語RAGの比較でも ruri が bge-m3 に勝っている

日本語文書・2000問での比較（Precision と MRR）。

| 構成 | P@1 | MRR |
|---|---|---|
| ruri-v3-310m（dense のみ） | **0.555** | **0.694** |
| bge-m3（dense のみ） | 0.541 | 0.678 |

差は小さいが方向は一致している。この記事の著者も「ローカル運用なら
ruri-v3-310m が最もコスト効率が良い」と結論している。

**ただしこの比較は Precision を報告しており、4言語のクエリを平均している。**
本プロジェクトの Recall@k（ADR-0037）とは直接比較できない。方向の参考と
してのみ扱う。

### Nemotron-3-Embed-8B は環境の制約で却下した

RTEB（検索ベンチマーク）で1位のオープンウェイトモデルを検討した。
モデルカードの記述が決定的だった。

> Hardware: Ampere, Blackwell, Hopper GPUs. Tested on A100 80GB and H100 80GB.
> It requires a **CUDA-enabled PyTorch** install and Transformers 5.2.0 or later.
> Examples use FlashAttention-2 by default.

**本プロジェクトの実行環境は Apple Silicon（MPS）であり、CUDA が無い。**
FlashAttention-2 も MPS には存在しない。

```python
# src/embedding/embedding.py
def select_device() -> str:
    return 'mps' if torch.backends.mps.is_available() else 'cpu'
```

仮に CPU で動いたとしても、規模が合わない。

| | 重み（BF16） | ベクトル（50,055件） |
|---|---|---|
| ruri-v3-310m（768次元） | 約0.6GB | 約615MB |
| Nemotron-3-Embed-8B（4096次元） | **約16GB** | **約3.3GB** |

ADR-0023 で生成用のLLMをローカルに置くと決めているため、**埋め込みモデルが
16GB を占めると生成側が動かない。**

なお Nemotron が1位なのは RTEB であり、日本語は評価対象34言語のうちの1つ
である。日本語特化モデルではない。

### ベンチマークの順位ではなく、条件を満たすものを選んだ

「MTEB 1位」「RTEB 1位」は選定基準にならなかった。本プロジェクトの条件は
次の3つで、順位はそのいずれにも対応していない。

```
検索対象が日本語          → 見るべきは JMTEB の検索タスク
ローカルで生成LLMと同居    → 8B クラスは入らない
70万チャンクを投入する     → 大きいモデルは時間が合わない
```

**1位のモデルを検討した上で、制約を理由に却下した**という記録を残す。

### プレフィックスを実装に反映している

ruri-v3 は入力の種類ごとにプレフィックスを付ける前提で学習されている
（1+3 prefix scheme）。

| プレフィックス | 用途 |
|---|---|
| `""`（空） | 意味の符号化 |
| `トピック: ` | 分類・クラスタリング |
| `検索クエリ: ` | **検索のクエリ側** |
| `検索文書: ` | **検索の文書側** |

実装はこれに従っている。

```python
def embed_documents(model, texts):
    prefixed = ['検索文書: ' + text for text in texts]
    return model.encode(prefixed, normalize_embeddings=True)

def embed_query(model, text):
    return model.encode('検索クエリ: ' + text, normalize_embeddings=True)
```

**クエリと文書を非対称に扱うモデルを、非対称に使っている。** `normalize`
を有効にしているのは cosine 空間（ADR-0021）との整合のため。

## Consequences

* Good: 日本語の検索という条件で、JMTEB 検索タスク1位のモデルを使っている。
  選定理由をベンチマークの数字で言える
* Good: パラメータ315M・768次元に収まっているため、生成用LLMとの同居が
  成立する（ADR-0023）。50,055チャンクの投入が約8分で済む
* Good: RTEB 1位のモデルを検討し、CUDA 必須・8B・4096次元という条件が
  ローカル実行と両立しないことを確認した上で却下した記録が残る。
  **ベンチマークの順位をそのまま採用しなかった判断が説明できる**
* Good: プレフィックス方式をモデルカードに従って実装している。
  非対称な学習をしたモデルを対称に使う誤りを避けている
* Bad: **自分の評価データで測っていない。** 外部ベンチマーク（JMTEB）と
  他者の比較記事に依拠している。bge-m3 との比較は実施可能だが、残り日数の
  都合で生成の接続を優先した。実施すれば本ADRに実測値を追記できる
* Bad: **ruri-v3-130m が検索タスクで同じ 81.89 である。** パラメータ132M・
  512次元で、310m の半分以下のサイズ。同スコアなら小さい方が合理的だが、
  **比較していない。** 310m を選んだ理由は「ファミリ内で上位」であり、
  検索タスク単独では根拠が無い
* Bad: プレフィックスが `embedding.py` にハードコードされている。別ファミリ
  のモデル（bge-m3 はプレフィックス不要、Qwen3 は指示文形式）に差し替えると、
  **誤った使い方のまま動く。** エラーにならないため気づけない。比較実験を
  行う場合はモデルごとに切り替える仕組みが必要になる
* Bad: 本ADRは事後の記録である。選定時点では記録しておらず、比較実験の
  候補を検討する段階で欠落に気づいた。**「選んだときに書く」が守れていない**
