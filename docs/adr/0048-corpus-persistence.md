# ADR-0048: 評価コーパスを永続化し、構築時に設定非依存の検品を行う

## Context and Problem Statement

**インデックスの構築経路が2つあり、それぞれ別のコーパスを作っていた。**

```
build_index.py            チャンクの先頭N件を投入
evaluate_generation.py    必須法令を含む5万件のサブセットを投入
```

どちらも `chromadb.Client()`（インメモリ）で、**プロセスが終われば消える。**
評価を回すたびに構築し直していた。

この構造の上で、原因未特定の異常が2件出ている。

### 異常1: 同一設定で Recall が 0.070 動く

```
0.719 / 0.741 / 0.767 / 0.774 / 0.789
```

ADR-0042 では「HNSW の近似最近傍探索によるばらつき」と結論したが、
10/29 と 10/29b を chunk_id で突き合わせた結果、**この説明が否定された。**

```
50問のうち 44問が、順序まで完全に一致
変わった6問は、共通するチャンクが 0/10
```

近似探索のばらつきなら部分的に重なる。**44問完全一致・6問完全不一致という
分布は、近似探索では説明できない。**

### 異常2: 無関係な2問が完全に同じ10件を返した

10/29b の実行で、ts005（訪問販売のクーリング・オフの日数）と ts024（要介護認定の
有効期間）が、**完全に同じ10件**を返した。内容は質問と無関係な省令で、
どちらも rank は null。

`scripts/check_embedding.py` で疑わしい文書10件とクエリ50問を調べたが、
NaN・Inf・ノルム異常・ベクトルの完全一致はいずれも出なかった。**原因は未特定。**

### これが比較実験の前提を壊す

これから行う比較実験のうち、半分はコーパスを作り直す。

```
再構築なし   BM25+RRF、リランカー
再構築あり   チャンク閾値、オーバーラップ、号チャンクへの柱書前置
```

**毎回構築し直す構造のまま構成間の差を報告すると、「それは構成の差ではなく、
構築のばらつきではないのか」に答えられない。**

## Decision Drivers

* **比較実験の判断に使う。** コーパスが実行ごとに動くと、差の帰属が決まらない
* **原因未特定の異常が2件ある。** 原因を特定できないなら、せめて再発を
  検出できる必要がある
* **検品は構成を変えるたびに走る。** 設定が変われば値が変わる指標は、
  検品の合否に使えない
* 残り日数が限られている。原因の特定に無制限に時間を使えない

## Considered Options

1. **永続化し、構築時に設定非依存の検品を行う**
2. 原因を特定してから比較実験に進む
3. インメモリのまま、構成ごとに3回ずつ回して幅で判断する

## Decision Outcome

Chosen option: **「永続化し、構築時に設定非依存の検品を行う」**

原因の特定ではなく**回避**である。これを隠さずに記録する。

### 原因の特定を待たなかった理由

候補は2つに絞れている。

```
H1  ベクトルの退化（representation collapse に近い現象）
H2  インデックスの局所的な破損
```

`retrieved_distances` を記録すれば区別できる（NaN なら H1、正常値なのに
的外れなら H2）が、**区別できたとしても対処は同じ**である。どちらも
「構築をやり直す」以外の手段がない。

永続化すると構築の回数が構成の数まで減るので、**発生の機会そのものが減る。**
残り日数を考えると、特定より回避の費用対効果が高い。

### 3回ずつ回す案を採らなかった理由

ADR-0042 の時点ではこの案を採る前提だった。しかし同一設定の幅が 0.070 と判明し、
**閾値の変更で期待される効果（一般に 0.02〜0.05）より大きい。**

```
ばらつき 0.070 > 期待される効果 0.02〜0.05
→ 3回の幅を取っても、幅が重ならない構成がほとんど出ない
→ 「どの構成も有意差なし」という結論しか出せない
```

幅で報告する方針は残すが、**それだけでは比較が成立しない。**

---

### 決定1: コレクション名を設定から導出する

```python
name = f'{model}_{chunk_threshold}_{reference_date}_{chunk_count}'
# 例: ruri-v3-310m_1000_20261013_50055
```

`COLLECTION_NAME` の固定名（`my_collection`）を削除した。

**名前が中身を識別するので、「名前は同じだが中身が違う」という状態が作れない。**

```
閾値を 600 に変える  → 名前が ..._600_... になる
基準日を変える       → 名前が変わる
件数が1件変わる      → 名前が変わる
```

当初は「コレクションのメタデータと設定を照合する」仕組みを足す設計だった。
**名前が4つの値から導出されるので、照合は冗長だと分かり削った。**

### 決定2: 構築経路を1本にする

```python
def build_index(client, model, chunks):
    ...
```

**どのクライアントを使うか、どのモデルを使うか、どのチャンクを入れるかは
呼び出し側が決める。** 永続化するかどうかも `--save` で呼び出し側が決める。

評価用のサブセット構築は `evaluation/build_eval_index.py` に置いた。

```
依存の向き   評価 → 製品   （許される）
             製品 → 評価   （許されない。ADR-0038）
```

サブセットの構築は評価の関心事である。`build_index.py`（製品側）が
`evaluation/` を import する形は避けた。

### 決定3: 検品は設定に依存しない3性質だけを見る

**これがこのADRの核である。**

当初の設計は「CHECK_IDS の3問が1位で引けること」を検品の合否にしていた。
これは機能しない。

```
チャンク閾値を 600 に変える
  → チャンクの切り方が変わる
  → gold の条のチャンクが変わる
  → 上位10件が変わる
  → ts005 が1位でなくなる

「構築が壊れた」のか「設定を変えたから」のか区別できない
```

**比較実験で閾値を振るのに、閾値に依存する検品を置くと、構成を変えた瞬間に
意味を失う。** 検品が確かめるべきは「ビルドが壊れていないか」で、
「検索が良いか」ではない。

採用した3つ:

| 検査 | 見るもの | 何の破損を示すか |
|---|---|---|
| 1 | `distance` に NaN がないか | ベクトルの破損 |
| 2 | 異なる質問が同じ結果を返していないか | インデックスの破損 |
| 3 | 必須法令のチャンクが存在するか | サブセット構築の失敗 |

いずれも**閾値やモデルを変えても成り立つべき性質**である。

順位と Recall は表示もしない。それは `evaluate_retrieval.py` の仕事である。

#### 検査2を集合で比べる理由

10件だけのコレクションで3問を引いたとき、距離が全部違った。

```
ts005   0.2263, 0.2427, 0.2437, ...
ts009   0.2279, 0.2334, 0.2338, ...
ts024   0.2212, 0.2242, 0.2251, ...
```

**同じ10件が、違う順序で返っていた。** リストで比べると見逃す。

```
[A, B, C] == [B, A, C]   False  → 見逃す
{A, B, C} == {B, A, C}   True   → 検出する
```

壊れ方の仕組みとしても、集合が一致して順序が違う状態が自然に起きる。

```
インデックスが壊れて、どのクエリでも同じ近傍しか候補に出ない
  → 候補の10件は同じ
  → 距離はクエリごとに計算される（クエリのベクトルは壊れていない）
  → 順序はクエリごとに違う
```

50問すべてで比べる（1225組）。3問だけだと 3/1225 しか見ないため、
10/29b の ts005・ts024 の組にたまたま当たっただけになる。

#### 検査3が未解決の謎の候補である

`create_sub_chunks` は 706,075 チャンクから5万件を選び、必須法令を必ず混ぜる。
**ここが失敗してもエラーは出ない。** 5万件が返り、構築も検索も正常に動き、
数字だけが静かに下がる。

```
10/19  Recall 0.633  圏外 15問
10/20  Recall 0.774  圏外  8問   → 5問が圏外から1位に飛んだ
```

ADR-0042 で「近似探索では説明できない、コーパスか設定の違い」と結論した
この動き方は、**「その法令がサブセットに入っていなかった」で説明がつく。**

検査3は3行でこの型を検出する。

### 決定4: 検品は独立したスクリプトにする

`evaluation/check_collection.py` にコレクション名を引数で渡す形にした。

```
python3 -m evaluation.check_collection ruri-v3-310m_1000_20261013_50055
```

**構築し直さずに検査だけを数秒で回せる。** これは永続化の副産物である。
永続化する前はできなかった。

```
構築（5万件の埋め込み）   十数分
検査                      数秒
```

`build_eval_index.py` に埋め込むと、検品のコードを直すたびに構築が走る。

### 検品そのものを検証した

**異常が起きなければ何も出ない検査は、通ったのか走っていないのか区別できない。**

`build_index.py --limit 10 --save` で10件のコレクションを作ると、
**3つの検査が全部異常を報告する状態**になる。

```
検査1   10件の距離が正常値 → 検出されないのが正しい
検査2   候補が10件しかない → どの質問も同じ10件を返す → 1225組すべて検出
検査3   先頭10チャンクに必須法令は無い → 6法令すべて検出
```

わざと壊す必要がない。**小さなコレクションが、そのまま検証用の固定具になる。**
実際にこの状態で3つとも動作を確認した。

## Consequences

* Good: **比較実験でコーパスが固定される。** 再構築なしの構成（BM25+RRF、
  リランカー）は同じコレクションに対して回せる
* Good: **原因未特定の2件の症状を検出できるようになった。** 原因は分からないが、
  再発したときに「構成の差」と誤解することはなくなる
* Good: **検品が構成を変えても使える。** 設定依存の指標（順位）を合否に
  使わないという切り分けが、比較実験の前提を守る
* Good: **検査だけを数秒で回せる。** 永続化の副産物。検品のコードを直すのに
  構築が不要になった
* Good: **名前が中身を識別する。** 設定が違えば名前が違うので、コレクションを
  取り違える状態が作れない。照合の仕組みが不要になった
* Good: **検品自体を検証できた。** 10件のコレクションが全検査を発火させる
  固定具になる。「検査が通った」と「検査が走っていない」を区別した
* Good: **構築経路が1本になった。** 先頭N件とサブセットという別のコーパスで
  測っていた状態が解消された
* Bad: **原因は未特定のままである。** これは回避であって解決ではない。
  H1（ベクトルの退化）と H2（インデックスの破損）の区別をしていない
* Bad: **検品が独立しているので、走らせ忘れる余地がある。** 構築の最後に
  コレクション名を表示して次のコマンドを示しているだけで、強制していない
* Bad: **検査2の校正が未了である。** 正常なコレクションでも「同じ10件を返す組」
  が出る可能性がある（同じ条文について聞いている質問が2つあれば一致しうる）。
  初回の実行結果を校正に使う必要がある
* Bad: **検査1（NaN）が効く見込みは低い。** `check_embedding.py` で異常が
  出ていない。ゼロベクトルは NaN にならないため、数値として壊れた場合しか
  拾わない。10/29b の症状は距離が正常値のままだった
* Bad: **同じ設定で作り直せない。** `create_collection` が名前の衝突で失敗する。
  作り直すには `delete_collection` が必要。安全側の挙動だが、手順が増える
* Bad: **件数が名前に入っているため、サブセットが1件変わると別の名前になる。**
  同じ設定のつもりでも名前が変わる場合がある
* Bad: **永続化したコレクションは `.gitignore` である。** 他の環境で再現するには
  再構築が必要で、そのとき同じコーパスになる保証はシード値だけに依存している
* Bad: **ADR-0042 が名指しした `EVAL_RESULT_FILE` の上書き問題に手をつけていない。**
  `evaluate_retrieval.py` が固定名を `'w'` で開いており、比較実験で証跡が消える
* Bad: **`embedding_function` が自動で `DefaultEmbeddingFunction` に割り当てられる。**
  `embeddings=` を省略すると別のモデルで埋め込まれる。現在は必ず渡しているが、
  無言の罠が残っている
