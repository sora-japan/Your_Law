# ADR-0049: BM25 のトークナイザに文字2-gram を用いる

## Context and Problem Statement

ADR-0025 で BM25 を自前実装すると決めた。そこでは「Python 側で形態素解析器と
BM25 の実装を用いれば、DB を変えずに実現できる」と書いていたが、
**実装では形態素解析器を使っていない。** その判断をここに記録する。

BM25 は文書を語に切ってから、語ごとの出現回数（tf）と文書頻度（df）を数える。
日本語には語の区切りが無いため、**何らかの切り方を決めなければ BM25 が
成立しない。** 形態素解析も文字 n-gram も、その「切り方」の候補である。

### Chroma 組み込みの BM25 は日本語を語に切れない

Chroma には `ChromaBm25EmbeddingFunction` がある。これを使えば自前実装が
不要になるため、まず調べた。

**トークナイザが snowballstemmer である。** 公式ドキュメントに明記されている。

```
This embedding function uses snowballstemmer to tokenize documents.
```

snowballstemmer は日本語を対象にしていない。日本語の条文を渡しても
語の境界が認識されず、**区切り記号のある場所でしか分かれない。**

BM25 は tf と df を語の単位で数えるため、語に切れていないものを入れても
意味のあるスコアにならない。

**これが却下の理由である。**

### IDF が文書の埋め込みに入っていないのは、欠陥ではない

調査の過程で、Chroma が返す値が次の式と一致することを確認した。

```
2.2 / (1 + 1.2 × (0.25 + 0.75 × 文書長 / 256))
```

これは BM25 の tf 部分そのもので、IDF の項が掛かっていない。
公式ドキュメントの既定値（k 1.2 / b 0.75 / avg_doc_length 256.0）と一致する。

**当初これを「BM25 の核が欠けている」と解釈したが、誤りだった。**

```
BM25 = Σ IDF(q) × [ tf·(k1+1) / (tf + k1(1 - b + b|D|/avgdl)) ]
                   └──────────── 文書だけで決まる ────────────┘
       └── コレクション全体の統計（N と df）に依存する ──┘
```

**IDF は文書を1件ずつ埋め込む関数には原理的に入れられない。** 1件追加する
たびに、既存の全文書の IDF が変わるからである。

したがって文書側には tf 部分だけを格納し、IDF は検索時に適用する。
Chroma は索引の設定で `bm25=True` を指定すると、クエリ側に IDF スケーリングが
かかる。Qdrant も同じ設計で、`"modifier": "idf"` を使う。

**スパースベクトルで BM25 を実現する標準的な分解である。**

この誤解を記録しておくのは、同じものを見た人が「IDF が無い」と判断する
のを防ぐためである。

### 法令用語は一般の辞書に無い

形態素解析器は辞書を引いて語の境界を決める。辞書に無い語は、
**知っている語の組み合わせに分解される。**

法令文には一般の辞書に無い語が多い。分解されると、本来1語として引けるべき
ものが引けなくなる。辞書を育てる道もあるが、**対象が全法令（8,997法令、
706,075チャンク）なので、どの語を追加すべきかを事前に列挙できない。**

## Decision Drivers

* 辞書に無い語で検索が壊れないこと
* 法令で実際に検索される語に届くこと。「契約」「工事」「届出」のような
  2文字の熟語が多い
* 辞書のメンテナンスを増やさないこと
* ADR-0010 で「検索方式は評価対象のため自前実装する」と定めており、
  切り方も制御できること

## Considered Options

1. Chroma 組み込みの `ChromaBm25EmbeddingFunction` を使う
2. 形態素解析器（MeCab / Sudachi）＋ 辞書
3. **文字2-gram**
4. 文字3-gram 以上

## Decision Outcome

Chosen option: **「文字2-gram」**

選択肢1は、トークナイザが日本語を語に切れない。

選択肢2は辞書に無い法令用語が分解される。辞書を育てる判断は、
対象の広さに対して終わりが見えない。

**選択肢4を採らない理由が、2を採らない理由と同じ形で出てくる。**

```
3-gram にすると「契約」「工事」のような2文字の熟語が索引を引けない
```

3文字ずつに切った索引に対して2文字で問い合わせると、一致する単位が存在
しない。日本語で2文字の語は非常に多いため、**この取りこぼしは広い範囲に効く。**

PostgreSQL で `pg_trgm`（3-gram）が日本語に不向きとされ `pg_bigm`（2-gram）が
作られたのも同じ理由である。

### 句読点をまたぐ2-gram を作らない

先に句読点で切ってから、各断片について2-gram を作る。

```python
clean_text = re.split('[、。・()「」]', normalized_text)
```

「売。」のような、句点をまたいだ2-gram は**どの語の一部でもない。**
作ると語彙が増え、文書長（BM25 の `|D|`）を水増しして正規化の分母を
狂わせる。

出現回数が必要なので、重複は取り除かない。

1文字しか残らない断片は `range(len(clean) - 1)` が `range(0)` になるため、
何も作られずに消える。

### 検証

3文書（`販売販売販売` / `通信販売` / `消防設備`）で、質問「販売」に対する
スコアを手計算と照合した。

```
0.685 / 0.508 / 0.0
```

手計算と一致した。IDF・tf・文書長の正規化がすべて意図どおりに効いている
ことを、この規模で確認してある。

## Consequences

* Good: **辞書が要らない。** 法令用語が辞書に無くても壊れない。
  辞書のメンテナンスという運用が発生しない
* Good: **2文字の熟語が索引を引ける。** 法令で検索される語の多くがこの長さで、
  3-gram を選ぶと取りこぼす範囲が広い
* Good: Chroma 組み込みの BM25 を**調べたうえで却下した記録が残る。**
  却下理由はトークナイザの1点に絞れている
* Good: **「IDF が入っていない」という誤読を記録した。** スパースベクトルで
  BM25 を実現する際、IDF が文書側に無いのは設計であって欠陥ではない。
  同じものを見た人が同じ誤解をしなくて済む
* Good: 切り方を自分で持っているので、比較実験の対象にできる
* Bad: **語彙が大きくなる。** 5万チャンクで約50万列。形態素解析なら
  もっと小さい。疎行列で持っているため実害は出ていない（約80MB、
  密なら100GB）が、全件（706,075チャンク）では未測定
* Bad: **意味の無い2-gram が大量に混ざる。** 「のに」「して」のような
  語をまたぐ組み合わせが索引に入る。IDF がこれらの重みを下げるが、
  ゼロにはならない
* Bad: **1文字の語が引けない。** 2-gram なので、1文字で問い合わせると
  一致する単位が無い。法令では「条」「項」「号」などが該当する。
  実害があるかは測っていない
* Bad: **形態素解析との比較を実測していない。** 却下の理由は「辞書に
  無い語が分解される」という性質であって、実際にどれだけ精度が下がるかを
  測ってはいない
* Bad: 句読点の集合 `[、。・()「」]` を手で決めている。他の記号
  （「：」「；」など）をまたぐ 2-gram は今も作られる
* Bad: **`ChromaBm25EmbeddingFunction` に自前のトークナイザを差し込めるかを
  確認していない。** 差し込めるなら、Chroma 側の BM25（索引が IDF を適用する）
  を使う選択肢があった。ただし ADR-0010 で検索方式を自前実装すると定めて
  おり、BM25 の重みや統合方法を制御する必要があるため、結論は変わらない
* Bad: **Chroma のスパースベクトル検索がローカルの `PersistentClient` で
  使えるかを確認していない。** ドキュメントが Cloud 配下にあり、
  ADR-0024 で `CloudClient` を使わないと決めているため、使えない可能性がある
