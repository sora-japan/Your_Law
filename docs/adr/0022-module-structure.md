# ADR-0022: 処理の段階で分けるパイプライン構成とし、パースとチャンク化は分離しない

## Context and Problem Statement

実装が進み、XMLパース、テキスト抽出、チャンク分割、埋め込み、検索が
複数ファイルに分かれてきた段階で、ディレクトリ構成を整理する必要が生じた。

当初は `backend/ai/`、`backend/data/`、`backend/src/models/rag/` の3系統に
分かれており、どこに何を置くかのルールが定まっていなかった。
`data/` にはデータ（法令XML）と調査用スクリプトが混在していた。

構成の選択肢として、クリーンアーキテクチャと DDD を検討した。

調査の結果、両者とも小規模プロジェクトへの適用については
オーバーエンジニアリングになるという指摘が複数ある。

* 初期段階で過剰に抽象化すると、シンプルな機能の開発でも過剰な設計が必要となり、
  余計なコードや複雑さが生まれる。最初は必要最小限の抽象化を行い、
  進行する中で必要に応じて抽象化を進めるべき
* DDD が有効なのは、業務ドメインが非常に複雑でビジネスロジックが多岐にわたる場合、
  大規模チームでの開発、ビジネス要件が頻繁に変わる場合
* 小規模プロジェクトで DDD を取り入れると「クラスやファイルが乱立して面倒」
  「簡単なことをしたいのにコードばかり増える」という結果になりやすい

ディレクトリの分け方には layer-based（層で分ける）、type-based（種類で分ける）、
feature-based（機能で分ける）の3系統がある。

## Decision Drivers

* 本プロジェクトの複雑さがどこにあるか
* 開発規模（1人）と期間（約3週間）
* 比較実験のために差し替える箇所が明確であること
* データフロー図とディレクトリ構成が対応していること

## Considered Options

1. クリーンアーキテクチャ（entity / usecase / interface adapter / infrastructure）
2. DDD（domain / application / infrastructure、集約・リポジトリ等を導入）
3. feature-based（法令取り込み / 改正検知 / 検索 / 質問応答 で分ける）
4. 処理の段階で分けるパイプライン構成

## Decision Outcome

Chosen option: "処理の段階で分けるパイプライン構成", because
本プロジェクトの複雑さは業務ルールではなく**データ処理**にある。
XMLの構造、法令のバージョン管理、チャンク分割がその中心であり、
ドメインモデルとして整理すべき業務ルールが存在しない。
したがって DDD の適用対象がない。

選択肢3（feature-based）は、機能をまたいで使う要素（パーサー、埋め込み、
ベクトルDB）が多く、共通部分が肥大して分割の意味が薄れる。
feature-based は規模が大きいほど効果が出る手法であり、本プロジェクトの規模では逆効果になる。

本プロジェクトの処理は XML → テキスト → チャンク → ベクトル → 検索 → 生成と
**一方向に流れるパイプライン**である。処理の段階でモジュールを分ければ、
データフロー図とディレクトリ構成が一対一で対応し、
どこに何があるかを図から追える。

ただし、クリーンアーキテクチャの中心的な考え方である
「**差し替える予定のある依存を、呼び出し側から分離する**」は採用する。
埋め込みモデル（ruri / Qwen3 / bge-m3）とベクトルDB（Chroma / pgvector）は
比較実験のために差し替える予定があり、抽象化のための抽象化ではなく実利がある。
ただしインターフェースクラスや DI コンテナは導入せず、
関数のシグネチャを揃えるにとどめる。

### 構成

```
backend/
├── data/              # データ置き場（コードは置かない）
│   └── all_xml/
├── src/
│   ├── ingestion/     # XML読み込み → テキスト抽出 → 正規化 → チャンク化
│   ├── embedding/     # テキスト → ベクトル（差し替え対象）
│   ├── store/         # ベクトルの保存と検索（差し替え対象）
│   ├── retrieval/     # 検索・BM25・RRF・リランキング
│   ├── generation/    # LLM
│   └── api/           # FastAPI
├── scripts/           # 一度きりの調査スクリプト
├── eval/              # 評価データと評価コード
└── docs/adr/
```

`scripts/` を本番コードから分離する。構造調査に用いたスクリプトは
役目を終えており、本番のパイプラインと混在させると読み手が混乱するため。

### パースとチャンク化を分離しない

当初は `parser/`（XML → 条のテキスト）と `chunking/`（条 → チャンク）を
分ける案だったが、1つの `ingestion/` にまとめる。

Microsoft の RAG ガイド（Azure Architecture Center「チャンク化のフェーズ」）は、
読み込みとチャンク化について次のように推奨している。

* ほとんどの場合、読み込みとチャンクコードの組み合わせはより簡単な実装である
* まず組み合わせることから始め、必要な場合に分離する
* **分離する場合は、ドキュメントを中間形式に変換しない。データが失われる可能性がある**

本プロジェクトでこの「失われるデータ」に当たるものは具体的に存在する。

| 情報 | 中間形式に含め忘れると失われるもの |
|---|---|
| `Sentence` の `Function` 属性 | 本文と但し書きの区別（ADR-0013 で再検討の可能性を明記済み） |
| `ArticleCaption` | 条見出しを単独で扱えない（ADR-0014 の比較実験で必要になる見込み） |
| `Table` / `TableRow` / `TableColumn` | 表の行と列の対応 |
| `Column` | 全角スペースが構造由来か原文由来かの判別 |
| `Rt` | ルビの読み仮名そのもの |
| `Extract` / `Delete` / `Hide` 属性 | 抄録・削除・非表示の状態 |

とくに上2つは、既に策定済みの ADR の中で「将来必要になりうる」と
自ら記録している情報である。中間形式に変換してから分離すると、
必要になるたびに変換処理を修正し、全件をパースし直すことになる。

チャンク分割は条・項・号という**XMLの構造に沿って行う**（ADR-0014）。
入力に構造が必要であることは仕様から導かれる必然であり、設計上の不備ではない。

レイアウトは flat layout とする。`src` レイアウトの利点は、
インストールされていない状態での誤った import を防ぐことにあり、
ライブラリとして配布する場合に効く。本プロジェクトは配布しないアプリケーションであり、
ML系プロジェクトでは flat layout が多く採用されている。

### Consequences

* Good: データフロー図とディレクトリ構成が対応し、処理の流れを追える
* Good: パースとチャンク化を分離しないため、中間形式による情報の欠落が発生しない。
  新たな属性や構造が必要になっても、その場で XML から取得できる
* Good: 差し替え対象（埋め込みモデル、ベクトルDB）が独立しており、比較実験が容易
* Good: 抽象化の層が薄く、1人・短期間での開発速度を落とさない
* Good: 調査用スクリプトと本番コードが分離される
* Bad: 特定のアーキテクチャパターンに則っていないため、
  構成の妥当性を名前で説明できない。判断の根拠を都度説明する必要がある
* Bad: 規模が拡大した場合、モジュール間の依存が整理されず結合が進む可能性がある
  → 機能が増えて処理が一方向でなくなった時点で再検討する
* Bad: `ingestion/` が XML のパースとチャンク分割の両方を担うため、
  1モジュールの責務が広くなる。チャンク分割のロジックだけを
  XML から切り離して単体テストすることができない
  → テストは実際の法令XMLを入力として行う
* Bad: Microsoft のガイドは主に PDF や HTML など、
  パースに曖昧さが伴う文書を想定している可能性がある。
  法令XMLは階層が明示されており前提が異なるため、
  この推奨がそのまま当てはまるかは検証していない
* Bad: 認証やユーザーデータを扱う機能を追加する場合、
  RDB が必要になり `store/` の位置づけを見直す必要がある
  （現時点では認証を実装しない方針）
