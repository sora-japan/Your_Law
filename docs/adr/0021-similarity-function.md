# ADR-0021: 埋め込みを正規化し、類似度関数にコサインを用いる

## Context and Problem Statement

最小RAG（登録認証機関等に関する規則、133条）を Chroma で構築したところ、
検索結果の距離が 217〜304 という値になった。

Chroma の既定の距離関数は L2（ユークリッド距離の二乗）である。
正規化されたベクトル同士の L2 二乗距離は最大でも 4 に収まるため、
この値は **ruri-v3-310m の出力が正規化されていない**ことを示していた。

一方、ruri-v3-310m のモデルカードは類似度関数としてコサイン類似度を指定している。
距離関数がモデルの学習条件と一致しておらず、順位が正しく出ない可能性があった。

距離関数と正規化の組み合わせを変えて、同一の質問で比較した。
質問は「職員の身分証明書の様式は？」、正解は第133条（67文字）。

| 距離関数 | 正規化 | 1位 | 2位 | 3位 | 1位の距離 |
|---|---|---|---|---|---|
| L2 | なし | **133** | 13 | 11 | 217.57 |
| コサイン | なし | **133** | 13 | 11 | 0.125290453 |
| **内積** | **なし** | 13 | **133** | 15 | -737.62 |
| 内積 | あり | **133** | 13 | 11 | 0.125290393 |

**正規化なしの内積のみ、正解が 2 位に落ちた。**3位には長い表を含む第15条が入った。
正規化ありの内積とコサインは、距離が小数点以下7桁まで一致した（末尾の差は浮動小数点誤差）。

## Decision Drivers

* 埋め込みモデルが学習時に想定した類似度関数に合わせること
* 設定の誤りが、エラーを出さずに順位だけを崩す事態を避けること
* 検索速度を過度に犠牲にしないこと

## Considered Options

1. L2（Chroma の既定）
2. 内積
3. コサイン

## Decision Outcome

Chosen option: "コサイン（かつ encode 時に normalize_embeddings=True を指定）", because
コサインはモデルカードが指定する類似度関数であり、学習条件と一致する。

正規化したベクトルでは、内積とコサインは数学的に同一の順位を返し、
実測でも距離が一致した。内積は計算が速いとされるが、
正規化を忘れた場合に**エラーを出さずに順位が崩れる**ことを実験で確認した。
コサインであれば、正規化の有無にかかわらず正しい順位が得られる。

速度差については、Chroma が内部で用いる hnswlib はコサイン指定時に
登録時に正規化したうえで内積で計算する実装と理解しており、
実質的な差は小さいと判断した（実装の詳細は未確認）。
加えて、全件投入時の処理時間は埋め込み計算が支配的であり、
距離計算の差は全体に対して無視できる。

L2 は正規化していないベクトルに対して、短いベクトルが有利になる偏りがある。
今回の質問では順位に影響しなかったが、採用しない。

正規化は文書側とクエリ側の**両方に同一に適用する**。
片方のみの正規化は比較を成立させない。

実装:

* `model.encode(texts, normalize_embeddings=True)`（文書・クエリとも）
* `create_collection(..., configuration={'hnsw': {'space': 'cosine'}})`

## 追記（2026-10-30): この決定は約3週間、実装されていなかった

旧版の実装指示は次の形だった。

```python
create_collection(..., metadata={'hnsw:space': 'cosine'})
```

**この書き方は Chroma に拾われていなかった。** エラーも警告も出ず、
コレクションは**既定の l2 で動いていた。**

ADR-0042 の調査で `collection.configuration` を出力したとき、
`space` が `l2` と報告されていた理由がこれである。当時は
「`metadata` 経由で cosine を指定している」と注記して済ませていた。
**注記ではなく、設定が効いていなかった。**

現行のAPIでは `configuration` で渡す。

```python
client.create_collection(
    name=name,
    configuration={'hnsw': {'space': 'cosine'}},
    metadata=metadata,
)
```

2026-10-30 に修正し、`collection.configuration` が
`{'hnsw': {'space': 'cosine', ...}}` を報告することを確認した。

### 検索結果への影響はない

埋め込みが正規化済み（`normalize_embeddings=True`）なので、
L2 距離と cosine 距離は単調な関係にある。

```
|a| = |b| = 1 のとき
  L2² = |a - b|² = 2 - 2·cos(a, b)

cos が大きい  ⇔  L2 が小さい
```

**上位k件の順位が一致する。** したがって 2026-10-04 から 2026-10-30 までの
測定値（ADR-0037、ADR-0042、ADR-0044）は、`space=l2` で測られているが、
cosine で測った場合と同じ順位を返している。

**数字を測り直す必要はない。** ただし「cosine で測った」と書くのは
正確でないため、該当するADRには `space=l2` だった旨を記す。

### この型の欠陥について

```
設定を書いた   → エラーが出ない   → 効いていると思った
               → 3週間気づかなかった
```

ADR-0021 自身が「設定の誤りが、エラーを出さずに順位だけを崩す事態を
避けること」を Decision Driver に挙げている。**その懸念が、
このADRの実装自体で現実になった。**

今回は結果に影響しなかったが、それは正規化していたからである。
正規化していなければ、距離関数の取り違えが順位を崩していた。

### Consequences

* Good: モデルの学習条件と一致する類似度で検索できる
* Good: 正規化を忘れても順位が崩れない。設定ミスに対して頑健
* Good: 距離が 0〜2 の範囲に収まり、値の解釈がしやすい
* Good: **正規化していたことが、設定が効いていなかった期間の測定値を
  救った。** 「頑健さのために cosine を選ぶ」という判断が、想定とは
  違う形で効いた
* Bad: 内積と比べてわずかに計算が多い可能性がある（実測はしていない）
* Bad: 比較は 1 法令・1 質問のみで行った。L2 とコサインで順位が変わらなかったことは、
  一般に差がないことを意味しない。影響の有無は評価データで確認する
* Bad: 正規化前のベクトルの大きさと条の文字数の関係は確認していない。
  内積で長い条が上位に来た理由を「長さの偏り」と断定する根拠はまだない
* Bad: **決定が約3週間実装されていなかった。** `metadata={'hnsw:space': ...}`
  が黙って無視される形式で、`collection.configuration` を出力するまで
  気づかなかった。**ADRを書いた後に、書いた通りに動いているかを
  確認していなかった**
* Bad: Chroma の距離関数の指定方法はバージョンによって異なる。
  `metadata` 経由の指定が通っていた版もあったと思われるが、特定していない。
  pgvector へ移行する場合は演算子（`<=>` コサイン / `<#>` 内積 / `<->` L2）を
  改めて選ぶ必要がある
* Bad: **距離関数によって値の意味が変わるため、絶対値で「一定値以下なら似ている」
  という判断はできない。** Chroma が返す `distances` はコサイン「類似度」ではなく
  コサイン「距離」であり（距離 = 1 − 類似度）、0 に近いほど似ている。
  内積を指定した場合は符号が反転し、負の大きな値が上位になる
  （実測で -737.62 が1位）。L2 は 0 以上の値で、正規化していなければ上限もない。
  閾値で足切りする処理を入れる場合は、距離関数ごとに値域を確認する必要がある
