# ADR-0036: 比較実験の前に評価データを確定させる

## Context and Problem Statement

ADR-0033 でサブセットの抽出方法を決めたが、その過程で工程の順序に制約が
あることが判明した。

サブセットは **評価データの gold に含まれる法令を必ず含む** 形で作る。
つまりサブセットの構成は評価データに依存する。

```
評価データの gold → 必ず含める法令 → サブセットの構成 → コーパス
```

評価データに問題を1問追加すると、gold の法令が増え、サブセットに含まれる
法令が変わり、**コーパスの内容が変わる**。

比較実験では閾値（200 / 500 / 1,000 / 2,000）を振って Recall@k / Hit@k /
MRR を比べる。埋め込みモデルの比較（bge-m3 / Qwen3-Embedding）は優先度で
落とす候補としている。比較が成立する条件は「変えていない部分が変わらない
こと」である。実験の途中で評価データを追加すると、それ以前に測った数値は
比較対象として使えなくなる。

### 現状

2026-10-13 時点で評価データは条文型16問のみ。gold に含まれる法令は
**1件（特定商取引法 `351AC0000000057`、430チャンク）** だけである。
状況型10問は未作成。

この状態で測った「必ず含める法令は1万件の4.3%」という数字は暫定値で
あり、状況型を追加すると大きく変わる。状況型の gold に挙がる法令
（介護保険法、建築基準法、消防法、食品衛生法、都市計画法など）は
いずれも特定商取引法より大きいと見込まれるため、合計が3,000〜5,000件、
目標1万件の3〜5割になる可能性がある。

その場合、サブセットの大半が gold の法令で占められ、競合する文書が
少ないため Recall が実際より良く出る。目標件数自体の見直しが必要になる。

## Decision Drivers

* **過去の数値がどのコーパスで測られたものか、見分ける手段がない。**
  ADR や README に書いた「Recall@5 = 0.72」という文字列は、コーパスが
  変わっても何も変わらない。古い数値と新しい数値が同じ顔で並ぶ
* **回し直すのを忘れることが実際のリスクである。** 再実行自体は安い
  （後述）が、忘れずに全部回し直すことを保証する仕組みがない
* **分析と文章化の方が時間を食う。** 数値を出すのは数分だが、読んで
  解釈して ADR やプレゼン資料に反映するのは数時間かかる。コーパスが
  変わるとそこをやり直すことになる
* 評価データの作成はドメイン判断を含み、機械的に進められない
  （状況型は「どの法令が関係するか」の判断が必要）
* ポートフォリオで提示する数値は、後から前提が崩れると提示した数字
  すべての信頼が失われる

## Considered Options

1. 実装を進めながら評価データを並行して増やす
2. 評価データ30問を確定させてから比較実験に入る
3. サブセットを gold に依存しない形にする（gold の法令を必ず含めない）
4. 評価データを増やすたびにサブセットを作り直し、全実験を回し直す

## Decision Outcome

Chosen option: **「評価データ30問を確定させてから比較実験に入る」**

工程を以下の順に固定する。

1. **評価データの確定**（条文型20問 + 状況型10問 = 30問）
2. `is_match` の修正（ADR-0035）と集計関数の修正（ADR-0034）
3. 必ず含める法令のチャンク数を再測定し、目標件数を見直す
4. サブセットの構築と再現性の検証
5. 比較実験（閾値4〜5通り）
6. 勝った構成で全件投入
7. 生成（Qwen3-8B）のビフォー/アフター

選択肢1は、実験を回した後に評価データを足した瞬間に過去の数値が無効に
なる。再実行は安いが、どの数値が古いコーパスのものかを見分ける手段が
ないため、気づかないまま documents に古い数値が残る。

選択肢3は ADR-0033 の要件1（gold の法令を必ず含む）を捨てることになり、
サブセットで Recall を測ること自体ができなくなる。

選択肢4は、再実行そのものは20〜30分で済むので計算時間の問題ではない。
却下の理由は、評価データを追加するたびに ADR・README・プレゼン資料の
数値をすべて差し替える運用になり、差し替え漏れを検出できないこと。

## Consequences

* Good: 比較実験の数値が、実験を通して同一のコーパスで測られたものに
  なる
* Good: 「サブセットが評価データに依存する」という依存関係を、実験を
  始める前に発見できた。実験後に気づいた場合、問題は再実行の手間ではなく
  「どの数値が古いコーパスのものか分からない」という状態に陥ることだった
* Good: 評価データの作成を工程の先頭に置いたため、最も頭を使う作業を
  疲れていない時間に当てられる
* Bad: 評価データが完成するまで、実データでの Recall が1つも出ない。
  進捗が数値として見えない期間が生じる
* Bad: 評価データを「確定」させるため、実験中に「この問題は不適切だった」
  と気づいても追加・修正ができない。修正する場合は、修正前の数値を
  破棄して全実験を回し直すか、修正前後の数値を混ぜないよう明記する
  必要がある
* Bad: 目標件数1万という値は、状況型を追加した後の再測定で見直す。
  現時点の「10,014チャンク / 181法令」という実測値は、評価データ確定後に
  取り直す必要がある
