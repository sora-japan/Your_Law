# ADR-0047: gold の粒度は問題ごとに最も深い単位で書く

## Context and Problem Statement

検索評価の Recall@k は**条レベル**で計算している（ADR-0035、ADR-0037）。

```
gold    (law_id, article_num)        例: 介護保険法 第70条
分母    gold の条の数
分子    1チャンク以上が届いた条の数
```

一方チャンクは4レベルに分かれている（ADR-0014）。

```
条 / 項 / 号 / 機械分割
```

**gold が1条で、その条が複数チャンクに分割されている場合、
どのチャンクが届いても Recall が 1.0 になる。** 答えに必要な項が
一度も届いていなくても 1.0 である。

gold が複数条ある場合はこの問題が起きない。ts033（gold 2条）は
Recall 0.5 を返し、片方が届いていないことを正しく示した。
**単一 gold かつ分割されている場合に限って過大評価する。**

### 症状が人手判定で現れた

ADR-0046 の人手判定で、直感に反する結果が出た。

```
1位     24問   ○率 21%
2位      7問   ○率 43%
3位以下   5問   ○率 60%
```

**1位で引けた問題の方が正答率が低い。** 1位24問の内訳で説明がつく。

```
1位24問の種別   summary 5 / fact 4 / negation 4 / number 3 /
                situation 3 / long 2 / multi_doc 2 / comparison 1
```

**summary と situation が8問集中している。** これらは gold が1条で
長い条を指す問題が多く、どのチャンクが来ても1位になる。

```
「1位で引けた」が「答えが届いた」を意味していない
```

この状態で検索の比較実験（オーバーラップ、BM25+RRF、リランカー）を
行うと、**過大評価を引き継いだ指標で構成を選ぶことになる。**

---

## 過大評価の実例を chunk_id で確認した（2026-10-30）

**旧版は ts040 を実例として挙げたが、これは誤りだった。**
`scripts/check_gold_chunks.py` で chunk_id を突き合わせた結果、
ts040 では過大評価が起きていなかった。

```
ts009  特定商取引法 第26条  3537字
       gold の答えは第1項
       第1項を含むチャンクが 0本        条レベル 1.0  項レベル 0.0   ← A型
       （届いたのは別の項のチャンクだけ）

ts040  介護保険法   第70条  6670字
       gold の答えは第2項
       第2項の号が1位と2位に届いている  条レベル 1.0  項レベル 1.0   ← B型
```

**どちらも「1位・条レベル Recall 1.0」である。** 同じ数字が正反対の
ことを意味していた。

```
A型（ts009）  答えが一度も届いていないのに 1.0     → 指標の欠陥
B型（ts040）  答えは届いているが、生成が使えていない → 被覆または生成の問題
```

旧版は ts040 を A型として扱っていた。**「長い条で1位だから過大評価だろう」
という推測で書いていた。** 突き合わせたら逆だった。

B型は指標の問題ではないため、項レベルに直しても数字が変わらない。
**項レベル Recall に直したときに値が落ちるのは A型だけである。**

## Decision Drivers

* **比較実験の判断に使う指標である。** 過大評価したまま構成を
  選ぶと、選択の根拠がなくなる
* **gold は、比較したい変数から独立していなければならない。**
  ADR-0044 の「比較が成立する条件はRAG以外のすべてが同一」と
  同じ要請である
* **指標の上限が k 以下でなければならない。** 到達不能な指標は
  構成間の差を測れない
* 評価データは凍結済みである（ADR-0036）。差し替えはしない
* 既存の数字（ADR-0037、ADR-0042）との整合を壊したくない
* 残り日数が限られている

## Considered Options

1. **gold の粒度を問題ごとに最深の単位にする（条・項・号の混在）**
2. 条レベルのまま、影響を受ける問題数だけ報告する
3. チャンクIDレベルの gold（IR/RAG の慣例）
4. 条項号から「関連チャンク集合」を導出して照合する
5. `gold_answer` のキーフレーズを retrieved chunk の本文に照合する
   （文字被覆率）

## Decision Outcome

Chosen option: **「問題ごとに最深の単位で書く」**

```
条で足りる問題      {law_id, article_num}
項まで必要な問題    {law_id, article_num, paragraph_num}
号まで必要な問題    {law_id, article_num, paragraph_num, item_num}
```

**旧版は「項レベルに統一する」としていたが、統一しない。** 問題によって
必要な深さが違う。号で答えが決まる問題を項レベルで測れば、その問題では
過大評価が残る。

### コードの変更が要らない

`is_match` が gold の鍵だけを見る形になっている。

```python
all(value == retrieved_meta.get(key) for key, value in gold.items())
```

**gold に `paragraph_num` が無ければ項を見ない。** 鍵が増えれば自動的に
深く照合する。混在に既に対応している。

さらに `calculate_recall_at_k` が `len(gold_list)` で割るため、
**号を複数エントリにすればそのまま被覆率になる。**

```
gold = [
  {law_id, article_num: '34', paragraph_num: '1', item_num: '11'},
  {law_id, article_num: '34', paragraph_num: '1', item_num: '14'},
]
→ 分母 2。1つだけ届けば 0.5
```

**設計の変更は gold のデータだけで、コードは触らない。**

### 「号は柱書に依存するから gold の下限は項」は誤りだった

旧版の検討で「号だけを切り出すと柱書が失われるので、gold の粒度の
下限は項である」と書いた。**これはチャンク設計の話で、gold の粒度の
話ではなかった。**

```
チャンク設計   号だけのチャンクは柱書を持たないので、意味が通らない
               → 号チャンクへの柱書前置を比較実験で試す（別の論点）

gold の粒度     どのチャンクが届けば答えが書けるか
               → 号のチャンクが届いていれば、答えは書ける
```

混同していた。**gold の粒度に下限はない。**

### 条レベル維持を採らなかった理由

過大評価が**一方向**に働く。改善したように見える方向にしか誤差が出ない
ため、比較実験で「改善した」という結論が出やすくなる。

### チャンクIDを採らなかった理由

IR/RAG の標準形は検索単位（＝チャンク）に関連ラベルを付ける形で、
BEIR 等のベンチマークはそうなっている。**慣例としてはこちらが
正しい。** それでも採らなかった。

**チャンクIDが設定依存である。**

```
chunk_id = <law_revision_id>#<n>     n は法令ごとの通し番号（ADR-0030）
```

同じ設定なら再現するが、オーバーラップやチャンク閾値を変えると
番号の指す条文が変わる。

```
config A で作ったチャンクID gold
  → config B では別の条文を指す
  → オーバーラップ / 閾値の比較が原理的にできなくなる
```

**比較実験でやろうとしているのが、まさにその設定変更である。**

一般形にするとこうなる。

```
gold は、比較したい変数から独立していなければならない
測る側が、比べる側と一緒に動いてはいけない
```

加えて、45問それぞれについてどのチャンクが答えを含むかを目視で
注釈する作業が新規に発生する。評価データを凍結した趣旨に反する。

### 関連チャンク集合の導出を採らなかった理由

「gold の条項号から、答えを含むチャンクの集合を機械的に導出し、
その被覆率を測る」案。gold は条項号のままなので設定非依存に見える。

**しかし関連集合の大きさが設定で変わる。**

```
閾値 1000  第34条が 3チャンクに分割  → 関連集合 3件
閾値  600  第34条が 5チャンクに分割  → 関連集合 5件
```

分母が構成によって変わるため、**構成間の比較で偏る。** 分割が細かい
構成の方が、同じ検索性能でも被覆率が下がる。

### 文字被覆率を採らなかった理由

`gold_answer` のキーフレーズを retrieved chunk の本文に照合する案は、
設定非依存で新規注釈も不要という利点がある。

**しかし3点で脆い。**

```
1  言い換えと表記   「八日」vs「8日」、「申込みの撤回」vs「クーリング・オフ」
2  長さで重み付け   長い条文のキーフレーズが多く数えられる
3  分割位置で動く   同じ検索結果でも、チャンクの切れ目で部分点が変わる
```

2と3は設定非依存という利点を打ち消す。**チャンクの切り方を変える比較
実験で、指標が切り方に反応してしまう。**

さらに、検索の評価に回答可能性の判定が混ざる。**検索が届いたか
どうかを測りたいのであって、答えが書けるかを測りたいのではない。**

項・号レベル指標の**交差検証としてのみ**使う。

## 照合規則

項と号は法律の構造である。**チャンクをどう切っても動かない。**
そしてチャンクのメタデータには `paragraph_num` と `item_num` が既に
入っている（ADR-0045 の `build_context` 修正で確認）。**本文の文字列
照合が不要で、メタデータの比較だけで済む。**

```
チャンクが gold(条X, 項Y) を満たす条件

  条 = X  かつ
    項 = ''         → 条全体が1チャンク。すべての項を含むので満たす
    項 = Y          → 満たす
    項 = Y, 号 = Z  → 満たす
    項 ≠ Y          → 満たさない   ← 現行の指標に無い判定
```

最後の行が過大評価を閉じる。ts009（第26条、答えは第1項）で、
別の項のチャンクが届いても満たさなくなる。

### 関連集合は k 以下でなければならない

**`gold_answer` の「など」は展開しない。**

```
ts032  都市計画法第34条  「第11号、第14号など」
       → 第34条には15号ある
       → 15号すべてを gold にすると、k=10 では上限 10/15 = 0.67
       → 18号ある条なら 10/18 = 0.56
```

**到達不能な指標になる。** 1.0 が原理的に出ない指標では、構成間の差が
上限に押しつぶされて見えなくなる。

```
gold に書くのは、gold_answer に明示されているものだけ
「など」の中身は展開しない
```

これは「答えとして十分か」ではなく「指標として機能するか」で決めた
線引きである。**答えの完全性は人手判定（ADR-0046）が見る。**

### 深い粒度を付けるのは必要な問題だけ

```
項・号を指定する   gold の条が複数チャンクに分割されている問題
条だけにする       それ以外 → 「条全体のどこでもよい」という現行の挙動
```

条が分割されていなければ項の区別に意味がない。**分割されている条が
何問あるかを先に数え、その問題にだけ深い粒度を足す。**

注釈のコストは低い。ADR-0046 の人手判定の過程で、45問すべての条文を
読んで項・号まで特定している。

```
ts024  「内容は第27条第11項と一致している」
ts034  「第51条第1項第2号を『第2項』と記載」
ts023  「第7_3条の項番号は誤り」
ts039  「gold_answer の第1項第5号」
```

**新しい分析ではなく、判定記録からの転記である。**

粒度を足すのは gold への**追加**であって、条の差し替えではない。
ADR-0036 の凍結の趣旨（測った後に gold を都合よく変えない）には
反しない。条レベルの Recall は追加後も同じ値を返す。

### 両方の数字を報告する

```
条レベル Recall@10   既存の値（同一設定の幅 0.719〜0.789、ADR-0042）
最深レベル Recall@10 これから測る
差                   = 過大評価の大きさ
```

**指標の欠陥を、指標を2つ並べて定量化する。** 既存の数字が残るため、
ADR-0037 と ADR-0042 との整合も壊れない。

## 実装前に確認が必要な点

**機械分割されたチャンクが項番号を持っているか。**

```
チャンクの4レベル   条 / 項 / 号 / 機械分割
```

機械分割チャンクの `paragraph_num` が空だと、「項='' なら条全体」
という規則に引っかかって**また全部満たしてしまう。**
`src/ingestion/chunk_splitting.py` で、機械分割時にメタデータを
どう引き継いでいるかを確認する。

空になっている場合は、規則を次のように狭める必要がある。

```
項 = '' かつ そのチャンクが条の全文を含む  → 満たす
項 = '' かつ 条の一部にすぎない            → 満たさない（判定不能として除外）
```

## Consequences

* Good: **設定非依存である。** チャンク設定を変える比較実験で
  gold が動かない。オーバーラップと閾値の比較が成立する
* Good: **コードを変更しない。** `is_match` が gold の鍵だけを見るため
  混在に対応済みで、`calculate_recall_at_k` が `len(gold_list)` で割るため
  号を複数エントリにすればそのまま被覆率になる
* Good: **メタデータの比較だけで済む。** 本文の文字列照合が不要で、
  表記揺れの影響を受けない
* Good: **既存の数字が残る。** 条レベルと最深レベルを並べて報告でき、
  差がそのまま過大評価の大きさになる
* Good: **注釈コストが低い。** 項・号の特定は人手判定の過程で済んでいる。
  分割されている条だけに付けるため、対象は10問前後と見込まれる
* Good: 既存の `retrieval_*.jsonl` に `retrieved_chunk_ids` が
  残っているため、**再検索せずに計算できる**
* Good: **ADR-0046 の逆相関に説明が付く。** 「検索指標を改善しても
  回答品質は上がらない」という観測を、指標の定義まで降りて説明できる
* Good: **却下した4案の理由が「指標の性質」で揃った。** 設定依存
  （チャンクID）、分母が設定で動く（関連集合）、長さと分割位置に反応
  （文字被覆率）、一方向の誤差（条レベル維持）。**gold は比較したい変数から
  独立していなければならない**という一般形が取り出せた
* Bad: **未測定である。** 最深レベル Recall の値はまだ無い。
  差がどれだけ出るかは分からない
* Bad: **旧版の実例が誤っていた。** ts040 を過大評価の例として挙げたが、
  突き合わせの結果 B型（答えは届いている）だった。**推測で実例を
  書いていた。** 実例は chunk_id を突き合わせてから書くべきだった
* Bad: **機械分割チャンクの項番号を確認していない。** これが空だと
  照合規則を狭める必要があり、一部の問題が判定不能になる
* Bad: **「など」を展開しない線引きは、答えの完全性を測らない。**
  ts032 の都市計画法第34条で、モデルが1号しか示さなかったことは
  この指標では落ちない。人手判定に依存する
* Bad: **凍結の運用に例外を作った。** 「追加であって差し替えではない」
  という線引きで正当化しているが、追加も gold の変更である。
  次回は最初から最深の粒度で作る
* Bad: **キーフレーズ照合を実装していない。** 交差検証の手段を
  用意すると言いながら、残り日数の都合で項・号レベルのみになる可能性がある
* Bad: ADR-0042 のばらつきの幅（同一設定 0.070、全体 0.156）は
  **条レベルの Recall の上で測った値である。** 粒度を直した後、
  幅が変わる可能性がある
