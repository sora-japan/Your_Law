# ADR-0034: 測れなかった問題を評価の分母から外さない

## Context and Problem Statement

評価スクリプトの初期実装に、数値を実際より良く見せる構造があった。

```python
ans_data = dummy_set.get(eval_id)
if ans_data is None:
    continue          # 検索結果が無い問題を飛ばす
eval_total += 1       # 分母はここで初めて増える
```

評価データが16問あり、検索結果ファイルに3問しか入っていない場合、
出力は「3件中3件正解 / ヒットレート100.00」になる。数値は立派だが
何も測っていない。「答えが無い」と「答えが間違っている」を同一視せず、
**存在しなかった問題を評価対象から消している。**

同じ構造が `metrics.py` の集計関数3つにもある。

```python
def calculate_mrr(rr_list: list[float]) -> float:
    if len(rr_list) == 0:
        return 0.0
```

`0.0` は「スコアがゼロだった」という意味を持つため、「1問も評価して
いない」と区別がつかない。`calculate_hit_rate` と
`calculate_recall_at_k` も同じ形である。

これは自分が作った評価スクリプトが、自分に都合のいい数字を出す構造に
なっていた実例である。指標を作る側のバイアスとして記録する。

## Decision Drivers

* 評価の数値はポートフォリオで提示するものであり、後から「実は分母が
  縮んでいた」と判明すると提示した数字すべての信頼が失われる
* 「静かに 0 が出る」「静かに分母が縮む」はエラーにならないため、
  気づく機会が実行時には存在しない
* 原因の切り分けができること。検索精度の問題と、データが欠けている問題を
  区別したい

## Considered Options

1. 測れなかった問題を分母から外す（現状）
2. 測れなかった問題を 0点として分母に数える
3. 測れなかった問題があれば処理を停止する
4. 分母から外すが、外した件数を必ず出力する

## Decision Outcome

Chosen option: **原因によって 2 と 3 を使い分ける**

「測れない」には原因が2種類あり、対処が異なる。

### A. データが壊れている場合は停止する

gold の法令IDがコーパスに存在しない場合。原因は以下のいずれかで、
**どれも人間が気づいて直すべきもの**である。

* `eval_set.jsonl` の `law_id` の打ち間違い
* その法令が現行版に存在しない（廃止、または未施行のみ）
* 法令IDではなく法令番号を書いた（`351AC0000000057` と
  `昭和五十一年法律第五十七号` の混同）
* `find_current_version_paths` のバグ

この状態で進めると、その問題の Recall は永久に 0 になり、しかも出力は
「検索精度が低い」という顔をする。原因の特定に時間を失う。

`create_sub_chunks` に実装済み。差集合で検出し `ValueError` で停止する。

```python
missing = must_law_ids - chunks_by_law_id.keys()
if missing:
    raise ValueError(f'goldの法令がコーパスにありません: {sorted(missing)}')
```

### B. 検索が引けなかった場合は 0点として分母に数える

検索を実行して、上位k件に正解が含まれなかった場合。これは**測定結果**
であり、異常ではない。0点として全問の分母に数える。

評価スクリプトを `db.search` を直接呼ぶ形に書き換えることで、「検索結果の
行が存在しない」という状況そのものが設計から消える。クエリを投げれば
必ず結果（空リストを含む）が返るため、分母は常に問題数と一致する。

### 集計関数の空リスト

`calculate_mrr` / `calculate_hit_rate` / `calculate_recall_at_k` が空の
入力に対して `0.0` を返す挙動を改める。空は「評価していない」であり、
スコアではない。例外を投げるか、件数を併せて返す形にする。

具体的な方式は実装時に決める（本ADRが `proposed` である理由）。

### 出力に必ず含める項目

どの方式でも、以下を出力に含める。

* 評価した問題数（分母）
* 評価データの総問数
* この2つが一致しない場合はその理由

分母と総問数を並べて出せば、縮んでいることが目で分かる。

## Consequences

* Good: 評価の数値が「全問に対する割合」であることが保証される
* Good: データの不整合と検索精度の低さが、停止するかしないかで区別される
* Good: 評価スクリプトを `db.search` 直結にすることで、問題の原因そのもの
  （答えの行が無い状態）が設計から消える
* Good: 「自分が作った評価が自分に都合よく動く構造になっていた」ことを
  自分で発見して直した記録が残る
* Bad: データが1件でも壊れていると評価が1問も回らない。急いで数字を
  出したい局面では不便になる。緩めたくなったときに緩めると、この決定の
  意味が失われるので、緩めるなら本ADRを更新する
* Bad: 本ADRは `proposed`。`evaluate_retrieval.py` の書き換えと
  `metrics.py` の集計関数の修正が未実施であり、実装後に `accepted` へ
  更新する
* Bad: 「0点として数える」は Recall を下げる方向に働く。ポートフォリオで
  見せる数字が悪くなるが、それが実態である
