# ADR-0034: 測れなかった問題を評価の分母から外さない

## Context and Problem Statement

評価スクリプトの初期実装に、数値を実際より良く見せる構造があった。

```python
ans_data = dummy_set.get(eval_id)
if ans_data is None:
    continue          # 検索結果が無い問題を飛ばす
eval_total += 1       # 分母はここで初めて増える
```

評価データが16問あり、検索結果ファイルに3問しか入っていない場合、
出力は「3件中3件正解 / ヒットレート100.00」になる。数値は立派だが
何も測っていない。「答えが無い」と「答えが間違っている」を同一視せず、
**存在しなかった問題を評価対象から消している。**

同じ構造が `metrics.py` の集計関数3つにもある。

```python
def calculate_mrr(rr_list: list[float]) -> float:
    if len(rr_list) == 0:
        return 0.0
```

`0.0` は「スコアがゼロだった」という意味を持つため、「1問も評価して
いない」と区別がつかない。`calculate_hit_rate` と
`calculate_recall_at_k` も同じ形である。

これは自分が作った評価スクリプトが、自分に都合のいい数字を出す構造に
なっていた実例である。指標を作る側のバイアスとして記録する。

## Decision Drivers

* 評価の数値はポートフォリオで提示するものであり、後から「実は分母が
  縮んでいた」と判明すると提示した数字すべての信頼が失われる
* 「静かに 0 が出る」「静かに分母が縮む」はエラーにならないため、
  気づく機会が実行時には存在しない
* 原因の切り分けができること。検索精度の問題と、データが欠けている問題を
  区別したい

## Considered Options

1. 測れなかった問題を分母から外す（現状）
2. 測れなかった問題を 0点として分母に数える
3. 測れなかった問題があれば処理を停止する
4. 分母から外すが、外した件数を必ず出力する

## Decision Outcome

Chosen option: **原因によって 2 と 3 を使い分ける**

「測れない」には原因が**3種類**あり、対処が異なる。

### A. データが壊れている場合は停止する

gold の法令IDがコーパスに存在しない場合。原因は以下のいずれかで、
**どれも人間が気づいて直すべきもの**である。

* `eval_set.jsonl` の `law_id` の打ち間違い
* その法令が現行版に存在しない（廃止、または未施行のみ）
* 法令IDではなく法令番号を書いた（`351AC0000000057` と
  `昭和五十一年法律第五十七号` の混同）
* `find_current_version_paths` のバグ

この状態で進めると、その問題の Recall は永久に 0 になり、しかも出力は
「検索精度が低い」という顔をする。原因の特定に時間を失う。

`create_sub_chunks` に実装済み。差集合で検出し `ValueError` で停止する。

```python
missing = must_law_ids - chunks_by_law_id.keys()
if missing:
    raise ValueError(f'goldの法令がコーパスにありません: {sorted(missing)}')
```

**この検出が覆う範囲は限定的である**（下記の追記を参照）。

### B. 検索が引けなかった場合は 0点として分母に数える

検索を実行して、上位k件に正解が含まれなかった場合。これは**測定結果**
であり、異常ではない。0点として全問の分母に数える。

評価スクリプトを `db.search` を直接呼ぶ形に書き換えることで、「検索結果の
行が存在しない」という状況そのものが設計から消える。クエリを投げれば
必ず結果（空リストを含む）が返るため、分母は常に問題数と一致する。

### C. 答えがコーパスの範囲外にある場合は不可答として扱う（追記 2026-10-30）

**告示は本プロジェクトのコーパスに含まれていない。**

e-Gov の法令XMLから取得しているのは法令本体であり、法令種別は
憲法・法律・政令・勅令・府省令・規則である。**告示はこの列挙に入らない。**

```
介護報酬の算定基準         → 告示。コーパスに無い
診療報酬点数表             → 告示。コーパスに無い
各種の基準・様式を定める告示 → コーパスに無い
```

これは A（データの壊れ）でも B（検索の失敗）でもない。
**コーパスの境界である。**

```
A  gold に書いた法令がコーパスに無い        → 評価データの誤り。停止する
B  コーパスにあるが上位k件に入らなかった    → 測定結果。0点で数える
C  答えがそもそも告示にある                 → 不可答。棄権が正しい挙動
```

ADR-0044 の ts043 がこの型だった。

```
ts043（RAGなし）
  「介護報酬の算定基準（昭和59年告示第148号）」第2条第1項 を根拠として提示
  → 介護保険法は平成9年。昭和59年の介護報酬告示は存在し得ない
  → 法令番号の形式も告示のものではない
```

**この問題に対する正しい挙動は棄権である。** RAGありでは棄権した
（ADR-0045 の 4/5 のうちの1問）。

したがって、**告示に答えがある質問は評価データの「不可答」に分類する。**
検索の失敗として数えてはいけない。検索が届かないのは当然であり、
コーパスを広げない限り永久に届かない。

**逆に、告示の内容を答えてしまった回答は創作として扱う。** コーパスに
無い情報を出しているため、根拠は記憶か捏造のいずれかである。

この分類は ADR-0011（網羅性を保証しない）および ADR-0001（取得範囲）の
帰結であり、新しい決定ではない。**明文化していなかったため、
評価の集計で検索失敗と混ざる余地が残っていた。**

### 集計関数の空リスト

`calculate_mrr` / `calculate_hit_rate` / `calculate_recall_at_k` が空の
入力に対して `0.0` を返す挙動を改める。空は「評価していない」であり、
スコアではない。例外を投げるか、件数を併せて返す形にする。

具体的な方式は実装時に決める（本ADRが `proposed` である理由）。

**2026-10-30 時点で未実施である。** さらに調査の過程で、
`calculate_mrr` と `calculate_hit_rate` の**実装が同一である**ことが
判明した。名前が違うのに中身が同じなので、どちらを呼んでも同じ値が
出る。整理が必要である。

`calculate_recall_at_k` が `len(gold_list)` で割る形になっていることは、
ADR-0047 の「号を複数エントリにすれば被覆率になる」という設計に
そのまま使える。**こちらは変えない。**

### 出力に必ず含める項目

どの方式でも、以下を出力に含める。

* 評価した問題数（分母）
* 評価データの総問数
* この2つが一致しない場合はその理由

分母と総問数を並べて出せば、縮んでいることが目で分かる。

## 追記（2026-10-30): A の検出が覆う範囲

`create_sub_chunks` の `ValueError` は、**全コーパスに gold の法令が
あるか**を見ている。

```python
chunks_by_law_id   # 706,075チャンク全体から作った索引
missing = must_law_ids - chunks_by_law_id.keys()
```

**サブセットに入ったかは見ていない。**

```
覆う      gold の法令が 706,075 チャンクの中に存在しない   → ValueError
覆わない  存在するが、5万件のサブセットに入らなかった      → 静かに通る
```

後者は、必須法令を強制的に混ぜる処理にバグがあった場合に起きる。
**エラーは出ず、5万件が返り、その法令の問題がまとまって圏外になる。**

ADR-0042 の 10/19（Recall 0.633、圏外15問、うち5問が次の実行で1位に
飛んだ）の候補としてこの型を挙げたが、**A の検出があるため
「コーパスに無かった」の線は消える。** 残るのは「コーパスにはあったが
サブセットに入らなかった」の線である。

ADR-0048 の検品（検査3）は、**構築後のコレクションに対して**
必須法令のチャンクが存在するかを確認する。A の検出と組み合わせて、

```
create_sub_chunks の ValueError   コーパスに無い        → 構築前に停止
check_collection の 検査3          サブセットに入らない  → 構築後に検出
```

という二段構えになる。

## Consequences

* Good: 評価の数値が「全問に対する割合」であることが保証される
* Good: データの不整合と検索精度の低さが、停止するかしないかで区別される
* Good: **「測れない」が3種類に分かれた。** データの壊れ（停止）、
  検索の失敗（0点）、コーパスの範囲外（不可答）。告示を明文化したことで、
  コーパスを広げない限り届かない問題を検索の失敗と混ぜなくなった
* Good: 評価スクリプトを `db.search` 直結にすることで、問題の原因そのもの
  （答えの行が無い状態）が設計から消える
* Good: 「自分が作った評価が自分に都合よく動く構造になっていた」ことを
  自分で発見して直した記録が残る
* Good: **A の検出の範囲を明示した。** コーパスへの存在は見ているが
  サブセットへの投入は見ていない。ADR-0048 の検品がこの穴を埋める
* Bad: データが1件でも壊れていると評価が1問も回らない。急いで数字を
  出したい局面では不便になる。緩めたくなったときに緩めると、この決定の
  意味が失われるので、緩めるなら本ADRを更新する
* Bad: 本ADRは `proposed`。**`metrics.py` の集計関数の修正が
  2026-10-30 時点で未実施である。** さらに `calculate_mrr` と
  `calculate_hit_rate` の実装が同一であることが判明しており、
  整理が必要
* Bad: 「0点として数える」は Recall を下げる方向に働く。ポートフォリオで
  見せる数字が悪くなるが、それが実態である
* Bad: **告示をコーパスに含めない判断自体は、利用者から見れば欠落である。**
  介護報酬や診療報酬は実務でよく参照される。範囲外であることを
  README とプレゼンで明示する必要がある
