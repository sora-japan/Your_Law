# ADR-0035: 一致判定は gold が指定したフィールドだけを比較する

## Context and Problem Statement

評価データには2種類の問題がある（ADR-0026、ADR-0027）。

| 種類 | 問題の形 | 正解の粒度 |
|---|---|---|
| 条文型（20問予定） | 「職員の身分証明書の様式は？」 | **条レベル** |
| 状況型（10問予定） | 「介護事業を始めたいが関係する法律は？」 | **法令レベル** |

状況型の正解は、埼玉県の新規指定申請ページの「介護保険法だけでなく
関係法令（建築基準法、都市計画法、消防法、食品衛生法等）の基準を
満たしていることが必要」という記載を出典とする。この一覧は法令名しか
挙げておらず、条番号は存在しない。

一方、検索結果は**チャンクレベル**である。チャンクは条・項・号・機械分割の
いずれかの単位で、1つの条が複数チャンクに分かれることもある。

`metrics.py` の現在の一致判定は3フィールドの完全一致を要求する。

```python
def is_match(gold: dict, retrieved_meta: dict) -> bool:
    law_id_match = (gold.get('law_id') == retrieved_meta.get('law_id'))
    provision_match = (gold.get('provision') == retrieved_meta.get('provision'))
    article_num_match = (gold.get('article_num') == retrieved_meta.get('article_num'))
    return law_id_match and provision_match and article_num_match
```

状況型の gold に `article_num` は書けない。省略すると
`gold.get('article_num')` は `None` を返す。検索結果側は
`build_metadata` が `OPTIONAL_KEYS` を空文字で埋めるため `''` である。
`None != ''` なので一致しない。

**つまり状況型10問は、どれだけ検索が優秀でも全問ミスになる。**
しかも `.get()` で両側を包んでいるため `KeyError` も出ず、静かに 0 が出る。
これは ADR-0034 と同じ失敗パターンである。

## Decision Drivers

* 条文型と状況型を同じ指標体系で扱いたい（評価コードを2系統に分けない）
* gold は手で書くデータであり、キー名の打ち間違いは気づきたい
* 検索結果はコードが生成するデータであり、欠けていたら前処理のバグ
  （ADR-0030 の `REQUIRED_KEYS` と同じ立場）

## Considered Options

1. 3フィールド完全一致（現状）
2. gold が指定したフィールドだけを比較する
3. 条文型と状況型で別の判定関数を持つ
4. 状況型の gold に代表的な条番号を人手で付ける

## Decision Outcome

Chosen option: **「gold が指定したフィールドだけを比較する」**

gold に書かれたキーを反復し、そのキーについてのみ検索結果と比較する。

* gold に `law_id` だけ書けば → 法令単位の判定
* gold に `law_id` + `provision` + `article_num` を書けば → 条単位の判定

同じ関数で両方の粒度を扱える。gold の書き方が判定の粒度を決める。

選択肢3は判定が2系統になり、「どちらの定義で測った数字か」が分からなく
なる。実際に `evaluate_retrieval.py` の `judgement`（文字列の集合に
含まれるか）と `metrics.py` の `is_match`（フィールド単位）という2つの
定義が並立していた。`judgement` は削除し、`metrics.py` に寄せる。

選択肢4は、出典に無い情報を人手で補うことになり、正解データの根拠が
弱くなる。埼玉県の一覧は「最低限含まれるべき法令の集合」として使うと
決めている（ADR-0027）。

### 空の表現を1つに決める

gold（手書きの JSONL）と検索結果のメタデータ（`build_metadata` が生成）が
突き合わされる境界である。空を `None` と `''` のどちらで表すかを統一し、
コードにコメントで明記する。

`build_metadata` は `OPTIONAL_KEYS` を空文字で埋めるため、検索結果側は
必ず `''` である。gold 側は「キーを書かない」で表現し、判定は gold に
あるキーだけを見るので、この不一致は判定に影響しない形になる。

### gold 側は直接アクセスする

検索結果側は `.get()` でよい（分割レベルによって存在しないキーがある）。
gold 側は `gold[key]` で直接アクセスする。gold は自分が手で書いたデータで、
キー名を打ち間違えたら気づきたい側である。

`build_metadata` が「必須キーは直接アクセス、任意キーは `.get()`」と
分けているのと同じ発想（ADR-0030）。

## 粒度のミスマッチが指標に与える影響

本決定で一致判定は扱えるようになるが、チャンクレベルの検索結果を
条・法令レベルの正解と比べるという構造そのものは残る。既知の性質として
記録する。

**長い条は複数のチャンスを持つ。** 1つの条が3チャンクに分かれていれば、
上位k件の中に3回登場する機会がある。短い条より有利になる。

**上位k件が同じ条で埋まることがある。** 5件引いたのに実質1条、という
状態が起きうる。Hit@5 は 1 になるが、取得できた「異なる条」は1つである。

**特定商取引法は430チャンクある。** 法令レベルの gold（「この法令から
最低1チャンク引けたか」）では、チャンク数の多い法令が有利になる。
状況型の gold に挙がる法令（介護保険法、建築基準法など）はいずれも
大きいため、この偏りは効く方向にある。

これらは「チャンク単位で検索し、人間が理解する単位（条・法令）で評価する」
という設計の必然であり、指標の読み方に反映する。将来、重複する条を
まとめてから評価する（条単位に畳む）方式も検討できるが、今回はスコープ外
とする。

## Consequences

* Good: 条文型と状況型を1つの判定関数・1つの指標体系で扱える
* Good: gold の書き方が判定の粒度を決めるため、評価データ側だけで
  粒度を調整できる
* Good: 一致の定義が1箇所になる（`judgement` を削除）
* Good: 状況型10問が全問ミスになる不具合を、評価を回す前に発見できた
* Bad: 本ADRは `proposed`。`is_match` の書き換えと `judgement` の削除が
  未実施であり、実装後に `accepted` へ更新する
* Bad: gold のキーが少ないほど判定が緩くなる。`law_id` だけの gold は
  「その法令のどのチャンクでも正解」になるため、条文型より Recall が
  高く出る。条文型と状況型の数値を合算した平均は意味が薄く、
  **種類別に分けて報告する必要がある**
* Bad: 長い条・大きい法令が有利になる偏りが残る。条単位に畳んでから
  評価する方式は未検討
* Bad: 空の表現（`None` か `''` か）の統一は、判定に影響しない形に
  したことで回避しているが、将来 gold を自動生成するようになると
  再び問題になりうる
