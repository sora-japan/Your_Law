# ADR-0035: 一致判定は gold が指定したフィールドだけを比較する

## Context and Problem Statement

評価データ50問（2026-10-15 確定）には、正解の粒度が異なる3種類が混在する。

| 粒度 | カテゴリ | 問数 | gold の形 |
|---|---|---|---|
| 条レベル | fact 10 / multi_doc 5 / comparison 5 / number 5 / negation 5 / long 5 / summary 5 | **40** | `law_id` + `provision` + `article_num` |
| 法令レベル | situation 5 | **5** | `law_id` のみ |
| 正解なし | unanswerable 5 | **5** | `[]`（空のリスト） |

状況型（situation）の正解は、埼玉県の新規指定申請ページの「介護保険法だけでなく
関係法令（建築基準法、都市計画法、消防法、食品衛生法等）の基準を満たしている
ことが必要」という記載を出典とする。この一覧は法令名しか挙げておらず、
**条番号が存在しない**。出典に無い条番号を人手で補うと正解データの根拠が
弱くなるため、gold は法令レベルのままにする（ADR-0027）。

一方、検索結果は**チャンクレベル**である。チャンクは条・項・号・機械分割の
いずれかの単位で、1つの条が複数チャンクに分かれることもある。

`metrics.py` の修正前の一致判定は、3フィールドの完全一致を要求していた。

```python
def is_match(gold: dict, retrieved_meta: dict) -> bool:
    law_id_match = (gold.get('law_id') == retrieved_meta.get('law_id'))
    provision_match = (gold.get('provision') == retrieved_meta.get('provision'))
    article_num_match = (gold.get('article_num') == retrieved_meta.get('article_num'))
    return law_id_match and provision_match and article_num_match
```

状況型の gold に `article_num` は書けない。省略すると
`gold.get('article_num')` は `None` を返す。検索結果側は
`build_metadata` が `OPTIONAL_KEYS` を空文字で埋めるため `''` である。
`None != ''` なので一致しない。

**つまり状況型5問は、どれだけ検索が優秀でも全問ミスになる。**
しかも `.get()` で両側を包んでいるため `KeyError` も出ず、静かに 0 が出る。
これは ADR-0034 と同じ失敗パターンである。

## Decision Drivers

* 3種類の粒度を同じ指標体系で扱いたい（評価コードを粒度ごとに分けない）
* gold は手で書くデータであり、キー名の打ち間違いは気づきたい
* 検索結果はコードが生成するデータであり、欠けていたら前処理のバグ
  （ADR-0030 の `REQUIRED_KEYS` と同じ立場）

## Considered Options

1. 3フィールド完全一致（修正前）
2. gold が指定したフィールドだけを比較する
3. 粒度ごとに別の判定関数を持つ
4. 状況型の gold に代表的な条番号を人手で付ける

## Decision Outcome

Chosen option: **「gold が指定したフィールドだけを比較する」**

gold に書かれたキーを反復し、そのキーについてのみ検索結果と比較する。

* gold に `law_id` だけ書けば → 法令単位の判定
* gold に `law_id` + `provision` + `article_num` を書けば → 条単位の判定

同じ関数で両方の粒度を扱える。**gold の書き方が判定の粒度を決める。**

選択肢3は判定が2系統になり、「どちらの定義で測った数字か」が分からなく
なる。これは仮の話ではなく、実際に `evaluate_retrieval.py` の `judgement`
と `metrics.py` の `is_match` という2つの定義が並立していた。`judgement`
は削除し、一致の定義を `metrics.py` の1箇所に集約した。

選択肢4は、出典に無い情報を人手で補うことになり、正解データの根拠が
弱くなる。埼玉県の一覧は「最低限含まれるべき法令の集合」として使うと
決めている（ADR-0027）。

### 実装

```python
def is_match(gold: dict, retrieved_meta: dict) -> bool:
    """goldに書かれているキーだけを比較する。

    goldがlaw_idのみなら法令単位、3フィールドあれば条単位の判定になる
    """
    match = all(value == retrieved_meta.get(key) for key, value in gold.items())
    return match
```

`gold.items()` を反復するため、比較するフィールドは gold 自身が決める。
検索結果側は `.get()` でよい（分割レベルによって存在しないキーがある）。

### `all()` が必要な理由

`all()` を外すとジェネレータ式がそのまま返る。

```python
match = (value == retrieved_meta.get(key) for key, value in gold.items())
return match       # generator object が返る
```

**ジェネレータオブジェクトは、中身が空でも全要素が偽でも、常に真である。**
したがって `find_rank` の

```python
if is_match(gold, retrieved_item):
    return rank
```

が rank=1 で必ず成立し、MRR / Hit@k / Recall@k がすべて 1.0 になる。
例外は出ず、警告も出ない。完璧な検索精度という顔をした指標が出力される。

リスト内包表記に変えても解決しない。`bool([False, False])` は `True` で
あり、空でないリストは真だからである。真偽値1個に畳む `all()` が必要。

これは「静かに良い数字が出る」系の不具合で、ADR-0034 と同じ系統である。
評価コードの不具合は、実装の不具合と違って**出力を見ても気づけない**。

### 一致判定の確認

`metrics.py` の `__main__` に5パターンを置いた（2026-10-15 実行、全て期待通り）。

| gold | 検索結果 | 期待 | 確認する性質 |
|---|---|---|---|
| `law_id` のみ | 同じ法令・別の条 | True | 法令単位では条が違っても一致する |
| `law_id` のみ | 別の法令 | False | 法令が違えば一致しない |
| 3フィールド | 完全一致 | True | 条単位の一致 |
| 3フィールド | 条番号だけ違う | False | 条の差を拾う |
| 3フィールド | 本則/附則だけ違う | False | `provision` の差を拾う |

修正前の実装では、本則チャンクが400,308件（全706,075件の57%）あるため、
`provision` が一致するだけで通る組み合わせが大量に発生していた。

### gold のキーの打ち間違いが検出されない理由

Decision Drivers に「gold のキー名の打ち間違いは気づきたい」と挙げたが、
本実装はこれを満たしていない。

```python
all(value == retrieved_meta.get(key) for key, value in gold.items())
#              ^^^^^^^^^^^^^^ .get() はこちら      ^^^^ キーはこちらから
```

**キーを持ってくるのは gold 側、`.get()` で問い合わせるのは検索結果側**
という向きが要点である。gold に `artcle_num`（`article` の綴り間違い）と
書くと、その綴りのまま `retrieved_meta` に問い合わせることになる。
`retrieved_meta` は `build_metadata` が機械的に作るためキーは正しく
`article_num` であり、`artcle_num` は存在しない。

```
key='law_id'      gold側='325AC0000000201'  meta.get(key)='325AC0000000201'  一致=True
key='artcle_num'  gold側='6'                meta.get(key)=None               一致=False
all(...) = False
```

打ち間違えたキーは gold の中に存在するので、`gold.get('artcle_num')` なら
`'6'` が返る。しかし問い合わせ先は正しいキー名を持っている側であり、
そこに間違った綴りで聞くため `None` が返る。`'6' == None` が偽になり、
**その問題は検索の良し悪しに関わらず常に不正解**になる。例外は出ない。

当初の設計案では「gold 側は `gold[key]` で直接アクセスし、打ち間違いなら
`KeyError` で気づく」としていたが、`gold.items()` で反復する形にしたことで
gold 側に添字アクセスが存在しなくなり、`KeyError` が出る経路が消えた。
検出するには、評価データの読み込み時に gold のキーを既知の集合
（`law_id` / `provision` / `article_num`）と突き合わせる検証が必要である
（ADR-0034 の A と同じ形）。**未実装。**

### 状況型は Recall@k に天井を持つ

状況型の gold は複数の法令が並ぶ（介護保険法・建築基準法・都市計画法・
消防法・食品衛生法など）。`calculate_recall_at_k` は gold 1件ごとに
ループするため、状況型の Recall@k は「必要な法令のうち何件を引けたか」
という意味になる。

このとき **gold の件数が k を超えると、Recall@k は構造的に 1.0 に届かない。**
上位k件に、k個より多い異なる法令は入らないためである。

**実測（2026-10-16）: gold 件数の最大は3件**（`scripts/count_gold.py`、
全50問の `len(row['gold'])` の最大値）。したがって k ≥ 3 であれば
Recall は 1.0 に到達でき、k=5 / 10 では天井に当たらない。

| k | gold 3件の問題の Recall 上限 |
|---|---|
| 1 | 1/3 ≒ 0.33 |
| 3 以上 | 1.0 |

**k=1 の Recall だけは上限が 1/件数 になる。** gold が3件の問題の
Recall@1 は、検索が完璧でも 0.33 である。これを「精度が低い」と読んでは
いけない。k=1 を報告する場合は Hit@1 を併記するか、Recall@1 を複数 gold の
問題について報告しないかを決める必要がある。

状況型は、指標によって逆向きの偏りを持つ。

| 指標 | 状況型での性質 |
|---|---|
| Hit@k | 1件当たれば 1.0。**緩い** |
| Recall@k | 全法令を引く必要がある。k < gold件数 なら**天井に当たる** |

なお「gold 件数」（リストの長さ、Recall の分母）と「gold のフィールド数」
（辞書のキー数、判定の粒度）は別の数字である。実測ではどちらも最大3だが
これは偶然であり、前者は状況型から、後者は条文型から出ている。
JSONL の `gold` がリストを指し、`metrics.py` の `gold` が辞書1件を指す
という命名の不一致があるため、混同しやすい箇所として記録する。

## 粒度のミスマッチが指標に与える影響

本決定で一致判定は扱えるようになるが、チャンクレベルの検索結果を
条・法令レベルの正解と比べるという構造そのものは残る。既知の性質として
記録する。

**長い条は複数のチャンスを持つ。** 1つの条が3チャンクに分かれていれば、
上位k件の中に3回登場する機会がある。短い条より有利になる。

**上位k件が同じ条で埋まることがある。** 5件引いたのに実質1条、という
状態が起きうる。Hit@5 は 1 になるが、取得できた「異なる条」は1つである。

**法令レベルの gold はチャンク数の多い法令が有利になる。**
「この法令から最低1チャンク引けたか」を問うため、チャンクの多い法令ほど
引きやすい。状況型の gold に挙がるのは介護保険法・建築基準法・都市計画法・
消防法・食品衛生法で、いずれも大きい法令のため、この偏りは効く方向にある。

これらは「チャンク単位で検索し、人間が理解する単位（条・法令）で評価する」
という設計の必然であり、指標の読み方に反映する。将来、重複する条を
まとめてから評価する（条単位に畳む）方式も検討できるが、今回はスコープ外
とする。

## Consequences

* Good: 3種類の粒度を1つの判定関数・1つの指標体系で扱える
* Good: gold の書き方が判定の粒度を決めるため、評価データ側だけで
  粒度を調整できる
* Good: 一致の定義が1箇所になった（`judgement` を削除）
* Good: 状況型5問が全問ミスになる不具合を、評価を回す前に発見できた
* Good: `all()` を外すと全指標が 1.0 になることを、実装の途中で踏んで
  確認している。評価コードの不具合は出力を見ても気づけないという性質の
  実例として残る
* Bad: **gold のキーの打ち間違いが静かに通る。** Decision Drivers に
  「キー名の打ち間違いは気づきたい」と挙げたが、実装はこれを満たして
  いない。詳細は後述。gold のキーを既知の集合と突き合わせる検証を
  入れていないため、**未対応**
* Bad: `is_match({}, retrieved_meta)` は `True` を返す（`all([])` が
  真であるため）。空の gold は、比較する条件が1つもないので
  **どのチャンクにも一致する**ことになる。現在の不可答5問は gold が
  `[]`（空のリスト）であり、`is_match` に空の辞書が渡る経路が存在しない
  ため、この不具合は起きない。ただし将来 `[{}]`（空の辞書を1つ含むリスト）
  と書くと、その問題は全チャンクが正解になる。不可答を `[]` で表している
  ことが、結果として安全側に働いている
* Bad: gold のキーが少ないほど判定が緩くなる。`law_id` だけの gold は
  「その法令のどのチャンクでも正解」になるため、条文型より Recall が
  高く出る。条文型40問と状況型5問の数値を合算した平均は意味が薄く、
  **種類別に分けて報告する必要がある**
* Bad: 長い条・大きい法令が有利になる偏りが残る。条単位に畳んでから
  評価する方式は未検討
* Bad: 空の表現（`None` か `''` か）の統一は、判定に影響しない形に
  したことで回避しているが、将来 gold を自動生成するようになると
  再び問題になりうる
