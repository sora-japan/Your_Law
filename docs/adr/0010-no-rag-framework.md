# ADR-0010: RAG の中核処理に統合フレームワークを使わない

## Context and Problem Statement

RAG の実装には LangChain のような統合フレームワークを用いる方法と、
各処理を個別に実装する方法がある。
統合フレームワークは文書の分割・埋め込み・検索・回答生成を数行で組めるが、
分割方式や検索方式が内部で決定される。

本プロダクトは「どの技術がどの課題に効くか」を評価によって示すことを目的としており、
チャンク分割と検索方式そのものが評価対象である。

## Decision Drivers

* チャンク分割・埋め込み・検索の挙動を比較実験の対象とすること
* 実装の中身を説明できる状態を保つこと
* 開発期間が限られており、学習コストを抑えたいこと

## Considered Options

1. LangChain 等の統合フレームワークで RAG 全体を構成する
2. すべて個別に実装する
3. 中核処理は個別実装とし、フロー制御にのみフレームワークを検討する

## Decision Outcome

Chosen option: "中核処理は個別実装とし、フロー制御にのみフレームワークを検討する", because
チャンク分割・埋め込み・検索は本プロダクトの評価対象であり、
フレームワークの内部で決定されると、比較実験の条件を制御できない。

加えて、法令XMLの構造（編・章・節・条・項・号）に沿った分割は、
文字数や区切り文字で機械的に分割する汎用の分割処理では実現できないため、
どちらにせよ個別実装が必要である。

一方、判定フローには分岐と再検索のループが含まれる見込みであり、
状態管理が複雑になった場合は LangGraph の導入を検討する。
ただし導入は「個別実装で状態管理が困難になった」ことを確認してから判断する。

### Consequences

* Good: チャンク分割・検索方式を比較実験の対象として制御できる
* Good: 実装の各段階を説明でき、評価結果の解釈が可能になる
* Good: 依存ライブラリが減り、バージョン互換の問題を避けられる
* Bad: 実装量が増え、開発時間を要する
* Bad: フレームワークが提供する既成の最適化（キャッシュ、リトライ等）を
  自前で実装する必要がある
