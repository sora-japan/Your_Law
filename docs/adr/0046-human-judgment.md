# ADR-0046: 回答の正誤は5段階で人手判定する

## Context and Problem Statement

生成の評価（ADR-0044）で「回答が正しいか」を測る必要があった。

機械的に測れるものは既にある。

```
棄権したか          テキストに「わからない」等が含まれるか
打ち切られたか      output_token >= max_new_tokens
生成時間            計測済み
法令番号を書いたか  テキストに法令番号の形式が現れるか
```

**しかし「その回答が正しいか」は測れていない。**

### 条番号が出ているかでは正誤が分からない

最初に考えたのは「回答に正解の条番号が現れるか」を機械的に見る方法である。
採らなかった理由は3つある。

```
法令名を照合できない   別の法令の同じ条番号でも一致してしまう
項を照合できない       条が合っていても項が違えば答えは違う
内容を照合できない     条番号が正しくても、その条が何を定めているかは見ていない
```

### ts049 が決定的な例を出した

RAGなしの ts049（介護保険法について問う問題）の回答がこうなっている。

```
第3条、第22条、第23条、…、第215条、…、第355条（2048トークンで打ち切り）
```

介護保険法の本則は第215条までである。第216条以降の140個は
存在しない条番号だが、**この回答には介護保険法に実在する条番号の
ほぼ全部が書かれている。**

```
検索が完全に失敗し、内容が空で、打ち切られた回答が
「正解の条番号を含んでいる」
```

**条番号の有無を見る方法では、この回答を正解と区別できない。**
条番号を照合せずに列挙するだけで指標を満たせてしまう。

この回答は `generation_norag_*.jsonl` に保存されており、
**誰でも開いて条番号を数えれば確認できる。**

## Decision Drivers

* **「条番号を書いた」は「正答」ではない。** 根拠の条番号が合っていても
  内容が誤っていれば、利用者は誤った法令解釈を信じる
* **RAGあり/なしの対比が本プロジェクトの主張である。** 創作が
  どの条件で起きるかを分類したい
* **面接で説明できる根拠を残したい。** 数字だけでなく、なぜその
  判定になったかを後から辿れる形にしたい
* 判定は50問×2条件＝100件。1件ごとに条文の原文照合が必要で、
  数時間かかる

## Considered Options

1. **5段階（○ / △ / × / 創作 / 棄権）で人手判定する**
2. 2段階（○ / ×）で人手判定する
3. LLM-as-a-Judge
4. 条番号の文字列一致による機械判定で報告する

## Decision Outcome

Chosen option: **「5段階で人手判定する」**

### 判定の基準

| 判定 | 基準 |
|---|---|
| ○ | 条番号・内容ともに正しい |
| △ | 内容は正しいが、項番号の誤りや射程の限定などの不足がある |
| × | 実在の条文を引いているが、結論または根拠が誤っている |
| 創作 | 条文に無い内容を根拠として提示した（存在しない法令名・条番号を含む） |
| 棄権 | 答えられないと述べた |

### 2段階にしなかった理由

**△ が11件出た。** 2段階だとこれが ○ か × に潰れる。

```
ts024  内容は第27条第11項と一致している / 項番号を第1項と誤記
ts034  goldの第51条・第55条は両方カバー / 第51条第1項第2号を「第2項」と記載
ts035  内容は全て正確 / 第27条第4項を「調査」とした
ts013  核心は正しい / 項番号2つ誤り（第2項→第3項、第3項→第7項）
```

**△ は修正可能な欠陥である。** × （結論が誤り）と同じ箱に入れると、
何を直せばよいか分からなくなる。

実際にこの区別が修正につながった。**△ 11件のうち4件が項番号の
誤りで、原因は `build_context` が文脈に項番号を渡していないこと**
だった（ADR-0045 に追記）。2段階で「× 11件」と記録していたら、
この原因には到達しない。

### LLM-as-a-Judge を採らなかった理由

判定には条文の原文照合が必要である。judge が条文を参照する手段は
同じコーパスを引くことで、**検索が失敗した問題では judge も
失敗する。**

```
評価対象と同じ失敗モードを持つ評価者になる
```

検索失敗9問は、まさに判定が一番難しい群である（創作7件がここに
集中している）。そこで judge が使えないなら、判定の中核で使えない。

### 創作を独立した判定にした理由

× と創作を分けたのは、**改善の投資先が違う**ためである。

```
×    実在の条文を引いている → 検索は届いた。生成の問題
創作  条文に無い内容を出した → 検索が届いていない可能性が高い
```

この分離が、下記の測定結果で最も強い観測を生んだ。

## 測定結果

判定記録は `cd9863dc-eval_human.csv`（50問×2条件）にある。

### 全体（50問）

```
            RAGあり  RAGなし
○             11       0
△             11       0
×             14       0
創作           10      50
棄権            4       0
```

○+△ = **22 / 50（44%）**。創作 **10 → 50**。

### 創作は検索の失敗の症状である

```
検索成功 36問   ○11  △11  ×12  創作 2        創作率  5.6%   ○+△ 61%
検索失敗  9問   ○ 0  △ 0  × 2  創作 7        創作率   78%   ○+△  0%
不可答   5問   棄権 4            創作 1        棄権率   80%
```

**創作率が 14倍違う。** そして検索が届かなかった9問に ○ も △ も
1問もない。

```
検索は必要条件である    届かなければ 0 / 9
検索は十分条件ではない  届いても 22 / 36
```

**この2行が本プロジェクトの評価の結論である。** 改善の投資先が
検索であることが、ここで決まる。

### 質問の形で成績が割れた

```
短答型（fact / number / negation / multi_doc）    25問  ○ 40%  ○+△ 68%
長文型（long / summary / situation / comparison） 20問  ○  5%  ○+△ 25%
```

種別別（RAGあり）。

| 種別 | ○ | △ | × | 創作 | 棄権 |
|---|---|---|---|---|---|
| fact | 4 | 2 | 1 | 3 | 0 |
| number | 2 | 2 | 0 | 1 | 0 |
| negation | 2 | 1 | 2 | 0 | 0 |
| multi_doc | 2 | 2 | 1 | 0 | 0 |
| comparison | 1 | 1 | 0 | 3 | 0 |
| long | 0 | 2 | 3 | 0 | 0 |
| summary | 0 | 1 | 4 | 0 | 0 |
| situation | 0 | 0 | 3 | 2 | 0 |
| unanswerable | 0 | 0 | 0 | 1 | 4 |

**long / summary / situation の15問で ○ が0件である。** 条文1つを
指して答える問題は4割正答するが、複数の条文を網羅・統合する問題は
1問も正答がない。

### 検索順位が回答品質を予測しなかった

```
1位     24問   ○ 5  △ 9  × 9  創作 1    ○率 21%
2位      7問   ○ 3  △ 1  × 2  創作 1    ○率 43%
3位以下   5問   ○ 3  △ 1  × 1           ○率 60%
```

**1位で引けた問題の方が ○率が低い。** 1位24問の内訳を見ると理由が
分かる。

```
1位24問の種別   summary 5 / fact 4 / negation 4 / number 3 /
                situation 3 / long 2 / multi_doc 2 / comparison 1
```

**summary と situation が8問集中している。** gold が1条で、その条が
長くチャンク分割されていれば、どのチャンクが来ても順位1位になる。
答えに必要な項は届いていないのに。

**この逆相関は検索指標の欠陥の症状である。** ADR-0047 の出発点に
なった。

### 失敗の型が9種類に分かれた

```
不足 / 逆 / 検索 / 自己矛盾 / 項番号誤り / 射程の限定 /
余計な補足 / 見出しの創作 / 法令名の創作
```

このうち**項番号誤りはコードの欠陥に帰着し、修正済みである**
（`build_context`、ADR-0045）。**見出しの創作**は条見出しを持たない
条文（消防法 0/263、食品衛生法 0/90）で起き、RAGありでは文脈内の
実在見出しを模倣する形、RAGなしでは文脈なしに起きる形の2通りが
確認された。**法令名の創作**は4型に分かれた。

```
丸ごと創作         「クーリング・オフ制度に関する法律」(ts016)
                  「賃貸借契約法」(ts046)
創作名＋括弧に本物  「建築物の防火に関する法律（建築基準法）」(ts046)
実在法の脱字       「食衛生法」(ts050)
存在しない条番号    介護保険法「第355条」(ts049、本則は第215条まで)
```

## 判定の範囲外としたもの

**枝番の内部表記は判定の対象から外した。**

回答に `第7_3条` のような内部表記（e-Gov XML の `7_3`）が現れる問題が
あったが、これは別途修正する予定だったため、判定の注記には記録して
いない。後から判定記録を読むと「見落とし」に見えるが、**既知の欠陥を
スコープ外にした判断である。**

```
10/20 の測定   16問 / 50 に内部表記
10/29 の測定   17問 / 50
10/29b（修正後） 0問
```

修正は ADR-0045（`format_number`）に記録した。

**判定記録に「この判定では見ていない項目」の欄を設けていなかった。**
次回は除外項目を先に書く。

## Consequences

* Good: **失敗を段階で切り分けられた。** 「精度が低い」ではなく
  「検索で9問、生成で26問落ちている」と言える。改善の投資先が決まる
* Good: **創作率が検索の成否で14倍違う**という観測が得られた。
  創作を生成側の性質ではなく検索の失敗の症状として説明できる
* Good: **検索指標の欠陥が症状として現れた。** 順位1位の○率が
  3位以下より低いという逆相関は、人手判定なしには見えない。
  ADR-0047 がここから出た
* Good: **条番号の文字列一致では正誤が測れないことを、具体例で示せた。**
  ts049 は、条番号を列挙するだけで「正解の条番号を含む」状態を作れる
  実例である。保存済みの jsonl で誰でも確認できる
* Good: 判定の過程で `build_context` の項番号欠落を特定し、修正した。
  **評価が設計の欠陥を見つけた**という流れが残っている
* Good: 判定の根拠を注記として同じCSVに残したため、○△×の境界が
  後から検証できる（RAGあり側）
* Bad: **盲検ではない。** 判定したのは実装者自身で、どちらがRAGありか
  見えている状態である。回答をシャッフルして条件を隠すべきだったが、
  実施していない。**バイアスを排除できていない**
* Bad: **RAGなし50件すべてが「創作」だが、根拠の注記が残っているのは
  7問だけである**（ts029, ts032, ts040, ts043, ts046, ts049, ts050）。
  残り43問は判定を再現できない。報告では、機械照合できる
  「法令番号を明示した回答 19/50、そのすべてに誤り」を根拠に置く
* Bad: **「創作」ラベルが2種類の重さを混ぜている。** ts004
  「通信販売については第12条のみ」は実在条文の内容取り違えで、
  ts046「賃貸借契約法」は法令名ごと存在しない。前者は検索成功側で
  起きており、性質が違う可能性がある
* Bad: **判定者が1人で、一致率を取っていない。** 複数人で判定して
  κ係数を出すのが筋だが、人手が無い
* Bad: **判定基準を判定開始後に固めた。** ts008 の ○ / × の境界で
  迷い、ts015 の「棄権が正しい場合」の扱いを途中で決めた。
  基準を先に文書化してから判定するべきだった
* Bad: **判定の除外項目を記録していなかった。** 枝番の内部表記を
  意図的にスコープ外としたが、注記に残していないため、後から
  見落としと区別できない
* Bad: **50問は母数が小さい。** 種別ごとは5問なので、種別別の数字は
  傾向に過ぎない。unanswerable の 4/5 も同様
* Bad: 判定に数時間かかっており、**構成を変えるたびに繰り返せない。**
  比較実験（ADR-0042）は人手判定なしで回せる検索指標で行う
* Bad: **「検索成功36問 / 検索失敗9問」の切り分けが、過大評価を含む
  Recall に依存している**（ADR-0047）。検索成功とした36問の中に、
  答えの項が届いていない問題が混ざっている
