# ADR-0014: チャンクは条単位を基本とし、上限超過時は項・号へ段階的に降りる

## Context and Problem Statement

RAG の検索対象となるチャンクを、法令XMLからどの単位で切り出すかを決める必要がある。

考慮すべき制約が2種類ある。**この2つは性質が異なる。**

**1. 技術上限**
埋め込みモデル（ruri-v3-310m / bge-m3）の最大入力長は 8,192 トークン。
これを超えた分は切り捨てられるため、超過は情報の欠落に直結する。
日本語はおおむね1文字1トークン前後のため、8,000文字程度が目安となる。

**2. 検索精度の観点からの適切なサイズ**
埋め込みはテキスト全体を1つのベクトルに圧縮する。長いチャンクほど
複数の話題が平均化され、特徴がぼやけて検索でヒットしにくくなる。
逆に短すぎると「前項の規定は」のような参照が意味を失う。
**技術上限と最適サイズは別物であり、8,192トークンは後者ではない。**

`MainProvision` 配下の `Article` について、テキスト抽出・正規化後の
文字数分布を測定した（暫定値。後述の制約あり）。

| 区間 | 件数 | 割合 |
|---|---|---|
| 〜500 | 407,869 | 74.0% |
| 501〜1,000 | 83,287 | 15.1% |
| 1,001〜2,000 | 37,861 | 6.9% |
| 2,001〜5,000 | 16,796 | 3.0% |
| 5,001〜8,000 | 2,887 | 0.5% |
| 8,001〜 | 2,620 | 0.5% |

最大は 246,498 文字（普通交付税に関する省令 第12条）。
8,001文字超2,620件の構成を調べたところ、1条あたり平均で `Sentence` 156個、
`TableColumn` 40個、`Item` 38個、`Column` 32個、`Paragraph` 25個、`Subitem1` 18個。
長さの原因は自然文ではなく**構造化された項目の量**であった。

分割単位を降りた場合の最大文字数は以下のとおり。

| 単位 | 最大文字数 |
|---|---|
| 条（Article） | 246,498 |
| 項（Paragraph） | 235,844 |
| 号（Item） | 33,627 |

号まで降りると、8,000文字を超えるものは 22 件まで減少する。

## Decision Drivers

* 法令を扱うため、意味を壊す分割は誤った回答に直結する
* チャンクの境界が出典の単位と一致していること（根拠提示が主機能のため）
* 技術上限を超えて情報が切り捨てられないこと
* 断片化しすぎると、チャンク単体では文脈が失われ根拠として使えない

## Considered Options

1. 固定文字数（200〜500文字程度）で機械的に分割する
2. 条単位で固定し、上限超過分は切り捨てる
3. 最初から項または号の単位で一律に分割する
4. 条を基本とし、上限を超えた場合のみ項・号へ段階的に降りる

## Decision Outcome

Chosen option: "条を基本とし、上限を超えた場合のみ項・号へ段階的に降りる"

### なぜ条を基本単位とするか

**1. 条は立法時に設計された意味の単位である**

法令の条は、一つの規範・定義・手続きを表す単位として立法段階で区切られている。
機械的な文字数分割と違い、**区切りの妥当性を人間が保証済みの境界**である。

**2. 出典の単位と一致する**

法令を引用する標準形式は「◯◯法第◯条」であり、条が引用の最小単位となる。
本プロダクトは根拠となる条文を出典つきで提示することを中核とするため、
チャンク境界と出典境界が一致していれば、検索結果をそのまま根拠として提示できる。
固定文字数で分割すると「第◯条の途中から◯文字」という提示不能な単位になる。

**3. 条内参照が閉じる**

法令には「前項の規定は」「前条に規定する」といった相対参照が頻出する。
実データでも `印紙犯罪処罰法` 第二条第二項に「前項ノ未遂罪ハ之ヲ罰ス」を確認した。
項単位で切ると参照先がチャンク外になり、単体では意味をなさない。
条単位であれば「前項」参照は同一チャンク内で解決する。

**4. 実測分布が条単位と整合する**

測定では約74%の条が500文字以下、96%が2,000文字以下であった
（ただし後述のとおり暫定値）。多くの条が、追加の分割なしに
検索に適したサイズへ自然に収まる。

### 他の選択肢を採らない理由

選択肢1（固定文字数）は、上記2の理由により出典として提示できない単位を生む。
法令を扱う本プロダクトでは採用できない。

選択肢2（切り捨て）は情報の欠落を招く。法令の条文が途中で失われることは許容できない。

選択肢3（一律に項・号）は、96%を占める2,000文字以下の条まで不必要に分割し、
条単位で完結している意味のまとまりを壊す。号単位では1チャンクが
数十文字の断片になる場合があり、単体では文脈が失われる。

### 閾値の扱い

分割を発動する閾値は、**技術上限（8,192トークン）ではなく、
検索精度から決定すべき値**である。現時点でその値は未確定であり、
第3週のチャンク設計で以下を同一の評価データで比較し、実験的に決定する。

* 条単位（分割なし、技術上限のみで発動）
* 条単位＋閾値を変えた段階分割（複数パターン）
* 項単位で一律
* 固定文字数＋オーバーラップ

それまでは暫定的に 8,000 文字を閾値として実装を進める。

### 上限を超える場合の扱い

号まで降りてもなお超過するもの（暫定で22件）については、
文字数による機械的分割を適用する。精度低下を抑えるため、
上限手前で直近の句点（「。」）を探して分割位置とする。

全チャンクに、法令名・法令ID・沿革ID・条番号・条見出し・
本則/附則の区別をメタデータとして付与し、分割された場合でも
出典と位置が特定できる状態を保つ。

### Consequences

* Good: チャンク境界が出典の単位と一致し、検索結果をそのまま根拠として提示できる
* Good: 区切りの妥当性が立法段階で保証されており、意味の途中で切れない
* Good: 条内の相対参照（「前項」等）がチャンク内で解決する
* Good: 情報の切り捨てが発生しない
* Bad: 分割ロジックが階層的になり、実装が複雑になる
* Bad: 同一の条が複数チャンクに分かれた場合、検索で一方だけがヒットして
  文脈が欠ける可能性がある
  → メタデータの条番号により、同一条の他チャンクを取得できる設計とする
* Bad: 条単位でも2,000文字を超えるものが4%あり、検索精度の観点では
  大きすぎる可能性がある。閾値の実験結果によっては方針の見直しが必要
* Bad: **本ADRの測定値はすべて暫定である。** 測定に用いた10,702ファイルには
  同一法令の複数バージョンが含まれており（ユニークな法令IDは8,997）、
  条の件数・文字数分布・超過件数はいずれも重複を含む。
  地方税法（33版 × 1,348条 = 約44,000件）だけで全体の約8%を占めるため、
  重複排除後に分布が変動する可能性がある。
  **重複排除の方法を決定した後、再計測してから本ADRを accepted に更新する。**
* Bad: 「8,000文字」は文字数からの概算であり、実トークン数はモデルの
  トークナイザに依存する。埋め込みモデル選定後に再計算する
