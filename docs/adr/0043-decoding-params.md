# ADR-0043: デコーディングパラメータはモデル提供元の推奨値を使い、set_seed で固定する

## Context and Problem Statement

生成の評価（ADR-0044）を始める前に、`model.generate` に渡す
パラメータを決める必要があった。

```python
gen_params = {
    'max_new_tokens': ?,
    'do_sample': ?,
    'temperature': ?,
    'top_p': ?,
    'top_k': ?,
}
```

**この値によって生成結果が変わる。** RAGあり/なしの比較を
するのだから、パラメータ起因の差が混ざると比較が成立しない。

パラメータを選ぶために、自作のベンチマークで **193構成**を測定した。
しかし**どの構成の回答が良いかを判定する手段がなかった。**
速度と出力長は測れたが、品質は測れていない。

## Decision Drivers

* **比較実験の土台である。** RAGあり/なしで同一でなければならない
* **再現性が要る。** ADR-0042 で検索側のばらつきを抱えているため、
  生成側で新たなばらつきを足したくない
* **打ち切りを出さない。** 根拠の条番号が出力の途中で切れると、
  引用の有無を判定できない
* 品質で選びたいが、品質を測る手段がない

## Considered Options

1. **Qwen3-8B 非思考モードの推奨値 + `set_seed` で固定**
2. 自作ベンチマーク（193構成）の結果から選ぶ
3. `do_sample=False`（greedy decoding）で完全決定的にする

## Decision Outcome

Chosen option: **「推奨値 + `set_seed`」**

```python
gen_params = {
    'max_new_tokens': 2048,
    'do_sample': True,
    'temperature': 0.7,
    'top_p': 0.8,
    'top_k': 20,
}
```

### 193構成を測ったが、品質で選べなかった

自作ベンチマークで `greedy` / `temperature` / `top_p` / `top_k` / `repetition_penalty` の組み合わせを
193通り測定した。得られたのは生成時間と出力トークン数である。

**「どの設定の回答が法令アシスタントとして良いか」は、
自動では判定できなかった。** 正誤判定には人手か LLM-as-a-Judge が
必要で、193構成分の判定は現実的でない。

よって**選定の根拠にできなかった。** 測定そのものは無駄ではなく、
「測ろうとして、測れないと分かった」という記録として残る。

採用したのはモデル提供元（Qwen）が非思考モードに対して示している
推奨値である。**自分で決められない部分を、学習時の想定に合わせた。**

### 思考モードは無効にした

Qwen3 は thinking モードを持つが、無効にした。

* 思考を有効にした場合、**試した問題で全問不正解だった**
* 英語で推論して日本語で答える挙動になる
* `<think>` タグは `skip_special_tokens=True` でも**残る**（実測）。
  `re.sub(r'<think>.*?</think>', '', text, flags=re.DOTALL)` で
  除去する必要がある
* 推論部分が出力トークンを消費するため、打ち切りの risk が上がる

### max_new_tokens は実測で決めた

当初 512 で回したところ、**50問中19問（38%）が打ち切られた。**
根拠の条番号が出力の途中で切れるため、引用の有無を判定できない。

2048 に変更して 0/50 になった。

| | 打ち切り | 出力トークン中央値 | 最大 |
|---|---|---|---|
| 512 | 19 / 50 | — | 512 |
| 2048 | **0 / 50** | 413 | 1149 |

最大が 1149 なので **1536 でも足りた。** 2048 にしたのは余裕を
見たためで、最適化していない。打ち切られた場合の判定不能を
避けることを優先した。

なお RAGなしでは 2048 でも **2問が打ち切られた**（ADR-0044）。
文脈がないと出力が長くなるため、同じ上限でも挙動が変わる。

### set_seed はループの中で呼ぶ

ここが最も重要な実装上の判断である。

```python
for eval_id, row in eval_set.items():
    ...
    set_seed(42)          # ← ループの中
    generated = llm.generate(...)
```

**`set_seed` は乱数の「状態」を設定する。値ではない。**
ループの外で1回だけ呼ぶと、状態が次の問題に繰り越される。

```
ループ外で1回:
  問題1 の出力長が1トークン変わると、問題2 以降の全問がずれる
  
ループ内で毎回:
  どの問題も同じ乱数の状態から始まる
```

検索結果が実行ごとに変わる（ADR-0042）ため、**ある問題の出力長が
変わることは日常的に起きる。** ループ外に置くと、1問の変化が
以降の全問を汚染する。

この挙動は「同じシードなら全部同じ乱数になるのではないか」という
直感に反する。実際に小さなコードで確かめて確認した。

## Consequences

* Good: **193構成を測った上で推奨値を採用している。** 「推奨値を
  使いました」ではなく「測ろうとしたが品質を判定できなかったので
  学習時の想定に合わせた」と説明できる
* Good: `set_seed` の位置による汚染を**実証して回避した。**
  ループ外に置いたままなら、ADR-0042 の再現性調査の結論も
  歪んでいた可能性がある
* Good: set_seed による出力の固定を実測で確認済み。同一シードで2回生成し、
  テキストが一致することを確かめた上で評価に使っている
* Good: `max_new_tokens` を実測（38%打ち切り）で決めている。
  勘で決めていない
* Good: 思考モードを**試した上で**無効にしている。
  `<think>` の除去が必要という実装上の発見も残っている
* Bad: **品質で選んでいない。** 推奨値が本プロジェクトの
  法令質問応答にとって最適である保証はない。193構成のデータは
  速度と長さの情報しか持たない
* Bad: **`do_sample=False`（greedy）を試していない。** greedy なら
  サンプリングがないため `set_seed` が不要で、完全に決定的になる。
  評価の再現性を最優先するなら、こちらの方が筋が通っていた可能性が
  ある。温度を入れた理由は「推奨値がそうだから」であり、
  評価用途として検討していない
* Bad: RAGなしで**2件の反復ループ**が発生した（同一文を2048
  トークンまで繰り返す）。`repetition_penalty` や `no_repeat_ngram_size`
  で緩和できた可能性があるが、検証していない
* Bad: `gen_params` が `evaluate_generation.py` にハードコードされている。
  本番構成の一部なので `config.py` に出すべきだが、残り日数の都合で
  後回しにした
* Bad: `max_new_tokens = 2048` は余裕を見た値で、1536 で足りていた。
  打ち切りが0になった時点で探索を止めている
