# ADR-0001: 法令データの初期取得に XML一括ダウンロードを採用し、更新は差分検知で行う

## Context and Problem Statement

本プロダクトは全法令（10,702件）を検索対象とする。取得方法として e-Gov 法令API v2 の
`/law_data` を法令IDごとに呼び出す方法と、XML一括ダウンロードを用いる方法がある。

デジタル庁は「法令APIプロトタイプ公開テスト（第3回）」（2025年1月、現在は終了）の利用規約において、
全法令をループして条文データを順次取得する利用方法はサーバリソースの負担となり
他の利用者にも影響が生じうるため控えるよう求め、一括取得が必要な場合は
XML一括ダウンロードの利用を案内していた。

なお当該規約は試験環境を対象としたものであり、正式版 API の規約に同じ記述があるかは未確認。
ただしサーバ負荷の観点は正式版でも同様と考えられる。

## Decision Drivers

* 公的APIの提供者に過度な負荷をかけないこと
* 法改正への追従が本プロダクトの主機能であり、更新の仕組みが必要なこと
* 開発期間が限られており、初期構築を短時間で終えたいこと

## Considered Options

1. 法令APIを法令IDごとにループ呼び出しして全件取得する
2. XML一括ダウンロードで初期構築し、以降もダウンロードし直す
3. XML一括ダウンロードで初期構築し、更新は差分検知でAPIから取得する

## Decision Outcome

Chosen option: "XML一括ダウンロードで初期構築し、更新は差分検知でAPIから取得する", because
一括ダウンロードは提供者が推奨する取得方法であり、初期構築のコストも最小で済む。
一方で更新のたびに約300MBを再取得するのは非効率であり、
`/laws` が返す `law_revision_id` および `updated` を保持済みの値と比較すれば
変更のあった法令のみを特定できるため、APIの呼び出しを最小限に抑えられる。

差分更新は本プロダクトの主機能（法改正の検知）そのものであり、
この仕組みを持つこと自体が要件を満たす。

### Consequences

* Good: 提供者の推奨に沿った取得方法となり、サーバ負荷を抑えられる
* Good: 更新処理が主機能（改正検知）と同一の仕組みになり、実装が二重にならない
* Good: `amendment_scheduled_enforcement_date` を用いれば未施行の改正も先回りで通知できる
* Bad: 一括ダウンロードと API でデータ形式が異なる（XML / JSON）ため、
  内部表現をどちらかに統一する処理が別途必要になる
* Bad: 一括ダウンロードは自動更新されないため、初期構築後の鮮度は差分更新の実行頻度に依存する
* Bad: 根拠とした規約が終了した試験環境のものであり、正式版の規約確認が残課題として残る
