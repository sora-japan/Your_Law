# ADR-0050: 埋め込みに渡す文字列に、法令名と改正法令番号を前置する

## Context and Problem Statement

同一のテキストを持つチャンクは**同一のベクトルになる**。短い定型文は
「どの質問からも中くらいの距離」に位置するため、本来の正解より近ければ
上位を占拠する。ADR-0048 で入れた検品が、これに引っかかった。

```
検査2 失敗: 異なる質問が全く同じ検索結果を返しています
            ts023（建築基準法の検査申請期限）と ts024（要介護認定の処分期限）

返ってきた10件   電波法施行規則、距離 0.1701（10件すべて同じ）
                 text = 'この省令は、公布の日から施行する。' 17文字
```

### 再現性の揺れとの関係

[ADR-0042](0042-retrieval-reproducibility.md) で「同一設定で Recall@10 が 0.070 動く」
と記録し、[ADR-0048](0048-corpus-persistence.md) で「原因の特定ではなく回避である」
と書いた問題がある。

同一ベクトルは距離が同点になるため、**どれが上位に来るかが実行ごとに変わりうる。**
揺れが起きる機構としては説明がつく。

**ただし、0.070 の全部がこれで説明できるとは言えない。**
重複を直したうえでコレクションを2回構築し、揺れが消えるかを測るまでは未確定である。

なお、保存済みのコレクションに対してクエリを2回投げると、
MRR@100 が 0.5932493824755001 で16桁まで一致する。
**揺れていたのは構築の側であって、検索の側ではない。**

### 原因は、埋め込みに本文しか渡していないこと

```python
documents = [chunk['text'] for chunk in chunks]   # db.add_chunks
```

`law_title` はメタデータにあるが、**ベクトルには一切反映されていない。**
だから別の法令の同じ定型文が、区別できない同じベクトルになる。

### チャンクに文脈を前置する手法は知られている

チャンクの前に文脈を足してから埋め込む方法は Contextual Retrieval として
公開されている。本家は文脈を LLM に生成させるが、
**本プロジェクトは法令名・改正法令番号・条見出しがメタデータに揃っているため、
LLM を使わず決定的に作れる。** 生成コストがかからず、実行ごとにぶれない。

## Decision Drivers

* 同一ベクトルによる上位の占拠をなくすこと
* 埋め込みに乗る文字列が、検索の役に立つ情報であること
  （記号列を足して重複だけ消す、という形にしない）
* 全チャンクを埋め込み直すため、どこまで必要かを**事前に見積もれること**
* 再現可能であること。LLM 生成だと実行ごとに文脈が変わる

## Considered Options

1. 索引から重複チャンクを削除する
2. **本文の前に「法令名」を置く**
3. **本文の前に「法令名 ＋ 改正法令番号」を置く**
   （`law_title` と、附則が持つ `amend_law_num`。本則には `amend_law_num` が無いので空になる）
4. 本文の前に「法令番号」を置く
5. 本文の前に「法令ID」を置く
6. 検索後・プロンプト組み立て前に、同じ本文を1件に畳む

## Decision Outcome

Chosen option: **「本文の前に『法令名 ＋ 改正法令番号』を置く」**

`scripts/compare_embed_text.py` で、コレクションを作る前に3案を比較した。
閾値2000・現行版の全件 601,299 チャンクで測定している。

「種類の数」は2回以上出てくる文字列が何通りあるか、
「重複するチャンク数」はそれらの文字列を持つチャンクの合計、
「削減可能数」は種類ごとに1件だけ残したときに消える数を指す。

| | ユニーク数 | 種類の数 | 重複するチャンク数 | 削減可能数 |
|---|---|---|---|---|
| 本文のみ（現状） | 427,948 | 19,947 | 193,298（32.1%） | 173,351（28.8%） |
| ＋法令名 | 568,437 | 10,694 | 43,556（7.2%） | 32,862（5.5%） |
| ＋法令名＋改正法令番号 | **601,188** | **107** | **218（0.04%）** | **111（0.02%）** |

**法令名だけでは 32,862 件が残る。** 同じ法令の中に同じ文面の附則が複数あると、
法令名を足しても分かれないためである。改正法令番号まで入れると 111 件になる。

### 測定の妥当性

「本文のみ」の行が、ADR-0042 の追跡時に記録した数字と完全に一致した。

```
総数 601,299 / ユニーク 427,948 / 種類 19,947 / 重複 193,298 / 削減可能 173,351
```

書き直したスクリプトが、同じものを測れていることの確認になる。

### 法令名は一意ではなかった

残った重複の出どころを見たところ、**大半が「別々の法令なのに法令名が同じ」**だった。

```
国民年金法等の一部を改正する法律の施行に伴う経過措置に関する政令
  361CO0000000054   昭和61年政令第54号
  401CO0000000337   平成元年政令第337号
  406CO0000000348   平成6年政令第348号
```

同じ名前の政令が3本あり、3本とも同じ改正政令で改正されているため、
同じ附則を持っている。省令でも、府省が違う同名のものが3本あった。

**法令を一意に識別できるのは `law_id` だけで、法令名ではない。**
（`law_id` はファイル名の先頭部分。1つの法令に版ごとのファイルがあるため
ファイルに対しては一意でないが、`find_current_version_paths` が法令ごとに
1版だけ選ぶので、読み込んだチャンクの中では法令と1対1になる）
選択肢5（法令IDを置く）なら
確実に分かれるが、`361CO0000000054` は埋め込みモデルにとって意味のない記号列で、
検索の役に立たない。選択肢4（法令番号）は人が読める形で一意だが、
**0.04% のために全チャンクを15文字ほど長くする**ことになる。

### 残る111件の内訳

上位10件を見たところ、3パターンで説明できた。

```
(1) 法令名が重複（law_id が違う）              10件中7件
(2) 項・号が前置に入っていない                  2件
    所得税法施行令 第185条 第1項第七号 / 第2項第七号
(3) 分割後の断片が一致（別表の反復）            1件
    地方税法施行規則 附則 第9項 の Split 断片
```

(2) は条見出しだけが text に入り、項番号と号番号は入らないため。
これも前置を増やせば消えるが、同じ理由で採らない。

選択肢1（索引から削除）は、**残った1件が別の法令のものになる**ため採らない。
「どの法令の施行日規定か」を聞かれたときに答えられなくなる。

選択肢6（検索後に畳む）は、検索して上位k件を取ったあと、プロンプトを
組み立てる前に同じものを1件にまとめる案である。索引を触らないので、
必要になった時点で後から足せる。

ただし**畳む基準を「本文が同じ」にすると、選択肢1と同じ問題が起きる。**
電波法施行規則と建築基準法施行規則の施行日規定が1件にまとまり、
どちらの話か分からなくなる。畳むなら「法令名も本文も同じもの」に限る必要がある。
そこまで絞れば、残る111件のような「同名の法令の同じ条文」だけが対象になる。

### 前置後の実測（ベクトル検索のみ）

同じ 50,055 チャンクに対して、埋め込みだけを差し替えて測った。
サブセットの選び方は `SUBSET_SEED` で固定しているため、対象は完全に同じである。

| 条文型40問 | MRR@100 | Recall@1 | Recall@5 | Recall@10 | Recall@20 | Recall@100 |
|---|---|---|---|---|---|---|
| 前置なし | 0.5932 | 0.4375 | 0.7000 | 0.7375 | 0.7375 | 0.8875 |
| 前置あり | **0.7516** | **0.5875** | **0.8625** | **0.9000** | **0.9500** | **0.9750** |

**9列すべてで上がった。** Recall@100 の +0.088 は
「今まで候補100件にすら入らなかった正解が入るようになった」ことを意味し、
Recall@1 の +0.150 は順位の改善である。**両端が同時に動いた。**

```
前置前  ハイブリッド＋リランキング  Recall@10 = 0.8750   検索49.5ms + リランク2,624.6ms
前置後  ベクトル検索のみ            Recall@10 = 0.9000   検索24.3ms
```

**ベクトル検索だけで、前置前のリランキング込みを上回った。**
Recall@1 は前置前のリランキング（0.6875）がまだ上なので、リランカーの役目は残る。

状況型5問は、上位と下位で逆の動きをした。

| 状況型5問 | MRR@100 | Recall@1 | Recall@10 | Recall@20 | Recall@50 | Recall@100 |
|---|---|---|---|---|---|---|
| 前置なし | 0.6195 | 0.3000 | 0.4000 | **0.7000** | **0.8000** | **0.8000** |
| 前置あり | **1.0000** | **0.4667** | **0.5667** | 0.5667 | 0.6667 | 0.7333 |

**MRR が 1.0 になった。5問すべてで1位に gold の法令が来ている。**
Recall@1 の 0.4667 は、gold が2〜3法令あることから計算される理論上の天井と一致する。

一方 Recall@20 以降は下がった。法令名が効いて1つの法令のチャンクが上位を占め、
**2つ目・3つ目の gold 法令を押し出している**と読めるが、5問なので断定はできない。

## Consequences

* Good: **同一ベクトルによる占拠が実質なくなる。** 削減可能数が 173,351 → 111 で、
  規模が3桁違う。10,341件が上位10件を埋めるという事故は起きなくなる
* Good: **法令名が埋め込みに乗る。** 「介護保険の申請期限」のような質問に対して、
  介護保険法のチャンクだという情報がベクトルに入る。重複とは独立した改善
* Good: **BM25 の索引にも法令名が入る。** 法令名をそのまま含む質問が引けるようになる
* Good: **プロンプトにも法令名が乗る。** 生成LLMが、どの法令の条文かを見られる
* Good: **LLM を使わないので費用ゼロで、実行ごとにぶれない。** メタデータから
  決定的に作れる
* Good: **コレクションを作る前に効果を見積もれた。** 作ってから測ると
  8分＋評価10分が1回の試行にかかる。文字列を数えるだけなら数分で済む
* Bad: **測ったのはベクトル検索だけ。** BM25・ハイブリッド・リランキングの3方式は未測定。
  リランカーに渡る候補が変わるため、組み合わせたときの効きは別に確かめる必要がある
* Bad: **状況型で Recall@20 以降が下がった。** 5問なので傾向とは言えないが、
  上位に集中して裾が痩せる動きが出ている。原因の確認をしていない
* Bad: **全チャンクの埋め込みをやり直すことになる。** 閾値200/1000の比較実験も
  取り直しになる
* Bad: **111件は残る。** 0.02% なので許容したが、ゼロではない
* Bad: **`amend_law_num` が空のとき、区切りが2つ並ぶ。**
  `'教科用図書検定規則  （趣旨）第一条…'` のような形になる。本則は全部空なので
  31万件が該当する。
* Bad: **法令名が一意でない状態は残る。** 同名の法令を名前だけで区別することは
  できない。これは前置の設計ではなく、法令データ側の性質である
* Bad: **閾値1000での重複率を測っていない。** ADR-0042 の記録と比較するため
  閾値2000で測った。本番の閾値1000では数字が変わる
* Bad: 前置する文字列を `chunk['text']` に入れるか、埋め込み用に別フィールドを
  持つかを決めていない。BM25 とプロンプトへの影響が変わる
