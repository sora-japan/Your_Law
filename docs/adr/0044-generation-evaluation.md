# ADR-0044: 生成の評価は RAGあり/なしを同一コードで回し、失敗段階を切り分ける

## Context and Problem Statement

検索の評価（ADR-0037）は Recall@k と MRR で測れていた。しかし
**「検索が当たったあと、モデルがそれを使えているか」は測れていない。**

検索で正解が10件の中に入っていても、モデルがそれを無視して
別のことを答えれば、利用者にとっては失敗である。逆に検索が外れた
とき、モデルが黙るのか、記憶から創作するのかで被害が全く違う。

さらに、ポートフォリオとして示したいのは**「RAGを入れた効果」**である。
効果を示すには、入れていない状態との対比が必要になる。

## Decision Drivers

* **RAG以外のすべてが同一でなければならない。** 生成パラメータや
  プロンプトの加工が片方だけ違うと、比較が主張を失う
* **検索のばらつき（ADR-0042）を比較に持ち込みたくない**
* 50問×2回の生成に約1時間かかる。やり直しの回数を減らしたい
* 残り日数が限られている

## Considered Options

1. **1ファイルに `USE_RAG` 定数を置き、両モードを同一コードで回す**
2. RAGなし用に別のスクリプトを作る
3. RAGありだけ測り、RAGなしは定性的な例示で済ませる

## Decision Outcome

Chosen option: **「`USE_RAG` 定数で1ファイルに閉じ込める」**

### ファイルを分けなかった理由

**比較が成立する条件は「RAG以外のすべてが同一」である。**

ファイルを分けると、片方の `gen_params` を直す、`set_seed` の位置が
片方だけずれる、といった差分が**静かに入る。** 「生成パラメータが
違ったのではないか」と疑われた時点で、比較の価値は失われる。

1ファイルなら、差分が `if` の中だけに閉じ込められる。
**「ここ以外は同じコードが走っている」と言える。**

分岐は4箇所だが、**ループ内に必要なのは1つだけ**である。

```
ループ前  : コーパス構築の有無 / システムプロンプト / 出力ファイル名
ループ内  : 検索と文脈組み立て、または context=None
ループ後  : 集計（測る指標そのものが違う）
```

### gold_law_ids は分岐の外に置いた

実装の途中で判断を変えた箇所である。

当初 `gold_law_ids` は RAGあり側だけで作っていた。しかし
**「この質問は答えられるか」は検索とは無関係**で、評価データ側の
属性である（`row['gold']` が空かどうか）。

そして**RAGなしでもこれが必要だった。** 不可答5問にRAGなしで
どう答えたかが、この比較の見どころの一つである。記録に無いと、
後からどの5問かを特定できない。

```
共通    : id, category, gold_law_ids
RAGのみ : rank, recall, retrieved_chunk_ids
```

### 集計は「守る」のではなく「分ける」

RAGなしのとき `rank` と `recall` に `None` を入れて `if` で
守る形を最初に考えたが、採らなかった。

**RAGなしに Recall@10 と MRR は存在しない。** 検索していないため
計算の対象がない。一方で意味を持つ指標は残っている（棄権、
打ち切り、生成時間、条番号の創作）。

`None` を避ける防御ではなく、**測るものが違う**という理解に
変えたため、集計はブロックごと分岐した。

### 記録項目は4つに絞った

`llm.generate` の戻り値。

| 項目 | 用途 |
|---|---|
| `text` | 正誤判定、条番号の引用判定 |
| `output_token` | 打ち切りの原因分析、レイテンシの内訳 |
| `token_limit` | 打ち切りの検出（`>= max_new_tokens`） |
| `generation_time` | レイテンシ |

**テンソルは返していない。** JSON化できず、GPUメモリを保持し続け、
ライブラリの内部表現が呼び出し側に漏れる。デコード済みの
テキストとスカラー4つで足りる。

`token_limit` は `>=` である。`>` は常に偽になる
（生成は `max_new_tokens` で正確に止まるため）。

**`cites_gold`（正解の条番号を引用したか）は記録に入れていない。**
これは `text` から後で計算できる。判定ルールは今後変わるため、
生成時に固定すると**ルールを直すたびに生成をやり直す**ことになる。

```
生成  : 高コスト（50問で25分）・再現不能 → 保存する
評価  : 低コスト・何度でも → 後から計算する
```

**この判断が後で効いた。** `cites_gold` が信頼できないと分かり
（ADR-0046）、人手判定に差し替えたが、再生成は不要だった。

## 測定結果

### 旧版の数字（`cites_gold` による自動判定）は撤回する

旧版はこの表を主たる測定結果として掲げていた。

| | 問数 | 意味 |
|---|---|---|
| 検索OK / 引用OK | 29 | 成功 |
| 検索OK / 引用なし | 4 | 生成の失敗 |
| 検索NG / 引用なし | 7 | 検索の失敗 |
| 検索NG / 引用OK | 0 | — |

この 29 / 4 / 7 / 0 は `cites_gold` の出力である。

```python
re.search(f'第{article_num}条', text)
```

**回答テキストに `第N条` という文字列が現れるかを見ているだけで、
法令名も項も内容も照合していない。** ADR-0046 で欠陥を具体例つきで
示した（ts049 が条番号を140個列挙して `cites_gold` を満たしうる例）。

### 旧版の解釈が誤っていた

旧版はこの表からこう書いた。

```
検索が届かない7問 → 0問。記憶からの創作が1件もない
```

**これは誤りである。** `cites_gold` が偽であることは
「**正しい**条番号を引用しなかった」を意味するだけで、
「何も創作しなかった」ではない。

人手判定（ADR-0046）の結果:

```
検索失敗 9問   ○ 0  △ 0  × 2  創作 7      創作率 78%
```

**検索が届かなかった問題では、7件が創作だった。** 旧版は
「創作が1件もない」と書いていた。**正反対である。**

```
cites_gold = False の意味
  旧版の読み   創作していない
  正しい読み   正しい条番号を引用していない（間違った条番号を創作しているかは不問）
```

**指標が測っていないことを、測ったように読んでいた。** これが
人手判定に切り替えた直接の理由である（ADR-0046）。

### 人手判定による測定結果（50問）

```
            RAGあり  RAGなし
○             11       0
△             11       0
×             14       0
創作           10      50
棄権            4       0
```

○+△ = **22 / 50（44%）**。創作 **10 → 50**。

検索の成否で分けると、創作率が14倍違う。

```
検索成功 36問   ○11  △11  ×12  創作 2        創作率  5.6%   ○+△ 61%
検索失敗  9問   ○ 0  △ 0  × 2  創作 7        創作率   78%   ○+△  0%
不可答    5問   棄権 4            創作 1        棄権率   80%
```

```
検索は必要条件である    届かなければ 0 / 9
検索は十分条件ではない  届いても 22 / 36
```

**旧版の「検索で7問、生成で4問落ちている」は、「検索で9問、
生成で26問落ちている」に修正される。** 投資先が検索であることは
変わらないが、生成側の失敗が旧版の6倍以上ある。

詳細（種別別、失敗の型9種類、法令名の創作4型）は ADR-0046 に置く。

### RAGあり/なしの対比（機械的に測れる指標）

| | RAGあり | RAGなし |
|---|---|---|
| 不可答5問の棄権 | **4 / 5** | **0 / 5** |
| 打ち切り | 0 / 50 | 2 / 50 |
| 出力トークン合計 | 22,167 | 35,665 |
| 出力トークン中央値 | 413 | 687 |
| スループット | 14.49 tok/s | 17.90 tok/s |
| 合計生成時間 | 1529.5秒 | 1992.3秒 |

**棄権が 4/5 から 0/5 になった。** RAGなしでは5問すべてで条番号を
提示している。内容は次のとおりである。

| ID | 提示した根拠 | 問題 |
|---|---|---|
| ts016 | 「クーリング・オフ制度に関する法律」 | **そのような法律は存在しない** |
| ts043 | 「介護報酬の算定基準（昭和59年告示第148号）」第2条第1項 | 介護保険法は平成9年。昭和59年の介護報酬告示は存在し得ない |
| ts045 | 最高裁昭和63年7月15日判決（民集10巻3号118頁） | **巻号が矛盾している。** 民集10巻は昭和31年頃 |
| ts015 | 2018年の行政処分事例を具体的に記述 | 事例の捏造 |
| ts044 | 「定めているものはありません」と述べた後、一般的な基準を説明 | 部分的に棄権したが答えてしまった |

可答問題でも法令番号の捏造が起きている。ts001 は特定商取引法を
**「平成10年法律第65号」**と記述した。正しくは昭和51年法律第57号で、
評価データの `gold_law_ids`（`351AC0000000057`）と一致する。
さらに第2条第1項の条文を創作して引用符つきで提示した。
**法令番号を書いた回答は19/50あり、すべて照合可能な捏造箇所である。**

**RAGなし側の報告は、この機械照合可能な数字を根拠に置く。** 人手判定で
RAGなし50件すべてを「創作」としたが、根拠の注記が残っているのは7問だけで、
残り43問は判定を再現できない（ADR-0046）。

### 打ち切り2件はいずれも生成の崩壊だった

```
ts049: …第313条、第314条、第315条、…第355条、（2048トークンまで）
ts017: その者が65歳に達する日からその日までの間に、（同一文の反復）
```

**「回答が長い」のではなく、反復ループに陥っている。**
両方とも115秒かけて意味のない列挙を続けた。RAGありでは0件である。

### レイテンシの内訳

直感に反する結果が出た。**文脈を1万トークン入れた方が速い。**

```
1トークンあたり : RAGありが19%遅い（文脈分のattentionコスト）
出力トークン数   : RAGありが37%少ない
   → 合計時間はRAGありが23%速い
```

**トークン単価は高いが、買う量が少ない。** 根拠がないとモデルは
長く書く。文脈があれば「第17条により〜です」で終わる。

ただし**問題単位で逆転しているのは32/50**であり、「常に速い」では
ない。出力が長い方が長いのは41/50。

### プロンプト修正後の再測定（10/29）

ADR-0045 の修正（項番号・枝番）の後、RAGありを再測定した。

| | 10/20 | 10/29 |
|---|---|---|
| 出力トークン合計 | 22,167 | 22,869 |
| 出力トークン中央値 | 413 | 370 |
| 出力トークン最大 | 1,149 | 1,501 |
| 合計生成時間 | 1529.5秒 | 1582.3秒 |
| スループット | 14.49 tok/s | 14.45 tok/s |

**文脈が伸びた分の prefill コストは、測れるほど出ていない。**
合計時間の +3.5% は出力トークンの +3% でほぼ説明がつき、
スループットはほぼ同じである（14.49 → 14.45）。

項番号を文脈に加えたことで文脈は長くなったが、**スループットへの
影響は観測できなかった。** スループットは micro 平均（合計トークン ÷
合計時間）で計算している。

## Consequences

* Good: **失敗を段階で切り分けられた。** 「精度が低い」ではなく
  「検索で9問、生成で26問落ちている」と言える。改善の投資先が決まる
* Good: **`cites_gold` を生成時に固定しなかったため、判定ルールを
  人手判定に差し替えても再生成が不要だった。** 「高コストで再現不能な
  ものだけ保存し、安いものは後から計算する」という切り分けが実際に効いた
* Good: **答えられない質問への挙動を測っている。** 棄権率を
  指標に入れているRAG評価は多くない。4/5 → 0/5 という明確な差が出た
* Good: **レイテンシの直感を実測で覆した。** 「RAGは遅い」に対し
  トークン単価と出力量に分解して答えられる
* Good: 比較の前提（RAG以外は同一コード）を構造で保証している。
  `USE_RAG` の3行を読めば差分が分かる
* Good: **自動指標の読み違えを、具体例つきで訂正した。**
  `cites_gold = False` を「創作していない」と読んでいた。
  正しくは「正しい条番号を引用していない」で、**間違った条番号を
  創作しているかは不問**だった。指標が測っていないことを測ったように
  読む失敗の実例として残る
* Bad: 29/4/7/0 を算出したコードがリポジトリに存在しない。
  当時その場で計算してファイルに残さなかったため、この数字は再現できない。
  ADR-0042 の「証跡なしの 0.752」と同じ型の失敗である
* Bad: **旧版の主たる測定結果（29/4/7/0）を撤回した。** 1回の実行の
  自動判定に基づいており、解釈も誤っていた。**数字を出す前に、
  その数字が何を測っているかを確認していなかった**
* Bad: **評価者が条件を知っている。** 判定を行うのは実装者自身で、
  どちらがRAGありか見えている状態である。回答をシャッフルして
  盲検にすべきだが、実施していない。**バイアスを排除できていない**
* Bad: **検索時間を計測していない。** `generation_time` は
  `model.generate` のみを挟んでおり、クエリの埋め込みと HNSW 探索の
  時間が含まれない。「RAGにすると1問あたり何秒増えるか」を
  システムとして言うには不足している
* Bad: **検索のばらつき（ADR-0042）がこの数字にも乗っている。**
  検索失敗の問題は実行によって変わる。`retrieved_chunk_ids` を
  記録したため固定は可能だが、本測定では使っていない
* Bad: 不可答5問は母数が小さい。4/5 と 0/5 の差は明確だが、
  **5問で棄権率を語るのは統計的に弱い**
* Bad: 人手判定は1回の実行の結果である。**複数回回して幅を出していない。**
  判定に数時間かかるため、構成を変えるたびに繰り返せない
* Bad: **この Recall（検索成功/失敗の切り分け）が過大評価を含んでいる**
  （ADR-0047）。「検索成功36問」のうち、答えの項が届いていない問題が
  混ざっている
