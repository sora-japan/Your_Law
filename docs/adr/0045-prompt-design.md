# ADR-0045: プロンプトは文脈を先・質問を後に置き、根拠を条文に限定する

## Context and Problem Statement

検索した条文をLLMに渡す形式を決める必要があった。決めるべきことは
4つある。

1. システムプロンプトで何を指示するか
2. 検索結果（最大10件）をどう並べるか
3. 文脈と質問をどちらの順に置くか
4. RAGなしの経路をどう扱うか

本プロジェクトは法令の質問応答であり、**根拠の条番号が示せない
回答は使えない。** また答えられない質問に答えてしまうと、
利用者が誤った法令解釈を信じる危険がある。

## Decision Drivers

* **根拠（法令名・条番号）を必ず示させる。** 条番号がなければ
  利用者が検証できない
* **答えられないときは答えさせない。** 法令領域では誤答の害が大きい
* **RAGあり/なしの比較で、プロンプト起因の差を作らない**（ADR-0044）
* 文脈は最大10件・1万トークン規模になる

## Considered Options

### 文脈と質問の順序

1. **文脈を先、質問を後**
2. 質問を先、文脈を後

### RAGなしの経路

1. **`build_user_prompt(question, None)` を必ず経由させる**
2. RAGなしは質問文を直接渡す

## Decision Outcome

### システムプロンプトを2本に分けた

```python
SYSTEM_PROMPT_NO_RAG = """あなたは優秀な法令アシスタントです。
回答には根拠となる法令名と条番号を示してください。
確実でない場合は、わからないと答えてください。"""

SYSTEM_PROMPT_RAG = """あなたは優秀な法令アシスタントです。
与えられた条文のみに基づいて答えてください。
回答には根拠となる法令名と条番号を示してください。
確実でない場合は、わからないと答えてください。"""
```

差は1行、**「与えられた条文のみに基づいて答えてください」**だけである。

比較のためには差を最小にする必要がある。RAGなし側から文脈への言及を
消し、それ以外は一字一句同じにした。**RAGの効果を測りたいのであって、
プロンプトの巧拙を測りたいのではない。**

両方に「わからないと答えてください」を入れている。棄権の挙動を
比較するには、**両方に棄権の許可を与えておく必要がある。**
片方だけに書くと、棄権率の差がプロンプトの差になってしまう。

### 検索結果に通し番号と見出しを付けた

```
以下は検索された法令の条文です。

【1】建築基準法 第6条 (本則)
<条文>

【2】消防法 第17条 (本則)
<条文>
```

通し番号を振るのは、**モデルが「【3】の条文によれば」と参照できる
ようにする**ためである。見出しに法令名と条番号を入れるのは、
回答で引用する際の情報をその場に置くためで、条文本文だけを並べると
モデルが条番号を知る手段がない。

本則と附則を区別しているのは、附則の条文が本則と同じ条番号を
持ちうるためである。

条番号を持たないチャンク（`article_num` が空文字）では条番号を
省く。**`db.py` が `OPTIONAL_KEYS` を空文字で埋めるため、
`is not None` ではなく空文字との比較が必要**だった。

### 文脈を先、質問を後に置いた

```
[文脈：10件の条文、数千〜1万トークン]

質問：[質問文]
```

理由は、**モデルは直前のトークンをより強く参照する**ためである。
数千トークンの文脈の前に質問を置くと、質問が埋もれる。

ここで「直前に強く反応するなら、質問を最初に置いた方がよいのでは」
という逆の直感が出た。**逆である。** 「直前」は出力の直前、つまり
プロンプトの末尾を指す。質問を末尾に置くことで、生成開始の直前に
質問がある状態になる。

### context にデフォルト値を付けなかった

```python
def build_user_prompt(question: str, context: str | None) -> str:
```

`context: str | None = None` としていない。**渡し忘れが静かに
RAGなしとして通る経路を作らないため**である（ADR-0040 と同じ理由）。

RAGなしの経路でも、質問文を直接 `generate` に渡すのではなく
`build_user_prompt(question, None)` を経由させる。素通りさせると、
この関数が質問文に何らかの加工（ラベル付けなど）をしている場合、
**RAGなし側だけその加工が効かない。** 比較の前提が崩れる。

## 人手判定が見つけた2つの欠陥（2026-10-29 修正）

ADR-0046 の人手判定で、**文脈の作り方そのものに欠陥が2つ見つかった。**
どちらもコードの修正に帰着した。

### 欠陥1: 項番号を文脈に渡していなかった

`build_context` は法令名と条番号だけを見出しに入れており、
**チャンクが条のどの項なのかを渡していなかった。**

```
修正前   【6】介護保険法 第70条
修正後   【6】介護保険法 第70条第2項第6号の3
```

チャンクのメタデータには `paragraph_num` と `item_num` が入っていたが、
見出しに出していなかった。**モデルは条文本文から項番号を推測する
しかなく、推測を誤っていた。**

人手判定の △ 11件のうち4件がこの原因だった。

```
ts024  内容は第27条第11項と一致している / 項番号を第1項と誤記
ts034  goldの第51条・第55条は両方カバー / 第51条第1項第2号を「第2項」と記載
ts035  内容は全て正確 / 第27条第4項を「調査」とした
ts013  核心は正しい / 項番号2つ誤り（第2項→第3項、第3項→第7項）
```

修正後の再測定（10/29）での効果:

```
ts039  9/9 正解
ts040  5/5 正解
ts032  4欠陥 → 1
ts024  第11項に修正された
```

**2段階判定（○/×）にしていたら、この原因には到達しなかった。**
「× 11件」では何を直せばよいか分からない（ADR-0046）。

### 欠陥2: 枝番が内部表記のまま出ていた

e-Gov の XML は枝番をアンダースコアで表す。

```
9_2        第9条の2
58_11_2    第58条の11の2
5_2（号）   第5号の2
```

**これをそのまま文脈に渡していた。** 結果、回答が
`第9_2条` という、法令の引用として成立しない表記になっていた。

```
10/20 の測定   16問 / 50 に内部表記が残っていた
10/29 の測定   17問 / 50
10/29b（修正後） 0問
```

修正は `src/generation/prompt.py` に関数を足した。

```python
def format_number(num: str, unit: str) -> str:
    """法令番号の枝番表記を、読める形にする。

    e-Gov のXMLは枝番が58_11_2の形になっている。
    そのまま出すと「第58_11_2条」になり、法令の引用として成立しない。
    unitは条、項、号のいずれかで、先頭の直後に挟む。
    """
    num_parts = num.split('_')
    num_str = '第' + num_parts[0] + unit
    for num_part in num_parts[1:]:
        num_str += 'の' + num_part
    return num_str
```


### 欠陥3: 見出しの創作（未修正）

条見出しを持たない法令で、モデルが見出しを創作する。

```
消防法        見出しを持つ条  0 / 263
食品衛生法    見出しを持つ条  0 /  90
```

**RAGあり条件では、文脈内の実在する見出しを模倣する形で起きる。**
`build_context` が見出しのある条には見出しを出し、ない条には出さない
ため、**出力形式が不均一になり、モデルが欠けている側を補完する。**

RAGなし条件では文脈がないため、ゼロから作る形で起きる。
**2つは別の現象である。** RAGあり側はプロンプトの形式に起因する。

修正していない。候補は2つある。

```
案1  見出しが無い条には「（見出しなし）」と明示する
案2  見出しを一切出さない（全条で形式を揃える）
```

**案2は情報を捨てるが、形式の不均一がなくなる。** どちらが良いかは
測っていない。

## 測定結果

### プロンプトの効果（機械的に測れる部分）

| | 結果 |
|---|---|
| 不可答5問での棄権（RAGあり） | **4 / 5** |
| 不可答5問での棄権（RAGなし） | 0 / 5 |
| 法令番号を明示した回答（RAGなし） | 19 / 50、すべて誤り |

**同じ指示を持つRAGなし側では棄権が0である。** つまり
「わからないと答えてください」という指示だけでは棄権しない。
**棄権を生んでいるのは指示ではなく、文脈の有無である。**

棄権した4問の表現。

```
ts015  「回答することはできません」
ts043  「わからないと答える必要があります」
ts044  「明確ではありません」
ts045  「提供できません」
```

### 旧版の「創作が0件」は撤回する

旧版はこう書いていた。

```
検索NG7問での条番号の創作   0件
→ 「与えられた条文のみに基づいて」が機能している
→ 文脈に正解がない7問で、モデルは記憶から正しい条番号を持ち出さなかった
```

**前半（0件）が誤りで、後半（正しい条番号を持ち出さなかった）は正しい。**

この 0件 は `cites_gold` の出力で、「**正しい**条番号を引用したか」を
見ていた。**間違った条番号を創作したかは見ていない。**

人手判定の結果:

```
検索失敗 9問   創作 7件（78%）
```

**7件創作していた。** 指示が効いているのは「正解を記憶から持ち出さない」
という限定された意味であって、「創作しない」ではない。

```
正しい記述   文脈に正解がないとき、モデルは正解を記憶から持ち出さなかった
誤った記述   文脈に正解がないとき、モデルは創作しなかった
```

**「与えられた条文のみに基づいて」は、創作を止めていない。** 創作率を
下げているのは検索の成功であり、検索成功36問での創作率は 5.6%、
検索失敗9問では 78% である（14倍）。

**プロンプトの効果ではなく、検索の効果だった。**

## Consequences

* Good: **棄権が4/5で機能している。** 答えられない質問を評価データに
  含めた（ADR-0034）判断が、ここで回収されている
* Good: **「わからないと答えて」だけでは棄権しない**ことが分かった。
  同一の指示を持つRAGなし側が0/5である。プロンプトの指示より
  文脈の有無が効くという、再利用できる知見になった
* Good: RAGあり/なしのシステムプロンプトの差が1行に収まっており、
  比較でプロンプト起因の差が生じない
* Good: `context` にデフォルト値を置かなかったため、RAGなしの経路でも
  同じ関数を通ることが型で強制されている
* Good: **評価が設計の欠陥を2件見つけ、修正につながった。**
  項番号の欠落と枝番の内部表記。どちらも「精度が低い」では終わらず、
  コードの特定行に帰着した
* Good: **項番号の修正効果を再測定で確認した。** ts039 9/9、ts040 5/5、
  ts032 4欠陥→1。修正が効いたことを数字で言える
* Bad: **旧版の「創作0件」を撤回した。** `cites_gold` の偽を
  「創作していない」と読んでいた。正しくは「正解を引用していない」で、
  人手判定では7件創作していた。**プロンプトの効果を過大に評価していた**
* Bad: **見出しの創作が未修正である。** `build_context` が見出しの
  有無で出力形式を変えており、モデルが欠けている側を補完している。
  修正案は2つあるが、どちらも測っていない
* Bad: **ts016 で棄権が効かなかった。** 「クーリング・オフの通知書の
  ひな形」を求める質問に対し、存在しない「クーリング・オフ制度に
  関する法律」を根拠として提示した。文書作成を求める質問では、
  条文に限定する指示が弱まる可能性がある（未検証）
* Bad: **文脈先・質問後を、逆順と比較していない。** 採用理由は
  一般的な知見であり、本プロジェクトのデータで測っていない。
  入れ替えて50問回せば検証できるが、1回25分かかるため実施しなかった
* Bad: **通し番号と見出しの効果を単独で検証していない。** 番号を
  外した版、見出しを外した版と比べていないため、どちらが効いているか
  分からない
* Bad: **k=10 固定で、件数の影響を見ていない。** `GENERATION_K` を
  増やすと Recall は上がるが無関係な条文も増える。ADR-0046 の
  「検索成功なのに ×  12問」は、10件の中に正解があったのに使えなかった
  事例であり、**件数を減らした方が良い可能性がある**
* Bad: **枝番の修正が Recall を下げた。** 10/29（0.789）→ 10/29b（0.719）。
  検索側のコードは変えていないため、ADR-0042 のばらつきの範囲内と
  考えられるが、**修正と同時に測ったため切り分けられていない**
* Bad: システムプロンプトが `prompt.py` にハードコードされている。
  プロンプトを変えて比較する場合、バージョン管理の仕組みがない
