## 1. プロダクト概要

**一言**: 法律や制度の改正が「自分・自社に関係あるのか」を、
ローカルLLM が根拠とともに判定して伝えるツール。
改正時だけでなく、「そもそもどの法律が自分に関係あるのか」も対象。

**想定ユーザー**: 事業者（および個人）。専門家に頼れない小規模事業者ほど困っている領域。

**技術検証としての位置づけ**:
RAG・SFT・DPO をそれぞれ適用し、どの技術がどの課題に効くかを評価で示す。
成果物は「製品」ではなく「検証レポート＋実装リポジトリ」。

**題材選定の2軸**（本人設定）:
1. 社会意義があるか、人の役に立つか、必要とされているか
2. 技術力の証明になるか、目標（AIエンジニアの知識を持ったPM）に向かっているか

## 2. 確定した設計判断

| # | 判断 | 根拠 |
|---|---|---|
| 1 | 法令データの初期取得は XML一括ダウンロード | 全法令をループ取得する利用方法への懸念（後述の要確認事項あり）。約300MB、取得済み・gitignore済み |
| 2 | 更新は差分検知でAPIから取得 | `law_revision_id` / `updated` の比較で変更法令を特定。負荷が小さい |
| 3 | 断定的な法的判断は出力しない | 弁護士法72条との距離。「該当しうる法令の提示」に留める |
| 4 | 網羅性は保証しない | 漏れが実害になる領域。再現率を定量提示することで限界を示す |
| 5 | 廃止・未施行法令を除外 | `repeal_status` / `remain_in_force` / `current_revision_status` で判定 |
| 6 | チャンクは条単位を基本とする | 「前項ノ未遂罪ハ之ヲ罰ス」型の参照が項単位では解決しない |
| 7 | 本則と附則を分離 | `MainProvision` / `SupplProvision` は性質が違う。附則は改正検知に使う |
| 8 | ローカルLLM を採用 | 準備フェーズ（API取得）と利用フェーズ（オフライン）を分離。ユーザーの事業情報が外部に出ない |
| 9 | ベクトルDBの変更は不要 | 候補モデルが768/1024次元で、pgvectorのHNSW上限2000次元に収まる（DB自体の選定は保留中） |
| 10 | LangChain等の統合フレームワークは使わない | チャンク分割・埋め込み・検索が評価対象のため、中身をブラックボックスにしない。フロー制御にのみ LangGraph を検討 |

## 3. データソース

| 種別 | 出所 | 形式 | 状態 |
|---|---|---|---|
| 法令全文（初期） | e-Gov XML一括ダウンロード | XML | 取得済み（約300MB） |
| 法令メタデータ | e-Gov法令API v2 `/laws` | JSON | 動作確認済み |
| 法令本文（個別） | `/law_data/{law_id_or_num_or_revision_id}` | JSON / XML | 動作確認済み |
| 改正履歴 | `/law_revisions/{law_id_or_num}` | JSON | 未確認 |
| 全文検索 | `/keyword` | JSON | 未確認（評価のベースラインとして使う案） |
| 添付・ファイル | `/attachment`, `/law_file` | - | 後回し |

**出典表示義務**: 政府標準利用規約（第2.0版）準拠。「出典：e-Gov法令検索（デジタル庁）」を
出力とREADMEに明記。法令の条文自体は著作権法13条により著作権の対象外。

### レスポンス構造（確認済み）

```
law_full_text (tag: Law)
  └ LawNum
  └ LawBody
      └ LawTitle
      └ MainProvision      本則
          └ Article (attr: Num)        条
              └ ArticleTitle
              └ Paragraph (attr: Num)  項
                  └ ParagraphCaption   見出し
                  └ ParagraphSentence
                      └ Sentence       本文（attr: Function = main / proviso）
                          └ Item       号
                              └ Column 表の列
      └ SupplProvision (attr: AmendLawNum)   附則
```

`children` は文字列とオブジェクトが混在。再帰時に型で分岐が必要。

### 改正検知に使えるフィールド

`amendment_enforcement_date`（施行日） /
`amendment_scheduled_enforcement_date`（**施行予定日 — 先回り通知に使える**） /
`amendment_promulgate_date` / `amendment_law_title` / `updated` /
`law_revision_id`（`法令ID_日付_改正法令ID` の構造）

## 4. モデル

### 埋め込み（比較検証する）

| | cl-nagoya/ruri-v3-310m | BAAI/bge-m3 |
|---|---|---|
| 次元数 | 768 | 1024 |
| 最大長 | 8192 tokens | 8192 tokens |
| 言語 | 日本語特化（JMTEB 77.2） | 多言語 |
| ライセンス | Apache 2.0 | **要確認** |
| 出力 | Dense | Dense / Sparse / ColBERT |
| サイズ | 310M | xlm-roberta系（大きめ） |
| 備考 | クエリ/文書にプレフィックスが必要 | Sparseは固有名詞に強い。3出力には FlagEmbedding が必要な可能性 |

**比較の段階**:
1. Dense同士で条件を揃えて比較
2. 余裕があれば bge-m3 の Sparse を足してハイブリッド検索（条番号・法令名の検索で効くか）

### 生成

- 候補: Qwen3-8B
- Ollama（Metal）で実行。VRAM・レイテンシを実測する
- **比較候補を2〜3個立てる**（Qwen3-8B / 日本語特化モデル / サイズ違い）

### 学習（SFT / DPO）

- 推論用と同じモデルである必要はない。**1B〜4Bクラスで十分**
- 小さいほど改善幅が見えやすく、条件比較の回数を稼げる

## 5. 実行環境

- Apple M4 Max / メモリ36GB（ユニファイドメモリ。VRAMという区分はない）
- 埋め込み: PyTorch MPS（sentence-transformers）。MLXは不要
- 推論: Ollama（Metal）。MLXは不要
- 学習: **ここだけ検討が必要**

### 学習環境について（重要・要検証）

bitsandbytes は最新リリースで MPS バックエンドが大幅に改善され、
**4bit と LLM.int8() の全構成が MPS で動作する**とリリースノートに記載。
8bitオプティマイザのみ未対応。torch >= 2.9 が必要。macOS 26+ では kernels パッケージ推奨。
位置づけは「実験的サポート（experimental）」。

- 公式ドキュメントはバージョンによって記述が食い違う（v0.45系は「Planned」のまま）。
  **リリースノートと main ブランチのドキュメントを見ること**
- 動くなら松尾研の第6回・第8回資料がそのまま使える
- 動かない場合の代替は MLX（`mlx-lm` / `mlx-lm-lora`）。SFT/DPO を含む10種の学習アルゴリズムあり
- **第1〜2週の空き時間に、小さいモデルで4bit読み込みが通るか確認する**
- Unsloth（第8回で使用）の Apple Silicon 対応は別途要確認

## 6. 保留中：ベクトルDB

**選択肢**

| | pgvector | Chroma |
|---|---|---|
| メタデータ絞り込み | SQLで自由に書ける | 対応するが表現力は劣る |
| ハイブリッド検索 | PostgreSQL全文検索と同一DBで組める | 別途工夫が必要 |
| 学習コスト | [[chishiki-zukan]] で経験済み | 新規 |
| 起動 | サーバーが必要（Dockerでローカル可） | 組み込み型で手軽 |
| コスト | **ローカルDockerなら無料** | 無料 |

**コストについて**: このプロジェクトはローカル実行が前提なので、
Docker で PostgreSQL + pgvector をローカルに立てれば費用はかからない。
知識図鑑のホスティングとは別インスタンスとして扱えばよく、「2つ目が有料になる」問題は起きない。

**判断材料**:
- このプロジェクトは `category` / `repeal_status` / `law_revision_id` / 条番号 での
  絞り込みが中核。メタデータフィルタの表現力が効く
- ハイブリッド検索（条番号のような固有名詞）を試す可能性がある
- 残り時間が限られている。新規技術の学習コストは慎重に

**未決定**。決めたらここを更新する。

## 8. 設計上の未解決論点

- **法令間参照**: 「法第二条第一項」「令和三年法律第四十号」。条単位チャンクでも解決しない
- **但し書き**: `Sentence` の `Function: proviso`。例外規定なので本文だけでは逆の結論になる
- **表構造**: `Column Num=1` / `Num=2` を単純連結すると意味が壊れる
- **文語体法令**: 明治・大正期はカタカナ文語体。現代語クエリで引けるか要検証
- **チャンク粒度**: 8192に収まることと精度が出ることは別。条単位 / 項単位＋文脈付与 /
  上限分割 の3案を比較する

## 9. 工程

**段階方針: 10本で設計確定 → 100本で検証 → 全件**

| 週 | 主タスク |
|---|---|
| 1 | 一括DLの中身確認、条単位パーサー、10本で最小RAG |
| 2 | 要件定義書、業務フロー、非機能要件、評価設計方針 |
| 3 | 埋め込みモデル比較、チャンク設計の確定、100本で検証 |
| 4 | 生成モデル選定、生成制御実験、RAG実装（出典提示） |
| 5 | 全件投入、判定ロジック、範囲外判定、Ollamaで実測 |
| 6 | 評価データ作成と測定 |
| 7 | SFT / DPO 実験と採否判断 |
| 8 | ドキュメント整備、面談準備 |

**遅延時に削る順番**: SFT/DPO実験 → 全件投入 → フロントエンド
**削らないもの**: 要件定義（2週）と評価（6週）

### 松尾研資料の対応

| 資料 | 週 | 用途 |
|---|---|---|
| 第4回（datasets / tokenizer） | 2〜3 | チャンクサイズ設計、トークン長の見積もり |
| 第2回 Step 2（モデル選定 / Chat Template） | 4 | 生成モデル比較 |
